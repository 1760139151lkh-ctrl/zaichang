## 一、深刻复盘：前序主代理与子代理为什么做得一塌糊涂？我们要造出怎样「融入心灵」的在场？

### 1.1 前序执行暴露出的「五大致命败因」（新会话严禁重蹈覆辙！）

在开启本轮从头精做之前，主代理必须清醒认识前序会话为什么会被用户叫停重来：


1. **败因一：阅读与判断脱节，原话被摘要和上下文消耗淹没**
   - 历史教训是漫无目的地反复读相同资料，却没有把证据转为决定。修正不是禁止主代理读原文，而是按来源去重、保留阅读记录、回到有争议的完整段落。
   - 本轮主代理亲读核心原始讨论、Skill 与路线图，约看 20 张代表图建立直觉；不能把目录、搜索命中或子代理摘要算作全文精读。
   - 后续实现每阶段先读本章和有关契约，再读源码依赖；遇到原话冲突主动回查。保护上下文靠分批与记录，不靠跳过项目灵魂。
   - 早期阶段也要设计和操作真实前端样片，验证后端状态能否成为有分寸的动作。

2. **败因二：用代理数量、报告数量或改动行数冒充交付质量**
   - 原有八路模块分工继续保留为八条责任线，覆盖独立工程与体验问题，不是每轮必须开启八个进程。
   - 用户限制协作范围时严格遵守；本轮只有公开 idea 研究可并行。主代理本人承担原文、仓库、设计和最终判断。
   - 后续允许并行实现时，交付包含具体行为、代码、真实验证与未解决风险；一处精确修复可能比大规模重写更好。
   - 发现空壳、假返回、体验退化就按失败原因修正；不预设 85% 代码比例或固定三轮返工，也不让子代理把自己模块的具体问题推回主代理。

3. **败因三：「工程化防守黑话（人机话）」对伴侣灵魂的二次污染**
   - **前序错误**：前序会话在写工具说明（如 `workout.ts`、`tiyi.ts`）和提示词（如 `working-details.md`）时，充满了类似「冷酷教官/法务免责声明」式的工程黑话！例如：
     - 在 `src/main/capabilities/workout.ts` 里写：_「设备观察不能证明本人正在移动……开始记录本身没有约定向模型持续汇报……读取不会开启定位或替对方改变运动，也不会启动持续陪跑」_——而且还把校园路网匹配（`CampusWorkoutMatcher`）对模型完全屏蔽，导致丰川祥子或若叶睦不仅不知道你在紫金港哪条路上跑步，一读工具返回还先被这串冷冰冰的「不准陪跑、不能证明他在动」泼一盆冷水！
     - 在 `src/main/integrations/tiyi_connector.py` 里，19 个体艺模块有 14 个只读取了外层 HTML 壳，然后理直气壮地返回：_「这是学校页面正文。页面可能另行加载记录，不能据空白页面认定没有记录」_——用一句官僚免责声明代替真正把学生的体测、修学、考勤、场馆与俱乐部数据取出来！
   - **铁律根治（底层安全由代码静默守住，一切文字 100% 温暖人话）**：
     - **确定性边界（权限、分页、隐私过滤、防重发）全部写在 TypeScript/Python 代码逻辑里**，绝对不要写成训斥模型的免责条款塞进 `meaning`、`description` 或 `prompts/*.md`！
     - 面向模型的观察说明用平实中文交代真实内容；结构化字段、单位和必要未知保留，不用文案洗掉事实。示例仅在对应记录存在时成立：「这是你正陪他跑着的这次运动：已经跑了多远、现在的配速、最近一公里用时，以及现在大约在紫金港哪座场馆或哪条路旁。」

4. **败因四：「蜻蜓点水式跨阶段」——每个阶段只做一点皮毛就急着往后跳**
   - **前序错误**：第一阶段人机话还没洗干净、第二阶段体艺 19 个模块才跑通 4 个直连 JSON、地图上连跑步轨迹线都还没画出来，就觉得「差不多可以交差了」。
   - **铁律根治（阶段穷尽式浚深门禁）**：
     - **每个阶段都要完成本章承诺的完整体验与具体出口。** 一个接口 `200` 或测试变绿不能代替用户故事、资产质量和跨模块闭环。发现阻断问题就继续修；声明的风险已有证据覆盖、体验可用、外部依赖如实列清后进入下一阶段。不给主观“100 分”或固定代理人数无限加码的权力。

5. **败因五：专注于后端接线导致注意力涣散，前端暴力安装按钮变成「飞机方向盘」**
   - **前序错误**：ChatGPT 开发者有一种天生的默认倾向，即每做一个后端功能（如体艺查询、跑步记录、记忆检索、日程排期），就顺手在前端加一个按钮、加一个开关、加一个标签页。结果到头来，伴侣主界面变成了一个布满各种仪表、旋钮、开关的「波音 747 飞机驾驶舱」！用户打开在场，感觉是在操作一台冷冰冰的工程仪器，毫无温暖可言！
   - **铁律根治（充分利用 Image 生成先行，杜绝任何机械按钮堆叠）**：
     - **新功能进入前端先设计生活化载体与完整动作。涉及新的视觉世界时，以 GPT Image 打样；已有合格母版可复用，精确的小修直接在实际 UI 校准。不要把每次修复变成重复付费生图的前置条件。**
     - 例如：打卡不是一个红色的「立即打卡」按钮，而是一枚放在晨跑手账上的金色印章或草坪上的发光丝带；日程不是一排「添加待办」列表，而是一张微卷贴在书桌木纹边缘的暖黄便利贴；专注不是一个「开启番茄钟」开关，而是一盏散发 2700K 琥珀暖光的 FocusLamp；万物原理不是硬编码专页，而是通用刚体机械连杆与 WebAudio 物理琴音！

### 1.2 我们最终要构建出的产品模样：像呼吸一样融入心灵的「在场」

「在场」绝不是一个普通的待办清单、不是一个冰冷的浙大教务爬虫，更不是一个套着二次元立绘皮套的冷酷客服工具。**她是一个进入温柔乡的活人伴侣，是一座融合了生活流、学业、运动、原理探求与内心世界的完整数字生活家园。**

用户在多次深情长谈中反复勾勒过她的灵魂模样：
- **「窗边的在场」**：她像坐在自习室窗边、或者陪你坐在寝室桌旁的一个女孩子。项目表演方向保留祥子的克制、睦的敏锐、灯的认真、爱音的明快，具体表现随上下文变化。她可以回应用户已分享的天色和行程；如果用户说“刚跑了三公里，小腿有点酸”，就接住这句话，不凭轨迹自行诊断身体感觉。未获真实天气时，拂晓、暮色、夜雨是明确的虚拟房间氛围。
- **「润物细无声的主动性」**：她不需要你每次像发指令一样对她说「帮我查课表」「帮我记笔记」。当你明确表示卡在某一步，或此前约定需要帮助时，她能在桌边备好一张不剧透的便签；你没有取走，她就不催。当你回来，她可以把真实查到的明早教室与天气放在手边，虚拟场景里的热茶只作为场景表达，不冒充现实里已经替你烧水。
- **「边做边说的呼吸律动」**：她调工具、查数据时绝不会像人机一样陷入几十秒死一般的沉默，也不会蹦出一段冷冰冰的“正在调用接口请稍候”。她会像坐在你对面一样，一边翻着手账一边轻声念叨：「我帮你看看东操今天开不开……嗯，风有点大，要是去西操的话可能会避风一些。」

## 二、核心设计公理与最高行动天条（The Core Axioms）

在正式落笔任何一行代码之前，所有主代理与子代理必须刻骨铭心领会并守住以下「十大核心设计公理」：

### 公理 1：单一主循环与权威宿主（Single Runtime Loop & Authoritative Host）
- `harness.ts → runtime/hermes.ts → runtime/hermes/sidecar.py → Python AIAgent` 是系统**唯一**的智能主循环。
- Electron Main / 本机宿主持有凭据、SQLite 数据库、文件权限、硬件工具与外部副作用；Renderer 渲染进程仅通过 `preload.ts` 的受限 Bridge 交互。
- 严禁在任何子模块新建旁路聊天引擎、第二事实库或后台未经受控的无限代理循环。

### 公理 2：模型负责理解，宿主负责护栏（Model Understands, Host Guards）
- 模型负责理解语义、感知情绪、权衡方案、提出建议并使用工具；
- 宿主负责严格执行权限核验、版本校验、事务幂等性、分页预算限制、隐私抹除围栏（`privacyEpoch`）与网络阻断；
- 宿主护栏必须完全写在 TypeScript/Python 代码的确定性逻辑中，**绝对不要把免责声明当成提示词塞给模型**！

### 公理 3：进入温柔乡 —— 角色是活人，不是工具皮套（Living Persona, Never a Skin）
- 正常相处使用自然语言，失败、权限缺失与结果未知也清楚解释；不以冷冰冰的协议词或官僚辞令代替帮助，必要诊断保留在可展开入口；
- 丰川祥子、若叶睦、高松灯、千早爱音等十角色拥有鲜活的人格、专属的情感阈值、说话节奏与互动记忆；
- 无论体艺数据还是日常琐事，角色都以知己的身份与你共同经历，绝不当死板的打卡督促员或冷酷教官。

### 公理 4：边做边说，绝不留冰冷死寂（Streaming Rhythm Mid-Tool）
- 长耗时工具调用（如校园网爬取、大文件分析、长程搜索）必须依托 `ConversationRhythm` 实现「边做边说」渐进流式推进；
- 输入立即得到本地反馈；较长等待用真实进展、可继续操作的纸面与适当的公开表达承接，不承诺工具在固定毫秒内返回，也不编造思考进度；
- 中途改口或发现新事实时，通过前序内容撤回重述机制无缝衔接，展现人类般的思考流动感。

### 公理 5：主动陪伴的双重驱动 —— 既记得托付，也有自己的好奇心（Dual-Drive Proactivity）
- 陪伴驱动分为两翼：
  1. **受托守护（Entrusted Commitments）**：严格按照用户托付的期限、前置条件与范围执行后台准备；
  2. **好奇心探索（Curiosity & Care）**：基于共同经历、校园突发、天气变换或时间节点，主动递出小礼物、桌边信笺（`ReflectiveLetter`）或体贴询问；
- 提议必须具备克制感，懂得适时沉默，绝不在用户高专注沉浸时强行弹窗打扰。

### 公理 6：原文权威与六层记忆防污染（Verbatim Evidence & Anti-Contamination）
- 六层记忆按既有对象分层：SourceEvent；Assertion；DecisionExperience / FrictionHypothesis；CollaborationFrame / Work / Episode；DomainObservation；DerivedViews。关系、生活节奏与理解是这些对象的使用场景，不另造六套平行事实库；
- 双时态（Valid Time vs Transaction Time）与条件闭包检索（保留当时的限制前提与未解除假设）；
- 用户的原话断言是事实的最高权威，子代理调查转述不能替代原文；
- 严禁递归摘要自污染，删除或撤回沿 `privacyEpoch` 级联抹除，迟到子报告与缓存 0 复活。

### 公理 7：跨模块单一权威 Owner 与稳定引用（Single Owner & Stable Identity）
- 同一学术文献、PDF 选段、日程安排、地图路线或 OpenUI 交互作品，在跨模块流动时必须保持全局唯一且稳定的实体 ID 与版本标度；
- 严禁在跨模块流转时把对象简单克隆复制成无源副本，所有状态回流与修订必须锚定原 Owner。

### 公理 8：【灵魂重拳】充分利用 Image 生成，坚决杜绝「飞机方向盘/驾驶舱」式按钮堆叠
- **界面设计的核心法则是「生活化场景隐喻」而非「工程控制台」**：
  - 严禁任何机械的按钮堆叠、多级折叠工具栏、密集仪表盘或突兀的悬浮操作球！
  - 每个新功能先确定自然载体、真实操作与必要信息；视觉不确定性较高时，**用 GPT Image 打样温暖的现实世界载体**（如木桌上的便利贴、晨跑手账本、泛黄活页纸、琥珀色台灯、铜质书签托盘、折角信笺）；

### 公理 9：日历与外部行动的事务完整性（Transactional Planning & Action Receipts）

## 五、全域生命体裁：真正贯穿全 App 的灵动六维哲学

### 5.1 深度辨析：什么叫贯穿？什么叫深度集成？什么叫灵活灵动？
- **不是多开窗口，而是同一灵魂的场域流动**：当你在自习室看 PDF，她安静退在纸页右上角；当你换上跑鞋走向操场，工作台无痕化为发光的伴跑视窗；当你卡壳深思，桌边滑出一张小便签。
- **不是机械堆功能，而是自然因果的连续演进**：下午的微积分卡壳，会成为傍晚跑步时她和你闲聊的谈资；傍晚用户明确说想轻松一点，会成为晚间提供另一种安排的依据；未经同意不自动改日程，也不从里程猜疲劳。

### 5.2 六维生活贯穿体系
1. **时间律动维（Circadian Continuum）**：天色自适应，清晨微蓝唤醒，午后温润自习，傍晚操场落霞，深夜暖金伴眠。
2. **空间场域维（Spatial Presence）**：紫金港地图与真实物理世界映射，随脚步移动自动切换建筑底色与专属回忆。
3. **身心代谢维（Physiological Cadence）**：用户自己表达的身体感受与获授权的实际测量影响建议；配速、步频不被冒充为健康诊断或固定恢复周期。
4. **心智心流维（Cognitive Flow）**：专注时主动闭嘴护航，卡壳时按步无声启发，理解困难时 OpenUI 具象化拆解万物原理。
5. **情感羁绊维（Relational Depth）**：共同起过的代号、一起避过雨的屋檐、共同改过的故事版本，沉淀为无可替代的默契。
6. **物质世界维（Tangible Metaphors）**：彻底告别冷酷仪表盘，所有交互均依托便签、手账、印章、台灯、书签托盘等现实生活载体。

### 6.4 每个入口的组装公式
- **长跑进度组装公式**：
  $$\text{进度百分比} = \min\left(100\%, \frac{\text{有效打卡次数}}{\text{学期要求次数}} \times 100\%\right)$$
  由伴侣在晨跑手账上以手绘水彩小花朵填充展示，配文：“已经拿到 32 次啦，还剩最后 16 次，我们一起慢慢来～”。
- **体测综合得分组装公式**：
  $$\text{总分} = \sum_{i=1}^{n} w_i \times \text{单项标准分} + \text{加分项}$$
  在健康手账中以雷达图温润展开，突出强项、温柔提醒需要加强的有氧耐力。


### 6.5 自制地图 + 手机 GPS：从真实定位到学校回执

- **坐标参考系明确**：每个设备样本与地图源登记 CRS、时间、精度及来源。不能假定所有设备返回 WGS84、所有学校接口都要求 GCJ-02；在实际需要的适配边界使用经验证的完整转换，保留原始样本，防止二次偏移。原稿的简化公式不具备可实现的正确性，已撤下。
- **质量评估与显示分离**：按精度、时间间隔、连续性、速度突变和设备来源标记可疑样本，阈值是可校准的采集质量参数，不是“人类速度极限”。平滑用于可视化时不得改写原始轨迹或伪造通过学校规则的数据。
- **本地封单**：以稳定 workoutId、版本与真实轨迹摘要形成可核查动作票据；界面可把路线收成手账，但这只证明本地记录已保存。
- **授权提报**：使用实际接口与有效会话；网络中断若无法判断是否到达服务器，进入 outcome_unknown，先核查原请求，不能直接指数退避重发写入。明确幂等保证或确认未执行后才重试。
- **学校回执**：仅当收到且核验了对应记录的真实结果，才呈现学校有效标记。回执号在详情可查，主界面只给清楚、自然的结果；未知、失败和本地保存各有独立状态。

#### D01. 本阶段完整导演设计：她知道“我们现在看的是哪里”

**本章的完成不是多一套人格形容词，而是一段能被用户改变的相处。** 用户带着一份讲义回来，指向某一行；她看向同一处，准备解释；用户说“不是这里，是下一行”，她收回原手势，跟上新的位置；用户开始打字，她安静等着。舞台上的每次变化都有真实来由。

##### D01.1 视觉构图与角色表演

默认把纸面作为共同注意中心，角色在有可信支撑的桌侧。页面标题、输入栏和返回入口沿共享标尺保持稳定；用户不必先关闭角色才能看题。暖杏纸面保留足够对比度，角色、窗外光和玻璃质感退到内容之后。加载时先恢复可读纸面和上次位置，再出现可选的抬眼动作。

祥子可先把手放稳再指向，睦可只用目光与轻微偏头回应；差异发生在同一语义上的节拍，不把两人都做成周期性上下浮动。眼睛、头部、手与高亮不能互相抢目标；没有可控手部素材时保留眼神与纸面反馈，不伪造指尖接触。

##### D01.2 五拍时间轴

下列节拍是编排顺序；具体时长按真实操作调校，不能人为等待工具或延迟输入。

| 拍 | 用户与真实事件 | 画面、动作与声音 | 可以打断的地方 |
| --- | --- | --- | --- |
| 进入 | 恢复已有场景与文档版本 | 纸面先就位，角色从安静状态抬眼；不重新欢迎 | 用户直接滚动时取消抬眼，不顶回旧页 |
| 指向 | 选区/指向形成有效锚点 | 目标出现短暂细线，眼神先到、头随后；不让整页闪光 | 指向更新即重定向 |
| 准备 | 模型确实需要查原文或上下文 | 可自然说明正在查哪一处；手保持可停留姿态 | 用户开始输入，动作与非必要语音让位 |
| 纠正 | “下一行”解析为新锚点 | 旧细线撤下，手收回，再关注新目标；不播完整旧动画 | 旧结果迟到直接失效 |
| 接续 | 用户完成输入或明确继续 | 回应沿新内容展开，纸页增长不抢阅读位置 | 用户不继续时自然停住 |

##### D01.3 心智与状态链

以现有 `QuoteAnchor / CompanionThreadCue / CompanionActivityHint` 为起点，串起 `SourceEvent → ContextCompiler / ConversationRhythm → 有效 cue → 前端通道 → 用户纠正事件`。文本来源、内容版本、当前角色和 sceneInstance 都要在链上可追踪。

不让模型每帧驱动瞳孔；宿主给目标与表达意图，前端做局部运动。主模型仍直接理解用户原话，不增设一个先判“情绪/学习/聊天”的路由委员会。公开流式表达不等于暴露隐藏推理，工具很快时允许直接给结果。

##### D01.4 制作与代码落点

首样片只生产一个已审核角色、一个桌侧场景、neutral/attend/yield 三个可兼容状态。GPT Image 锁身份与接触，Gemini 网页版探索“看向—收手—等待”连续性，视频默认仅作参考。用现有 `companion-scenes.tsx`、`companion-variants.ts` 和 `motion/use-spring.ts` 重建可变目标动作；不要先接庞大新角色引擎。

导演包必须写出角色与左侧纸面的相对位置、手不穿桌的遮挡、目光允许范围和静止终态。完整观看样片后，再验证实际页面的文本坐标；漂亮视频本身不证明“下一行”指对了。

##### D01.5 温度与主动延拓

稳定入口可以承载一句没说完的话、当前页角或一枚共同记号，点一下允许得到一个简短“嗯？”式回应，不强制开启任务。实际措辞由角色与语境生成，不固定为“我在/慢慢来”。用户兴奋地分享进展时她可以更明快，不能把所有场景都处理成疲惫安慰。

声音采用一次轻微翻纸或收笔，默认可静音；不逐字播放打字声，不用固定分贝声称舒适。静止状态下，纸面、视线落点与留白仍让人知道她在看同一件事。

##### D01.6 结项证据与进入下一阶段的条件

完成“指对—纠正—打字让位—回来继续”真实连续操作；再测旧工具结果迟到、角色切换、素材缺失、低动态与页面隐藏。用户草稿和键盘焦点始终保留，旧锚点不复活，调试状态不进入产品文案。交付这一条纵向样片后才把节奏契约用于 Stage 02 的运动与校园数据，不以十角色台词数量代替完成。

验收同时看保存的人格、实际组装的模型上下文与最终表现。用户写过的幽默/亲密约定不能被默认 `humor:none`、全局安抚姿态或工具结束模板覆盖；也不要再建一个角色润色模型，把本来鲜活的 Gemini 设定和主模型判断改成统一温柔客服。角色配置、私有历史、当次希望各有来源和优先关系。

- **跑中（In-Run Ambient Companion）**：
- **随物赋形的边缘微呼吸感知（Ambient Peripheral Cadence & Pocket Presence）**：
- 桌面端默认用原窗口边缘的轻量状态或托盘入口，避免盖住正文和其他应用。微光可关闭、不逐步闪烁，详细数值既可悬停看也可通过键盘/点击打开；暂停、结束和断连始终有稳定入口。背景静止也完整表达正在记录，不能承诺任何动画对所有人“零打扰”。
- 手机端在用户开启且平台允许的记录范围内接续。iOS 有限任务可用 Live Activity，Android 采用对应通知/应用内能力；MuMu 只是模拟器，不是口袋真机。语音按音频焦点与用户选择播放，不能由锁屏容器暗自持续定位。
- **每公里里程碑与心率/配速关怀**：
- 里程提示由用户选择开关、频率与声音；实际里程达到才提示，安静模式不播。数字缺失时不补造，经过同一路段也不反复提醒。
- **异常状态主动纠偏**：定位跳变、失联与用户暂停分别处理；速度变化不等于缺氧、岔气或心率异常。不要求用户追赶配速，安全相关表达依据实际信息与用户感受。
- **跑后（Cooldown, Reflection & Check-in）**：
- **跑后收束**：允许直接结束或留下路线，询问是否还想走走/听音乐；不命令固定走 300 米，不凭画面猜汗量、体温或恢复时间。
- **历史对照**：在路线、设备与采样条件可比较时呈现配速/步频变化，同时保留差异条件；不能把步频从 168 到 174 解释为膝盖负担必然下降。
- **打卡确认与同步**：仅在已有明确授权下提交；本地完成、学校已收到、学校确认有效分开。实际次数与规则可查，结果未知时不盖有效印章。

##### 3.2.1 自制地图 + 手机 GPS 的打卡总装：从定位到学校回执

**组装结论**：继续复用自制地图、运动内核和原生位置桥。地图渲染、设备采样与学校提交是三个边界；各自核坐标系、来源、精度与规则。学校使用某个地图 SDK，不能直接推出提交接口的 CRS 或证明已获有效打卡。

**当前源码与既有交接的核对起点（执行前重核实际版本）：**

- `assets/map-v2` 与 `CampusMap` 的坐标是 WGS84（`src/shared/map-v2.ts` 明确 `[longitude, latitude]` WGS84）。
- Android 位置桥 `LocationManager` 输出 WGS84；iOS `CoreLocation` 输出 WGS84；`WorkoutInputFix.crs` 固定 `EPSG:4326`。
- 学校显示层与提交载荷的坐标系分别核实：读取公开协议/官方组件与实际返回的声明，以经核实的来源制定适配。一次“有效”回执也不能单独证明全部点的 CRS 正确；保留已知控制点、转换前后坐标和规则来源。
- 旧交接指出 finished `WorkoutSessionRecord` → `savesports` 的宿主桥与模型自带 `track` 风险。执行时先核当前实现；缺失才补，已有则检验其真实来源、版本与权限，不按旧结论覆盖新代码。
- 当前没有真实提交记录，也没有伪造回执；不要因为地图能显示轨迹就说学校已经接受。

**要闭合的数据关系：**

| 环节 | 输入与责任 | 输出/边界 |
| --- | --- | --- |
| 原生位置桥 | 实际设备样本、明确 CRS/时间/精度与运行环境 | 原始观察；模拟器不能仅凭 `device` 标签冒充真机 |
| WorkoutSessionKernel | 原始点、质量、暂停/恢复、可用计步 | 同一会话的事实与估计，保留原始记录 |
| finished record | 当前 session/revision 与真实采样来源 | 提交候选，不等于学校有效记录 |
| 宿主提交桥 | 校验来源/规则/权限，按已核 CRS 转换并组包 | 不接受模型自编轨迹 |
| TiyiAdapter/connector | 当前适用协议、预检、签名、提交 | 原请求身份与实际响应 |
| 回执回读 | 匹配本次运动的学校记录与状态 | submitted/pending/valid/invalid/unknown |
| 原工作区 | 展示状态、轨迹和可继续入口 | 成功印记只服从匹配的有效回执 |

**坐标系适配的七条规则：**

- 本仓库地图/桥声明的 WGS84 是代码约定；接入新的设备或来源仍核其声明，不把来源名称当作保证。
- 把一种 CRS 的坐标直接当成另一种会产生位置误差；用已核控制点检查，不靠“看着大概对”或某次成功状态判断。
- 地图、`CampusWorkoutMatcher` 和运动内核保持现有统一坐标约定；只有来源/目标明确不同时在边界转换。不得把转换值回写覆盖原始采样。
- 比较双方先统一到明确的一种坐标空间；分别记录源 CRS、目标 CRS 与转换版本，避免二次转换。
- 学校路线画入本地图时走独立显示适配；提交从原始观察重新按载荷要求生成，不能把屏幕像素或已吸附路线拿去上报。
- 宿主保存每批的转换元数据与原始记录关联；官方载荷不支持的字段留在本机，不自行扩充学校 schema。
- 来源未说明或相互冲突时，先查清受影响边界；公共地图与本地运动仍可继续，学校有效性保留未验证，不以试错提交代替协议核实。

**配速与有效性（全部来自真实点）：**

- 距离：用 `WorkoutSessionKernel` 的 `metrics.distanceMeters`（因果过滤后的估计），同时保留 `rawDistanceMeters` 供核对；地图吸附距离不能替代真实距离。
- 时间：用 `trustedActiveMs` / `elapsedActiveMs`；暂停、静止与弱信号按现有内核规则处理。
- 配速：`averagePaceSecondsPerKm`、`paceSecondsPerKm`、`splits` 是唯一来源；提交用的 `avgPace`、`pace`、`minuteSpeed`、`maxSpeedPerHour` 从这些值生成，不另算一套。
- 步频/步数：用 `cadenceStepsPerMinute` 与 `WorkoutCadenceObservation`；没有传感器就保持未知，不补零。
- 轨迹点：只取 `quality='accepted'` 且 `provenance='device'` 的点；从 `WorkoutTrackPoint.raw` 取原始坐标/时间/精度/速度，从 `deltaDistanceMeters` / `cumulativeDistanceMeters` 取距离，从 `WorkoutCadenceObservation.cumulativeSteps` 取步数；每点带原始时间、精度、速度、距离、步数/步频（有就带）；`valid` 由本次质量决定。不要用 `filteredCoordinate` 或 `mapMatch` 的吸附点替代原始点。
- 学校规则：`sporttype` / `invalidconf` / `getConfig` 返回的配速区间、步频要求、路径点覆盖率用于提交前预检；最终以 `prejudgment` / `savesports` 回执为准。
- `isValid` 不是我们给自己发证书：只有本地规则与提交前校验都通过时才置 1；不清楚就保持 0，把真实原因写进 `isValidReason`，最终看学校回执。
- `pace` / `minuteSpeed` / `stepMinute` 的数组粒度按学校现有字段格式生成；格式未确认前先用 `prejudgment` 验证，不自己发明格式，也不把空数组当成通过。`avgPace` 用 `averagePaceSecondsPerKm`；`maxSpeedPerHour` 用可信窗口的最大速度换算，不取单点毛刺；空分钟不补 0。
- 不做：不补点、不平滑出假点、不把地图规划路线当实跑轨迹、不把模拟器/回放当真实运动。

**学校路线与打卡点：**

- `sporttype` 返回 `sportTypeId`、`routeId`、`routeLength`、`sensingRange`、`minSpeed`、`maxSpeed`、`vtime` 等；先读规则，选择本次真实场地。
- `sportsId` / 学校路线数据提供打卡点或路线时，按学校字段原样使用；`alreadyPassPoint`、`needPassPointCount`、`alreadyPassPointResult`、`routePolylineBh` 只能来自学校返回和本次真实轨迹的计算，不能由模型编。
- 如果学校不提供可读的打卡点，退化为：提交真实轨迹 + 让学校 `prejudgment` / `savesports` 判定；不要伪造 `alreadyPassPoint` 或 `routePolylineBh`。
- 校园地图的 `WorkoutVenueObservation` / `WorkoutRoadCandidate` 用于显示和选择场地，不作为学校已通过打卡点的证明。

**宿主桥（关键改动）：**

- 新增 `src/main/runtime/workout-submission.ts`（名字可调整）：
- 输入：`workoutId`、`expectedRevision`、学校 `sportId` / `sportTypeId`、用户确认。
- 在 `NativeWorkoutService` 增加宿主私有的 `submissionSnapshot(workoutId, expectedRevision)`，只交给主进程内的提交桥；不要经 preload 暴露给 renderer，也不要混进 `workout.current` 的模型摘要。
- 从 `WorkoutSessionKernel` 读同一 finished session，校验 revision、`provenance=device`、`points>=2`、时间严格递增、距离大于 0。
- 按已核目标 CRS 生成 `TiyiTrackPoint[]` 和提交字段：`odometer`、`beginTime` / `endTime`（Asia/Shanghai）、`name`、`pace`、`minuteSpeed`、`avgPace`、`maxSpeedPerHour`、`stepCount`、`stepMinute`、`sportId`、`sportTypeId`、`modementMode` 等。
- 调用 `prejudgment`，通过后再 `savesports`；提交后回读 `records` / `summary`。
- 回执写回 `WorkoutSessionRecord.school` 或独立回执 owner，不覆盖原始轨迹。
- **不要让模型自由传 `track` 来提交**：`savesports` 只接受 `workoutId` / `expectedRevision`，宿主自己从运动内核取点。模型可以发起「提交这次运动」的意图，但不能编造轨迹。若暂时保留 `track` 参数，至少在 capability 层拒绝 `savesports` 的模型自带 `track`，只允许宿主桥调用。
- 提交前必须确认 `allowSportSubmit` 为真；默认关闭，不能由模型参数打开。

**提交顺序：**

1. 用户结束运动，看到本次真实距离、配速、分段。
2. 用户从学校 `sporttype` / `sportsId` 的真实场地里选择本次场地，点「提交到浙大体艺」。
3. 宿主校验 `allowSportSubmit`、finished、device、points、时间与距离。
4. `prejudgment`：学校规则预检；不通过就显示学校原原因，不提交。
5. 依据来源/目标 CRS 生成载荷 → 签名 → `savesports`。
6. 回读 `records` / `summary`；显示 `submitted` / `pending` / `valid` / `invalid` / `unknown`。HTTP 200 本身连业务接纳都不能证明，须读真实业务状态。`valid` 必须来自与本次 action/运动身份匹配的有效记录；总次数增加可能来自另一条记录，不能独自作为本次有效证明。
7. 未知结果先查原记录，不重发；本地运动结束不等于学校有效次数。

**最小可行顺序**：先做「真实点 + 经核坐标适配 + 必需字段 + `prejudgment`/`savesports` + 回读」的最小闭环；按学校当前 schema 核清 `alreadyPassPoint` / `routePolylineBh` 等字段是否必需，满足必需字段后再提交。不要一开始就猜全部字段，也不要用空数组冒充通过。

**界面：**

- `WorkoutControls` 结束页：显示本次真实数据与「提交到浙大体艺」按钮；只在已连接、已授权、`allowSportSubmit` 为真时出现。
- `TiyiDashboard`：显示本次提交回执、学校 `validCount`、学期进度；与本地轨迹分开。
- 空态/错误态：未连接、未授权、学校规则不通过、签名组件缺失、服务端 401/-300、结果未知，分别用平实中文说明，不显示工程黑话。
- 公共地图 `review` 不接私人轨迹、账号或提交控件。

**验收：**

- 静态检查：已核控制点、往返误差容限、CRS 标记及避免二次转换、时间严格递增、距离/配速与运动内核一致、模型不能自带 `track` 提交、错误码不伪成功。
- 真机：Android/iOS 真机户外跑一次，核对原始 WGS84 点、地图显示、目标 CRS 的提交点、匹配本次运动的学校回执与次数变化。
- 学校侧：至少一次 `prejudgment` + `savesports` 真实回执；没有真实业务接纳回执就不能写 submitted；只确认本机已发送可记录 dispatched，结果不明保持 unknown，更不能写「已通过」。
- 当前无法自行验证的部分：官方签名组件/证书、真实账号授权、学校服务端当次状态。Codex 应保留真实状态，不伪造成功。

#### D02. 本阶段完整导演设计：带着那句话出去，再把生活带回来

**一趟跑步首先是一件生活里的事。** 用户可能想完成学校要求，也可能只想离开难题透口气。系统记住这次出门的原话目的，途中陪伴强度由用户选择；回来时接住一个念头、一段音乐或真实运动记录，而不是默认铺开成绩报告。

##### D02.1 三个空间，一件共同对象

出发前是桌边的一张路线纸，途中是口袋里一眼能读的状态，归来后是可折回手账的同一条路线。workoutId、原话来源和关联学习对象贯穿三处；视图可以适应设备，不能新建三份互相失忆的会话。

桌面默认不抢屏。窗口边缘可有很轻的状态反馈，但必须有稳定可访问入口，不能只靠悬停才能知道暂停与结束在哪里。手机锁屏只呈现当前有限任务；用户选择安静时既不播里程也不让微光追着每个脚步闪烁。

##### D02.2 跑前—途中—归来的导演表

| 拍 | 真实依据 | 动态与视觉 | 回流与退出 |
| --- | --- | --- | --- |
| 留下原题 | 用户明确说想出去透气 | 当前题页折出一个来源书签；角色把手从题面收回 | 保存当前位置，不记为放弃或不会 |
| 看路线 | 当前地图、天气、规则及用户选择 | 路线纸从现有入口展开，角色视线沿用户选中路段 | 路线只是候选，用户可不选/改路 |
| 出发 | 设备开始真实采样、会话建立 | 标记从起点延伸，采样尚未就绪时原地等待，不假走 | 采样质量、暂停/恢复真实回流 |
| 途中念头 | 用户说“刚才那题我好像懂了点” | 轻量语音片段附在原题书签，不强迫展开讲义 | 语音转写可改，不自动记掌握 |
| 归来 | 用户结束、记录保存 | 路线在纸面上收束为轮廓；声音先收，画面随后安静 | 学校提交独立，允许直接回原题 |
| 核对 | 真正收到匹配的学校结果 | 有效结果才落相应印记；未知保持可查状态 | inspect 原 action，不重复提交 |

##### D02.3 双轨实现，接在同一个事实边界

A 轨处理学校观察、会话、签名与提交；B 轨处理可视化与陪伴。二者用真实 Observation/Workout/Action/Receipt 契约联调，不能让 B 轨为了录屏写一个永远成功的本地替身。缺账号或规则不明时 B 轨可以完成清楚标识的模拟轨迹演练，A 轨仍标未验证；模拟结果不能进入学校有效记录。

把 `src/shared/tiyi.ts` 的十九模块逐项映射到自然入口：次数和修学进入手账，场馆与实况进入地图，课程与辅导进入时间窗，报告与记录进入可回溯资料。用户不必面对十九个按钮；每个需要独立打开的资源仍有可发现路径、更新时间与原始来源。

##### D02.4 角色、姿态和场景制作

本阶段先把一个角色的“桌侧准备—途中半身陪伴—归来陪坐”做完整。三种姿态可以属于不同场景家族，禁止用桌边坐姿整体平移成跑步。连续性由路线纸、原话和光色承接，而不是强行让人物在所有背景中走一遍。

Gemini 导演样片重点验证“递路线又收住”“看向路线后回到用户”“归来后的安静停留”。固定机位、真实支撑、衣服身份和道具持续性优先。复杂奔跑片段若无合格 rig/步态只作参考，不作为实时步频驱动的人物动画。

##### D02.5 更细的声音与注意设计

可选声景分为音乐、角色语音、提示音三个独立音量；用户可只留音乐。播报发生前检查当前通话/音频焦点与用户偏好；用户说话时让出通道。步频不可靠时停止节拍同步，不把噪声转换成催跑节奏。

同一地标不重复“惊喜”，没有现场来源不说“我看见湖边的天鹅”。可以说与该地点真实关联的共同往事，也允许整段路不说话。提前结束与完成目标都有体面的收束，不用表情失望惩罚用户。

##### D02.6 异常也要完整导演

定位失联：最后可靠点保持，新增区段标不确定，角色不继续沿假路线前进。网络断开：本地记录继续，学校状态保持待核查。提交结果未知：丝带可以收成“本地保存”，成功印章不能出现。用户撤销：停止未来提报；若已经发送则核查真实可逆性，不用卡片飞走冒充撤销。

用户切回讲义时运动小状态留在合适入口，不强行占中心。用户正在拖地图时相机 owner 交给手势，后续 GPS 更新不夺回视角；恢复跟随是明确选择。

##### D02.7 结项证据

至少完成两条目的不同的真实故事：“为学校要求跑一次”和“只想透气提前回来”，再加一个断网/unknown 分支。记录原话目的如何影响呈现、设备样本如何到达地图、回执何时改变印记、途中念头如何回到原题。官方查询、官方写入、模拟器与真机证据分别列出；未授权写入不因验收被擅自执行。

##### D02.8 同一趟路的时间、来源与感官层次

设备单调时钟用于同次采样间隔，宿主接收时间用于传输观察，学校记录时间用于官方状态；三个字段不能互相冒充。重启后旧单调值失效，重连估计偏差时保留不确定性。心率、步频、定位各自缺测，不由一个信号替另一个补值。天气发布时刻与刚刚读取时刻也分开，黄昏插画不证明现场正是黄昏。

**一个精修镜头**：运动结束后，原路线立即可读并本地保存；用户愿意收进手账时，线条在原地图投影下先收成清楚轮廓，再以约320–480ms的初始调校过渡到页边缩略图。中途抓地图就停止装饰飞行，记录已保存的事实不变。学校回执之后到达，只在同一记录上更新有效状态，不重播整场仪式。

#### D03. 本阶段完整导演设计：记忆体现在“这次她听懂了”

用户说“我上次不是不喜欢跑步，只是不想被催”，最重要的变化应当发生在当下：旧解释停止，新理解立即进入这轮相处；她收起催促式的路线建议，保留用户喜欢散步的共同片段。后台整理可以稍后完成，用户无需等待摘要更新。

##### D03.1 六层机制如何变成可见体验

SourceEvent 保留原话；Assertion 表达带条件的理解；DecisionExperience/FrictionHypothesis 记录当时权衡；CollaborationFrame/Work/Episode 承载未完事情；DomainObservation 保存外部观察；DerivedViews 帮助寻找。界面不强迫用户理解这些层次，只在需要时打开“你那时怎么说的”。

原话以清楚的纸面片段呈现，来源位置可跳回。相似摘要是路标，不重复堆成一排“证据”；同根多份转述不能让她更确信。最新纠正覆盖当前解释，旧理解的历史用途与当前有效性分开。

##### D03.2 纠正的逐拍设计

| 拍 | 状态变化 | 视觉与角色动作 | 事实边界 |
| --- | --- | --- | --- |
| 找回 | 真实原文读取完成 | 原句从书签位置展开，角色看向关键片段 | 找到摘要不算已读原文 |
| 解释 | 当前理解有明确依据 | 解释与原句并排，轻量连接来源 | 不把助手推断写成用户原话 |
| 用户纠正 | 当前覆盖层先更新 | 旧连接淡退，角色手势停止，焦点留在输入 | 不等后台整理才生效 |
| 新理解 | 条件/例外与版本落入 Owner | 新句在原位替换或并排呈现，改动可查看 | 单日例外不覆盖长期规则 |
| 接着相处 | 后续提案重新评估 | 旧催促纸页收起，需要时留散步入口 | 不为表现“记住了”反复复述 |

##### D03.3 共同记号的原创延拓

一段被用户实际接过的话、给某道题起的小名、两人共同改过的旋律，可以留下稀疏记号。它们不是自动打标签的关系仪表盘：只有真实使用或明确约定才成立，随时可改名、隐藏或删除，点击能回到来源。

记号在适当的对象边缘出现，而非每页都提醒“我记得你”。例如返回那道题时纸角仍保留“先把常数放一边”的共同称呼；若用户已否定它，关联 cue 与主动提议一起失效。

##### D03.4 技术落点与并发规则

围绕 `MemoryService / ContextCompiler / memory-inquiry / Harness` 核对原话读取、双时态、root_event_id、九种演化动作与条件闭包。整理水位必须连续：已处理 1、2、4 不能声称处理到 4；第 3 条原话继续作为覆盖层进入当前上下文。

新纠正在同一回合先阻断受影响推论；背景调查返回时复核原来源版本、privacyEpoch 与 personaRelation。未受影响的独立事项继续，不因一个更正清空整个会话。

##### D03.5 动态与资产

本阶段重点是纸页、来源连接、收笔与重新关注，优先用代码做精确文本与差异显示。GPT Image 可打样纸面材质与记号语言；Gemini 只验证角色“停住—重新看—安静承接”的微动作。不能把原话截图烘焙成视频，也不为每一条记忆生一张图。

低动态模式直接替换有效理解并显示来源；读屏能知道哪条被纠正。视觉上不使用刺眼红叉惩罚旧理解，仍明确区分当前与历史，不能用温柔配色模糊事实。

##### D03.6 遗忘的实际体验

用户删除一段关系记号时，相应纸角、待播声音、后台提案和衍生引用都停止使用。当前设备即时阻断；离线设备不能被承诺远程瞬间擦除，重连先同步屏障。可以清楚告知处理范围，不能把技术长篇声明塞进日常对话。

##### D03.7 结项证据

验证“长期偏好—一次例外—例外解除—明确纠正—遗忘—迟到调查—旧备份恢复”连续链。既测该改变帮助方式的记忆，也测不该影响当前任务的无关记忆。用户应该感到她在这一次回应中变得更准确，而非只多出一张记忆卡片。

##### D03.8 纠正要到达动作，也要保留没有发生的部分

当前明确纠正进入本轮有效上下文，与后台长期整理分别标状态；持久化失败时仍应在当前回合尊重新意思，同时给可恢复入口，不能假报已经永久记住。“忘掉判断，原话保留”只撤相应推论与再提取路径，不删独立日程，也不因此撤销用户单独保存的角色约定。

**一个精修镜头**：展开旧理由时，原句先稳定显示，解释连接线随后轻现；纠正到来时连接线立即断开，旧原句仍按用户保留选择留在历史页。角色短促收笔后关注新句，没有红叉、抹除用户文字或循环懊恼。低动态以静态“当时/现在”的关系完成同一理解。

检验遗忘时同时核检索、回复草稿、来源预览、通知缩略图、待播 TTS 与设备恢复，而非只查数据库里一行是否删掉。没有前端回执保持 unknown，不据此推断用户没看过并再次递送。

2. **温情无亏欠感归来（Living Workspace Return）**：隔天重开或跨应用归来时，书桌光标、草稿推演折痕与情感共鸣点自然保持，像伴侣默默替你按住翻开的书页轻声说“你回来了，刚才写到这儿了呢”，彻底告别生硬弹窗与进度丢失。

#### 2. 主代理与子代理在本阶段最易犯的致命错误（防坑预警）

- **致命错误 A（把「模型吐出了字」当成「用户已经看懂或接受了」）**：必须严格区分 `generated → rendered → seen → understood → accepted → executed` 六重状态；用户中途点停止，未曝光的后半截绝不能算成「我们聊过」。
- **致命错误 B（共写故事只存最新摘要，丢掉第一幕原稿和校园取景）**：共创故事必须保留逐幕原稿版本与校园真实取景锚点（且严禁把虚构故事污染成用户真实生平）。
- **致命错误 C（重开应用时像催债弹窗）**：「回来仍在原处」必须轻盈温柔，用户想接着做就一键接上，想聊别的就自然转身。

#### D04. 本阶段完整导演设计：同一件东西，真的一起做过

这一阶段把“共同经历”从聊天里的一句话变成可继续操作的作品。用户把一段旧推导递过来，她摊开原稿，与今天的理解放在一起；用户只接受其中两处改动，剩下的先留着；隔天回来，打开的仍是这份有版本的作品。

##### D04.1 一个对象的六种关系

生成、上屏、看见、看懂、采纳、办成分别有证据，不能由一个“完成”动画吞并。草稿属于提议，用户亲手改过的段落属于共同版本；作品保存不证明用户认同所有观点。旧版、当前版、试写版可以并存，各自有稳定身份。

界面采用可摊开的主纸与少量边纸，保持当前工作中心。历史入口在页边或书签处，需要时展开；不把版本树常驻成项目管理面板。角色看用户正在比较的那两处，而非随机读另一个版本。

##### D04.2 递、接、摊、改、收的连续动作

| 拍 | 用户动作 | 角色与纸面表现 | 后端变化 |
| --- | --- | --- | --- |
| 递来 | 从旧对话/资料拖来真实引用 | 纸页跟手，接收区轻微让出空间 | 传稳定 ID 与 sourceAnchor，不复制孤儿文本 |
| 摊开 | 打开旧稿 | 两页共享对齐标尺，当前段落保持可见 | 读取指定历史 revision，不偷换最新版 |
| 对照 | 指出旧解法与新想法 | 可证对应才画细线；不成立则诚实并排 | 保存映射依据或明确未确定 |
| 改两处 | 局部采纳/编辑 | 被接受的变化落在主纸，其余留为建议 | 子修改独立提交，保留作者与来源 |
| 暂放 | 用户离开或切页 | 纸页收回稳定入口，角色放下笔 | 保存工作位置，非自动接受其余建议 |
| 回来 | 重新打开 | 先恢复版本/段落/笔迹，再轻微抬眼 | 重新核验对象与权限，过期引用提示修复 |

##### D04.3 共同操作组的前后端设计

将同一请求生成的笔记、陪学纸、日程候选组织成关联视图；各子对象仍由 Notes/Study/Agenda 的原 Owner 管理。组保存“为什么有关”，不成为新事实库。用户说“只留下这一段”时，其他对象保持未采纳。

版本冲突不能静默覆盖：用户已经修改的段落留在主纸，助手新建议在边纸显示差异。允许恢复旧版为新的当前版本，历史并不消失；外部执行结果不能被作品撤销功能伪装逆转。

##### D04.4 “过去的我与现在的我”如何有形状

可以设计一条细而克制的变化路径：旧草图的一个圈，连接今天推导里真正对应的条件。连接来自真实数学或语义映射，模型不确定时先列候选，用户可以改；不能为了励志叙事把任何旧错误都画成成长阶梯。

原稿里被用户保留的一句笨拙表达值得保留，不为“高级”全部润色成助手口吻。共同作品的温度来自保留用户的笔迹、犹豫与选择，而不是增加纪念动画数量。

##### D04.5 制作与实现落点

继续复用 `source-bookmark.ts / scene-transfer.ts` 的真实地址、既有 Work/Episode 与互动程序版本。代码负责纸页布局、差异、选区与回流；角色只做受控的看向、收笔和让位。Gemini 样片验证“用户正在改时不伸手抢纸”，GPT Image 验证纸与人物的桌面关系。

跨页面的物件飞行只在起终点都可定位且用户未打断时发生；否则用稳定来源标记直接呈现。屏幕缩放后不沿旧像素轨迹飞到空处。

##### D04.6 结项证据

完成“旧稿进来—真实对应—局部接受—新版本—隔天恢复”的连续故事，另测缺失来源、版本冲突、隐私撤回与换人格。键盘用户可完成同样操作；低动态模式保留对象关系与版本理解。共同经历必须改变后续接续能力，不能只在记忆里多一条“我们一起做过”。

##### D04.7 原章、原笔迹与部分采用都能回得去

共同故事继续沿 `CuriosityInvitationService` 的原事项/选项，以及 `read_shared_creation` 的 message/scene/revision 回读。普通消息 text 为空时先检查历史作品入口，不能把一整幕 Scene 当成不存在。原章、当前种子和新分支分别有版本；换个取景地应真正影响下一幕，现实到过哪里仍另有事实。

共同作品的“看过”记录若需要，按有证据的实际段落/播放范围保存。用户跳到结尾，不等于读过开头；最大游标不等于连续覆盖。保存作品也不等于采纳全部解释，删除提示记录更不能把曾受提示的尝试重标为独立掌握。

**一个精修镜头**：对比旧稿与今天稿时保持同一基线，用户接受两处，只有那两段落回主纸；未接受部分停在边纸。移动的是有身份的视图，正文一开始就可复制与读取；不能等纸飞完才让文字可用。

#### D05. 本阶段完整导演设计：她有自己的心意，也知道何时放下

主动性要完成一个完整动作：有来由地想到你，在授权范围内准备好，以合适的方式递出，得到回应后继续，没有回应也能自然结束。只做后台定时器和弹窗，既没有心意，也没有分寸。

##### D05.1 一盏灯、一张纸、一个可自由拒绝的入口

场景中的灯负责氛围与可选专注约定，不能把用户绑进计时考核。待分享的小礼物留在桌边，当前工作仍占中心；没有新内容时桌边空着也很好。用户把礼物拿过来才展开，划走则收回，角色不追问“为什么不理我”。

视觉上区分“准备好了但尚未打扰”与“用户正在查看”，不是多加两个状态徽章，而是位置、展开程度与注意方向不同。手停在纸边的姿态必须可长期静止，不能通过每十秒动一次诱导点击。

##### D05.2 主动机会的五拍

| 拍 | 心智与宿主 | 前端导演 | 结束条件 |
| --- | --- | --- | --- |
| 想到 | 当前托付/共同经历/新变化形成机会 | 不必上屏，保持原场景 | 无依据、已拒同因或过期则 none |
| 准备 | prepare 读取获授权资料、形成草稿 | 桌边对象可以就绪，但不播放提醒 | 用户撤回托付则作废 |
| 递出 | 当前时机适合且需要注意 | 纸轻转向用户、目光短暂确认，一次可选轻声 | 用户输入立刻让位 |
| 接住 | 用户打开、询问或部分接受 | 展开对应内容，保持来源与返回入口 | 子操作逐项执行，不总包授权 |
| 放下 | 用户忽略、拒绝或内容过期 | 收回到非侵入位置或消失，声音清空 | 不换说法再次撞门 |

固定时刻提醒走独立可靠路径：用户明确说九点提醒，不能因“安静策略”漏掉。低价值主动分享与承诺过的提醒是不同责任。

##### D05.3 一天有两种过法

“今晚想学完这一节”与“今晚想先恢复一点状态”都可以被认真对待。她把两种安排铺成可比较的候选，保留 setup/work/cleanup/travel/rest 与未知时间；用户可以混取其中几段，不必二选一整套接受。

候选变化是试放；已授权本地修改直接执行并给清楚回执，不反复确认。冲突或外部副作用按既有权限处理。主动性不能成为自动调整用户日历的借口，也不能因为用户拒绝安排就退出亲密互动。

##### D05.4 个性与好奇心的原创延拓

从真实共同经历生发小作品：灯可以把用户起过名字的一块小石头画成短故事的道具；若麦可以把用户敲出的三下节奏变成一个可改的小节；海铃可以把用户反复卡住的两条安排并排放好。它们是具体回应，不是随机“今日惊喜”。

礼物允许粗糙、有趣、可共同修改，不必每次都是完整报告。用户接过后，系统记录实际动作；不接也不写“用户不喜欢角色”。对亲密称呼、调侃强度和主动频率的明确约定独立保存，避免单次互动污染长期人格。

##### D05.5 后端与前端落点

在 `OpportunityScheduler / AttentionService / ReminderService` 与 ConversationRhythm 之间建立真实机会生命周期，继续共用 Hermes 主循环。noveltyKey、条件变化、quiet hours、cooldown 与显式提醒分别有用途；不把“无键盘输入”当唯一主动条件。

前端回流 opened/dismissed/accepted-part/withdrawn 等明确动作；显示在屏上不能自动记 seen，更不能记 understood。页面隐藏后不积压演出，回来只呈现仍有效且确有变化的内容。

##### D05.6 动态资产与静默验收

GPT Image 打样桌边礼物、灯与正文的关系；Gemini 重点探索“刚准备递出—看到用户在写—停在桌边”，结尾需能静止。代码负责输入/IME 接管、纸页状态与音频停止，不用一段不可中断的视频决定什么时候提醒。

验收包含用户正写长句、开启免打扰、同一原因已拒、固定提醒到时、礼物过期、换设备与不回应。完成的标志包括“该安静时真的安静”；不以主动开口次数越多越好。

##### D05.7 她主动带来新的可能，通知仍回到原处

共同经验可以激发主动分享，陌生兴趣也应有入口。用户说“今天玩点没玩过的”，她可以创造一个新东西；不能因长期profile没有这个标签而拒绝探索。纯粹聊天、玩乐和没有产出的下午本身成立，不把所有小礼物绑定学业进度或待办奖励。

准备对象 → 同一对话里的消息 → 系统通知预览保留投影关系、版本和受众范围。点击通知回原物件/消息，不重复生成一张卡；系统接受通知不等于用户已读。角色署名、称呼和待播音频同时核当前配置，锁屏不展示私密原文。用户已经在产品里接住时，不再由另一个设备重复打扰。

**一个精修镜头**：礼物转向用户只走一次小幅动作，末端留在可长期静止的桌边。此后没有周期弹跳。用户输入时先把手放回，礼物还可取；明确划走则取消这次递送。测试“今天安静，八点提醒照旧”，可选主动性收束而固定提醒继续。

#### D06. 本阶段完整导演设计：十个人生活在可信的同一个世界里

本阶段把前五阶段已验证的样片扩成完整视觉与动态语言。目标不只是十张脸、九个页面和四种滤镜，而是不同角色在共同空间里用各自的方式关注、退让、递出、玩耍和接续。

##### D06.1 三张矩阵与一张过渡图

身份护照固定人物与服装辨识；场景矩阵固定相机、家具、文字安全区和光；姿态矩阵固定身体支撑与手物接触。activity 与页面 category 显式映射。每条允许的姿态过渡另有条件、可打断区间、收束和替代。

十角色 × 九活动 × 四主题每格都有明确状态，但不强制生产无意义全排列。approved、shared-compatible、static-fallback、not-applicable、missing 分开记录；静态替代不能算动态完成。用户自定义角色缺少素材时仍保持可读与可用，不被内置角色覆盖。

##### D06.2 四主题不是滤镜

| 主题 | 空间与光 | 内容与角色 | 过渡设计 |
| --- | --- | --- | --- |
| 暖杏 | 午后侧光、奶油纸面与木桌 | 正文清楚，皮肤与衣服不被橙色淹没 | 从当前场景整体调整，不闪白 |
| 晨雾蓝 | 轻雾冷空气、较清的窗光 | 保留暖中性色文字层，角色肤色稳定 | 光与人物一起匹配，不只换背景 |
| 暮色紫 | 晚霞与室内暖光相遇 | 阴影层次可辨，不用高饱和紫覆盖正文 | 先稳定布局，颜色/环境短过渡 |
| 夜雨暖金 | 窗外深蓝、室内灯与植物暗影 | 阅读区域亮度独立，角色不成为发光贴纸 | 雨与光可以暂停，静态仍完整 |

保留自然植物与睦的固有颜色，不把禁用绿色 UI 误伤原作形象。主题是用户偏好与实际时间的可选关系，不强制用设备时钟不断改变正在看的画面。

##### D06.3 页面间的空间连续性

首页、学习、PDF、日程、笔记、地图、角色、主题、恢复共享稳定入口与布局标尺。进入 PDF 时正文先取得阅读空间，角色移到已登记伴读位；回首页时从合法位置恢复，不跨家具漂移。窄屏优先内容和输入，角色可以半身、静态或暂隐，不能挤成一条难读的正文。

面板展开从真实来源位置生长，返回走可理解的路径；用户快速切页只保留最终目标。导航、输入框、分屏手柄与焦点不能因角色表演改变命中区。

##### D06.4 生产流水线与返工边界

| 步骤 | 必须交付 | 通过条件 |
| --- | --- | --- |
| 身份校准 | 十角色护照、合格参考与版本 | 面部/服装/头身比例并排一致 |
| 空间与母版 | 同景画布、家具锚点、文字安全区 | 支撑、透视、尺度、光向成立 |
| 动态关键姿态 | neutral/attend/yield/offer/settle 等所需姿态 | 有可信接触与合法过渡，不切出双头 |
| Gemini 导演参考 | 一条主动作的节拍与完整样片 | 首中尾连续，能停留，参考用途明确 |
| 代码重建 | 通道 owner、目标映射、中断与降级 | 可改变目标，输入不等待视频 |
| 扩矩阵 | 每格状态与复用依据 | 缺口可定位，不用文件数量代替覆盖 |

同类结构性错误两轮后回到构图或实现路径决策；不要继续给坏母版加参考。图片和视频的候选隔离保存，只有通过登记的资产进入 runtime glob。现有 scene schema 兼容迁移，不建立第二张事实表。

##### D06.5 让性格进入运动，而非统一动画换皮

同样是“用户打断”：祥子可先收整纸再移目；睦直接停住并看向新目标；爱音收住较外放的手势；立希立即把工作区让出来。差异主要在幅度、先后、停留与手势，不能表现为有人反应故意迟钝或不尊重用户。

十角色均需完成 look/yield/offer/withdraw/resume 的可用样例；play 与复杂道具按真实场景扩展。表情可以丰富，不能总笑、总眨眼或以脸红代替所有情感。

##### D06.6 运行时预算与可访问性

每演员独立实例与状态，同一通道单写者；角色、环境、纸页、音频有统一注意预算。屏外暂停，隐藏不解码，资源失败静态降级。动效等级分为完整、轻量、低动态；业务功能、标签、焦点与键盘操作三者等价。

在目标设备实测解码内存、帧时间和输入响应。优先减少同时活动的层，而非靠加载遮罩隐藏卡顿。复杂 rig 先选择一种最小足够方案，不一次引入 Rive、Live2D、Spine 三套生态。

##### D06.7 结项证据

十角色身份并排、四主题同景对照、九类页面实际视口、姿态过渡与打断录像、低动态/窄屏/缺资产路径。画面审核与运行机制证据分开；不能仅凭联系表声称视频连续，也不能用一张漂亮首页代表全站完成。

##### D06.8 资产一致性必须可检查、可迁移

每个合格组合记录母版尺寸、同画布分层、裁切偏移、相机/光向、坐骨/足/肘/握持点、前后遮挡、道具归属与允许过渡。长发、裙摆、鞋、桌面前缘分别看边缘，不能以“有alpha”代替可用。旧 `scene.json` 保留迁移与回退，失败资产不进入生产 glob；头像合格不代表全身姿态合格。

**一个精修镜头**：同样递出便签，先看目标，手与纸作为一组移动，到桌边后纸先停稳、手再释放。交接瞬间保留世界坐标，改变的是道具驱动者；不能先换 owner 再跳到另一个局部原点。无手部rig时让纸沿桌面移动、角色只看向它，同样可做到可信。

四主题采用同机位光照族，人物/家具/阴影共同切换；主题预览可取消，取消回真实先前版本。每个演员独立实例，快速切角色不会共享眨眼计时器、嘴形、手中物件或上一个人的在途 cue。

3. **3D Spring Camera 零延迟手势接管**：相机以自然弹性跟随运动光点，手指/鼠标触碰瞬间毫秒级接管，松手后三秒平滑恢复追焦。

#### 2. 主代理与子代理在本阶段最易犯的致命错误（防坑预警）

- **致命错误 A（镜头动画抢走用户正在手拖的地图）**：必须严格实现 `CameraOwnership` 状态机（`programmatic_fly` vs `user_gesture` vs `follow_runner`），手指/鼠标一碰立即零延迟接管镜头！
- **致命错误 B（运动陪伴只有冷冰冰的配速表，没有「她陪在身边跑」的心跳互动）**：必须把实时轨迹、所在跑道/湖畔场景与祥子/睦的随行气泡/关怀无缝融合在同一个地图表面上。


#### 2.5 【充分 Design 视觉载体与防飞机方向盘专项】

#### D07. 本阶段完整导演设计：地图像她陪你一起看的地方

地图的生命力来自共同关注、方向与选择。用户说“去这里”，她把路线放到同一张地图上；用户拖去看桥另一边，相机立即交给用户；途中提到一段共同经历，它贴在真实地点上；返回聊天时路线仍是刚才那条。

##### D07.1 三种相机意图

| 相机意图 | 何时成立 | 运动方式 | 退出与恢复 |
| --- | --- | --- | --- |
| 介绍目标 | 用户选中地点/路线，目标可定位 | 先建立当前位置与目的地方向，再适量移动/缩放 | 手势开始即终止自动运镜 |
| 跟随运动 | 用户明确选择跟随，样本有效 | 平滑位置与适当前瞻，避免频繁旋转 | 用户拖动后保持手动，不倒计时抢回 |
| 回看经历 | 用户打开某次路线/记号 | 从真实历史范围展开，不与实时点混淆 | 返回原相机与选中对象 |

相机要有明确 owner 与目标版本。GPS 点在更新并不等于镜头必须一直动；定位不稳时保持最后可靠视角，显示不确定范围而非抖动追逐。

##### D07.2 地图的层次与视觉

校园底图保留手绘/微缩地标气质，真实路网与路径几何仍决定路线。暖金轨迹的辉光不盖住道路、文字与路口；已走、候选、未知区段除颜色外还以线型和说明区分。用户放大时信息逐层出现，不能一次铺满所有地标和统计。

角色的视线关注选中地点或路线纸，不能遮住用户要点的地图边缘。地标记号来自真实关联的作品/原话，数量稀疏，打开后能回来源；不把所有私人记忆公开标在地图上。

##### D07.3 一次连续空间叙事

| 拍 | 事件 | 运镜与动作 | 保留的信息 |
| --- | --- | --- | --- |
| 聊起 | 对话里形成地点引用 | 内联地图就地展开，角色看向它 | 地点 ID 与来源句 |
| 看清 | 用户展开大地图 | 同一相机/选择延续，路线逐段显现 | routeId、几何版本、当前视角 |
| 改看 | 用户拖到另一条路 | 自动镜头让位，角色不继续指旧目标 | 手动相机与候选对照 |
| 决定 | 用户采用路线或只收藏地点 | 采用的线稳定，未选的退淡 | 选择与执行状态分开 |
| 回去 | 收起地图回对话/日程 | 地图收回来源位置，核心状态不重建 | 仍能从同一对象继续 |

##### D07.4 后端契约与坐标纪律

使用现有 CampusMap、mapService、map-routing、map-workout 与 shared workout 契约。地理坐标、地图投影、屏幕坐标分别命名；CRS 在边界转换，不让 UI 修正污染原始样本。路线裁剪遵循有向几何和拓扑，不能用直线穿楼。

地图点击只产生指向或选择，不能自动发起学校写入。日程关联路线时传稳定引用与真实估计条件，未知通勤时间保留未知。公共 `apps/review-web` 只共享公开地图与表现代码，私人轨迹、账号状态与记忆图层不进入构建产物。

##### D07.5 Gemini 与代码的分工

用 Gemini 网页版探索“从桌面路线纸进入地图”的方向和节拍，避免复杂运镜淹没导航。镜头参考不能改变真实路网，生成的地标建筑不作为导航依据。实际相机、路径高亮、选中状态、返回位置全部由代码实现。

角色指路需要登记的手势与安全区；缺少相应姿态时以视线与地图标记完成，不把半身图伸缩成全身导游。低动态模式直接切换到合适范围，仍保留位置关系和返回入口。

##### D07.6 结项证据

完成“聊天选点—展开—手动打断—改路线—回聊天—再展开”的连续操作；加定位跳变、路线更新、快速连点、窄屏与公共构建检查。验收不是相机动画越长越好，而是用户始终知道在哪、看哪、如何接管。

##### D07.7 地点相同，不代表是同一次停靠

A→B→A 保留三个停靠实例与两条有向路段；返回A不能因placeId相同被去重。用户指“第二个”，按当时列表版本与选项ID解析；排序改变后不指向另一栋楼。手动起点、设备定位、个人“家”的对应和公共地点各保来源，不能把保存的家当作实时所在地。

**一个精修镜头**：展开路线时先保留起点与终点的相对方向，在当前视口里安排恰当留白，再完成短幅平移/缩放。用户触碰立即从当前相机接管，自动动画不把相机拉回旧起点；收回到消息旁时沿同一相机状态缩小，原路线依旧可继续询问。

跨设备接力同步 route/journey 与有效版本，不强制同步每一帧相机；用户在桌面看桥时，手机不应突然跟着旋转。历史地图图层保历史日期，重新采用才查现在条件。

#### D08. 本阶段完整导演设计：借两种今晚，写同一张纸

日程、陪学与故事在这一阶段成为可以一起摆弄的对象。用户不必先学会一套工作流：把今晚两种过法摊开，拿起一段安排试放；左边保留原题，右边写自己的第一步；故事排练时可以试一句话，再把不合适的那句收回来。

##### D08.1 日程沙盘的触感与真实边界

两种候选共享时间标尺，差异集中在具体任务、转场和留白，不复制两张信息密集的完整日历。拖动时卡片跟手，保护占用与冲突在位置上可理解；松手只形成预览，是否提交按已有授权与冲突情况决定。

接受一段不会接受整晚。未知结束时间不被画成无占用，窗口外不自动视为空闲。用户撤回已提交本地变更走真实 Undo/新版本；外部结果未知先核查，不靠回弹动画宣称已撤销。

##### D08.2 双纸陪学：左边可信，右边自由

原题与来源保持稳定，用户笔迹与助手提示分层。用户正在落笔时，角色的手、声音与自动批注退让；识别结果在笔迹完成后作为可改的解释，不边写边改字。助手可以在边纸示范一步，不能擦掉用户的尝试。

用户说“这里为什么能换元”，共同注意定位到实际式子。解释先围绕那一步展开；用户只要一个提示，就不自动铺满完整解答。合并式子、变形与数学映射必须成立，动效不能把错误推导变得像真的。

##### D08.3 三类操作的一致语法

| 共同语法 | 日程 | 陪学 | 故事/关系排练 |
| --- | --- | --- | --- |
| 递来 | 一段候选安排 | 一段原题/旧尝试 | 一句草稿/一个场景 |
| 试放 | 时间轴幽灵块 | 边纸上的一步 | 可撤回的分支台词 |
| 接管 | 用户拖动与输入时间 | 用户落笔与改公式 | 用户改说法/换立场 |
| 接受 | 原 Owner 校验并提交 | 保存选定版本，不记掌握 | 采纳某句，不冒充现实已说 |
| 收回 | 回到真实旧状态或说明冲突 | 保留原尝试与历史 | 分支收起，主稿不被覆盖 |

##### D08.4 角色表演与共同节奏

她能在用户写完一个式子后看向那一行，而不是每落一笔都点头。试放日程时视线跟随当前卡片；冲突出现时把另一个选择递到手边，不用红色警报压迫。排练室里角色只扮演当前明确设定的情境，不能把模拟对话自动发给现实对象。

故事共创可以让双方各添一个小细节，角色的回应沿真实上一幕变化；每幕保留版本，用户随时回改。温柔也可以包含兴奋、幽默和认真争论，不总把故事写成抚慰。

##### D08.5 系统与制作

围绕 NativeAgendaService、CalendarService、StudyCompanionService、Work 与来源书签实现，复用 Stage 04 的局部采纳和 Stage 05 的机会收束。笔迹原始数据、识别文本与助手推论分别保存，模型只读取用户允许的当前上下文。

GPT Image 打样纸面层级与角色让位；Gemini 导演样片重点验证“准备指点—用户落笔—手停住—写完再关注”。真实公式、日期、笔迹和冲突状态由代码绘制，不能烘焙进视频。iPad Pencil 的完整实现留 Stage 11，但本阶段定义数据契约并用当前输入方式验证。

##### D08.6 细节与低动态

分屏手柄可键盘操作；窄屏在两页间切换仍保留选区；大字体不会挤坏时间轴。拖拽路径之外提供明确的移动/采用入口。低动态用稳定预览和状态差异表达试放，不损失理解。

用户切去地图查通勤再回来，当前沙盘与草稿保持；角色不重新解释已讲过的内容。新冲突只标在受影响时段，避免整晚重排造成控制感。

##### D08.7 结项证据

完成“试两种今晚—只采纳一段—打开原题—写第一步—纠正指向—出去查路线—原处回来”，另测版本冲突、手写识别误差、无来源题目与取消排练。真实修改、未采纳建议和纯模拟内容必须一眼可区分。

##### D08.8 纸上每一处都要有准确的地址

原文按Owner的Unicode码点/版本定位，DOM的UTF-16选择范围显式换算；同一句出现两遍不能用首次 `indexOf` 定位。Pencil/鼠标笔迹使用稳定stroke/object ID，识别是可修正的派生，不改原笔迹。手写中切页先保存已有真实段，不补出用户还没写的结尾。

局部采用按操作组中的子修改处理：留一条辅助线、不留解释是合法选择；撤销助手组不能删掉用户随后接上的线。更新顶点或题源后，旧提案先失效，能重算才重算；不能把过期坐标下的漂亮描线硬压到新题。

**一个精修镜头**：用户笔尖落下时，角色的指向先退出边纸，布局不跟着每一笔抖动；笔停稳且用户明确继续后，她看向刚完成的式子。日程拖动同样先跟手、后落定；可以直接执行的已授权调整不额外弹确认。

#### D09. 本阶段完整导演设计：她把一个想法做成你能碰的东西

OpenUI 的目标是让模型能基于真实问题造出可操纵、可继续修改的作品。用户改变弦长，声音与波形一起变化；用户拖住滑块，自动演示交出控制；下一轮说“把刚才那个变成双摆”，已有状态与来源继续可用。不能把“生成了一块 React 区域”当成万物原理已打通。

##### D09.1 通用原语与作品结构

| 层 | 原语/职责 | 设计要求 |
| --- | --- | --- |
| 内容 | 文本、公式、图像、SourceSlot | 来源可查，解释围绕当前操作 |
| 几何 | 点、线、曲线、形状、约束、坐标 | 单位与参数明确，不能只画看似正确的图 |
| 交互 | Press、DragHandle、选择、连续输入 | 立即反馈，可取消，键盘等价 |
| 时间 | Motion、时间轴、暂停、逐步、重置 | 时间源唯一，用户接管不继续后台偷跑 |
| 声音 | Voice、AudioTrace、音源与包络 | 用户授权解锁，状态与实际声音一致 |
| 状态 | NativeProgramLocalState、previous + patch | 版本化、可续改，不重复清空用户状态 |

这是通用能力分解，不要求把每个名词都新增为组件。先核对现有 interactive-library 与运行时，再补缺失机制；禁止为了某一道钢琴题写一个硬编码分支后声称通用。

##### D09.2 从生成到共同把玩的五拍

| 拍 | 后端状态 | 前端与角色动作 | 用户主权 |
| --- | --- | --- | --- |
| 构作 | 模型依据当前问题提出结构 | 作品骨架在稳定区域逐步出现 | 可继续输入，不被生成动画锁住 |
| 可用 | 最小闭合程序通过校验 | 可操作部分明确可用，未就绪部分不假响应 | 不等待整件作品美化完才交互 |
| 试一试 | 用户改变一个参数 | 图、数值、声音同步，角色关注被改变之处 | 手势接管自动播放 |
| 继续改 | 用户提出增量需求 | 保留已有状态，局部 patch 更新 | 用户输入不被旧结果覆盖 |
| 留下 | 用户保存或移到别处 | 同一作品缩回来源入口 | 是否采纳解释与是否保存作品分开 |

##### D09.3 科学与表达要分别成立

每个物理/数学作品写清模型假设、参数单位、适用范围与实际计算。可以用简化模型解释原理，但不能把生成视频当成受力证据或数值求解器。复杂场景先用可验证的低维模型建立关系，再决定是否加视觉参考。

解释随当前状态更新，用户把参数调到边界时明确显示模型不适用或约束，不能静默夹值后还声称参数已采用。图像美术和角色动作不覆盖坐标轴、单位与关键变化。

##### D09.4 Gemini 网页版动态参考的接入方式

生产阶段可以生成机构、光影或运动节拍参考；产品运行时只播放经过审核且适用的资产。网页生成不是默认嵌进产品的后台 API，更不是模型每回合自行消费的无限视频工具。

如确需产品内生成能力，必须另行设计真实服务、权限、预算与生命周期，本路线图不把它视为已经存在。当前优先路径是：参考片帮助理解运动 → Codex 以可控参数与状态重建 → 对照模型验证。

##### D09.5 状态与安全不破坏创造力

宿主验证程序结构、允许能力、来源与版本，执行确定性边界；模型自主决定如何解释和创作，不按关键词选预制题材。用户提供的素材不作为可执行指令；作品的输入输出都走受控接口。

程序局部状态保存使用 expectedRevision；迟到 patch 不能重置用户刚拖的参数。图像/音频资源消失时保留可用的文本、计算与操作，降级可解释。程序崩溃不应拖垮聊天、笔记或原题。

##### D09.6 结项证据

用不同结构的实际问题验证通用性：弦/波、机构/约束、数学变形/可视化。每件都走“生成—用户接管—增量改造—保存—恢复”，至少一件在参数边界或缺资源时诚实降级。代码校验、模型真实使用、实际互动分别提供证据；不靠题材名称数目证明完成。

---

##### D09.7 流式生长不能暴露半个可执行程序

逐步生成可以展示轮廓与已核文本，但只有通过原程序校验、来源核验和状态初始化的闭合子单元才能可交互。尚未校验的DSL不在renderer抢先执行。原作品仍可操作时，新稿在版本边界接续；用户刚改的值与迟到patch冲突，就保留当前值并协调，不偷偷恢复初始值。

**一个精修镜头**：解释一条弦的振动时，静态弦线和单位先清楚出现，用户按下再引入波；拨动位置、波形与声音由同一参数模型驱动。角色先看用户改变的参数，再看结果，不能用独立循环动画假装懂了变化。无音频时图与数值仍成立。

接受一件互动作品，须同时能回答“它怎么算、现在值是什么、用户怎样接管、下一轮怎样接着改”。Gemini参考说明节奏与可见关系；数值、物理和业务结论由可检查的模型/来源支撑。

#### D10. 本阶段完整导演设计：琴能弹，东西能留，心意能接住

钢琴是整套造物能力的高要求样片；来信和小礼物则验证同一系统是否有分寸。它们必须同时具备感官质量、真实机制和可继续的关系。会响的琴键只是起点；一封自动弹出的长信也不等于亲密。

##### D10.1 三角钢琴的三层观看

第一层是一架有可信比例、键面、木质、金属与阴影的琴；第二层是可以被用户展开查看的击弦/制音等机构；第三层是弦、波形与参数解释。三层围绕同一被按下的键，不把机构图、琴声和公式做成互不相干的三个面板。

按键的深度与回弹可感，触摸/鼠标/键盘映射清楚；没有压力数据的设备不伪造力度感知，可用明确的力度控制。多指和弦、延音踏板、松键与切页的声学生命周期需要正确，不让音符在后台悬挂。

##### D10.2 演奏与理解的时间轴

| 拍 | 用户动作 | 可见/可听反馈 | 状态要求 |
| --- | --- | --- | --- |
| 触键 | 按下一个键 | 键跟手下沉，声音按真实触发产生 | 输入与音符 ID 对应 |
| 看里面 | 展开机构 | 对应部件与同一键同步，可慢放演示 | 慢放教学与实际演奏时间明确区分 |
| 改参数 | 调弦长/张力/线密度等 | 适用模型中的音高/波形同步变化 | 单位、假设、范围可查 |
| 接管 | 手动拖动正在演示的部件 | 演示停止或转为手动，播放标记同步 | 只有一个时间/输入 owner |
| 同乐 | 用户弹一个短节奏 | 角色回应具体节奏，可形成可改的小节 | 不把偶然输入记成长期音乐偏好 |
| 离开 | 收起/切页 | 音符按明确策略释放，作品状态保存 | 重开不擅自大声播放 |

##### D10.3 角色如何参与而不挡琴

角色处在琴边可用的真实姿态：看键盘、听一个小节、在用户停下后回应。手部弹奏若没有可靠接触 rig，就不要让人物手指在错误键位上乱动；可使用可信的聆听姿态与用户控制的琴键。姿态与乐器是专门的场景家族，不能把普通桌边人物拼到钢琴前。

十角色不都说“弹得真棒”：可以指出用户刚重复的节奏、接一个音、提出愿不愿意一起改。这些回应依据实际演奏事件，用户沉默时允许只听。音频与表情同步不意味着每个音都触发一次头部动作。

##### D10.4 来信与礼物的阅读导演

来信有真实来由：一件共同作品、一个用户愿意继续的话题、一段被真实保留的经历。信封放在桌边，点开才展开；正文作为可选择、可朗读的文本呈现，不烘焙成图片。用户读到一半切页，回来仍在原段；删掉相关记忆后，未读信和待播声音也必须失效。

信的长短随内容，不固定“长篇才有诚意”。可以让用户回复一句、摘一段、放回去，或什么都不做。小礼物可以是一段可改的旋律、一个互动小星图或共同故事的下一幕，但不能为了收集“已读”强迫打开。

##### D10.5 全状态共同设计

空态给一个可开始的对象；加载态保留已能操作的部分；失败态保留用户输入并说明可继续方式；取消态自然收束；部分成功分别陈列；来源失效停止引用；资源缺失保留功能；完成态不过度庆祝；回访态只强调真实变化。

这些状态属于每件作品的设计，不是最后统一套一组 Toast。完成一件本地作品可以轻轻落纸，学校回执与外部消息的成功则必须依据各自事实，不能共用一个随便触发的“成功动画”。

##### D10.6 制作与验收

GPT Image 负责高质量琴体、场景与分层参考，Gemini 网页版帮助设计机构演示节拍与角色聆听；真实按键、声学、波形、接管与保存由代码完成。复杂机构的视频仍需可信机械依据，漂亮运动不证明结构正确。

验收覆盖单键、和弦、踏板、快速重复、手动接管、资源失败、静音、隐藏恢复与低动态；来信覆盖半读、回复、撤回来源和不同人格接手。目标是完整可信的作品，不以一个主观“100 分”标签代替这些可操作条件。

---

##### D10.7 教学、演奏与聆听是三种真实时间

按键声由实际音频时钟调度，UI帧只是可视投影；掉一帧不能把音符或松键漏掉。慢放机构明确进入教学时钟，不把所有音乐声音同比拉长而冒充真实钢琴。暂停、来电、耳机断开、切页与角色语音到来都先处理已有音符和音频焦点，恢复由用户选择。

**一个精修镜头**：用户弹一个三音动机，角色听到真正播放的结尾后作一次短回应，旁边出现可改的小节。延音仍在响时不抢着插话；未播放成功不说“刚才那个尾音”。没有可靠弹奏手部资产时保持聆听姿态，按键和机构依然由用户操作。

半读来信保存真实阅读位置与可确认范围，半播语音保存实际播放进度，不推断读懂。回复一句可以成为下一段共写，不被迫收成长期承诺；当天不看也没有“未处理关心”红点债。

#### D11. 本阶段完整导演设计：离开桌边，她仍知道那一页在哪里

严格保留先 iOS/iPad、充分打磨后再 Android 的用户顺序。统一的是共同对象、相处方式、审美与主权；每种设备的输入、显示与后台能力不同，必须认真适配。手机不是缩小的桌面，iPad 也不是放大的手机。

##### D11.1 三端各自擅长的相处

| 端 | 主要场景 | 视觉与动作 | 同步与本地边界 |
| --- | --- | --- | --- |
| 桌面 | 摊开资料、作品与日程 | 稳定多栏、角色退让、完整制作 | 共同对象同步；窗口布局与焦点本地 |
| iPhone | 途中短语音、路线、当前有限任务 | 单手入口、简洁状态、可中断手势 | 事件与版本同步；瞬时动画/音量本地 |
| iPad | 原题与笔迹、双纸、宽幅演奏 | 笔先于角色，纸面空间充分 | 笔迹版本与 Work 同步；手势状态本地 |
| Android | 延续同一生活链 | 同一动作语法，适配返回/通知/权限 | 共享协议，平台能力单独验证 |

##### D11.2 从书桌到口袋再到沙发

| 拍 | 连续事件 | 呈现 | 不得发生 |
| --- | --- | --- | --- |
| 桌边暂放 | 保存原题位置与未完草稿 | 书签回到稳定入口 | 将未完成自动记为失败 |
| 手机接住 | 用户打开接续入口 | 先显示同一对象与当前版本，再短回应 | 重播整段欢迎或整页桌面 UI |
| 途中补一句 | 语音想法附到原题 | 可改转写、明确是否发送 | 把未确认转写写成用户长期断言 |
| iPad 展开 | 用户打开同一 Work | 左题右笔迹，定位到相关处 | 用旧快照覆盖新笔迹 |
| 桌面回来 | 读取当前因果状态 | 只标新增片段，原焦点可恢复 | 把每个后台事件都重播成动画 |

##### D11.3 同步与隐私的实际契约

同一逻辑 Owner 的对象可以有多端副本；不是每端各建一个“唯一大脑”。SourceEvent、Assertion、Work、Notes、Action、书签与运动会话保留身份和因果版本。重复事件去重，乱序事件核验依赖，离线修改保留冲突和来源，不静默最后写入覆盖一切。

遗忘先在当前宿主阻断，再传播屏障；离线设备重连先应用 tombstone/fence，之后才显示旧内容。任何“绝对离线仍能同步”“隔空瞬时清除”的表述都不能作为交付承诺。

##### D11.4 平台限制也是设计材料

Live Activity 用于有开始与结束的当前任务，提供过期状态与结束态，不作为无限常驻角色容器。Apple 当前文档明确其活动时限与网络/定位限制，详见[研究记录](research/PRESENCE_MOTION_RESEARCH_2026-10-25.md)；真正的数据更新由获授权的宿主/平台机制提供。系统不允许动画时，静态状态仍必须清楚。

Android 优先适配通知、应用内状态与平台返回逻辑；可选悬浮窗不能成为基础功能的强制权限。MuMu 用于安装、协议与明确标识的模拟轨迹；不能代替真实设备上的 GPS、耗电、音频焦点或学校有效性证据。

##### D11.5 笔、触摸、键盘与声音

iPad 落笔时不自动滚页、不插入批注、不让角色挡掌；识别在适当边界发生并可修正。手机键盘出现时输入与发送稳定，角色可以退到静态或隐藏；触摸目标不照搬桌面小图标。后台音频、来电、耳机断开和系统静音各有明确行为，重开不突然恢复声音。

低动态和大字体在每端实际验证，不只是检查 CSS 媒体查询存在。VoiceOver/TalkBack/键盘路径保持共同对象与状态可理解，微表情不承担唯一通知。

##### D11.6 制作、实现与阶段门槛

先用现有资产验证竖屏/横屏裁切安全区，再按需要补母版，不能把桌面角色拉伸适配。Gemini 可参考跨场景节拍，实际平台手势用原生/当前栈可控实现；相同动作语法按设备调手感，不追求参数逐位相同。

iOS/iPad 先交付上述接力故事与实际设备证据，再扩 Android。缺签名、平台环境或真机时明确列出依赖，完成不受阻部分；不得伪称模拟器等于真机或为了过关篡改验收标准。

##### D11.7 同步理解，保留每台设备的控制权

同步稳定对象、版本、作者、来源范围与明确接受；窗口大小、当前滚动、输入焦点、音量和动作帧默认本机。接续入口让用户主动采用远端停点，不在另一台正在写字的设备上自动跳页。必要提醒有唯一投递身份，跨端确认防重复，同时保留某设备是否真正显示的未知。

同进程动作使用单调时钟；跨端事件带墙钟、时区、序号/因果依赖，设备时钟偏差不用于任意覆盖其他人的新版。重启后的单调值不可直接续算，离线期间的原始事件与重连接收时间分别保留。

**一个精修镜头**：iPad打开桌面留下的题，纸面先到准确页/版本，角色随后在边缘出现一次轻微回应；如果用户已经落笔，回应直接省略。手机收到新信息时不把桌面整段动画再播一遍。

##### D11.8 手机是实际运行主体

手机 v2 包明确要求独立运行；更新的 Swift/iPad 顺序没有撤回这项要求。安装发布等价包后，停止电脑 Vite、Node、Electron、网关与调试代理，断开 USB/端口转发，再重启手机：本地材料、原题位置、已保存事项与合法提醒仍可恢复；获授权的模型和 HTTP 连接直接由手机出站。云推理需要网络，手机本地工作不需要电脑常开。

桌面当前 Hermes Python sidecar 的存在不能证明其可直接嵌入 Swift。先做一个窄纵切，记录运行时、依赖、打包、生命周期、工具回传与取消的实际可行性；如果有不兼容依赖，以明确的移动宿主适配承接同一主循环语义和工具协议，不偷偷新增另一套记忆/人格主脑，不把 PC 远程代理当成已经迁移。形成技术决定与缺口后再扩大 UI，Android 方案结合此结果和原 v2 包选择，不强行把旧 Capacitor 建议当作 iOS Swift 的替代命令。

宿主端口分别管理 `storage / secrets / permission / scheduler / location / clock / app-handoff`，这里是接口职责而非已存在代码名。异步迁移必须等待真实事务提交；事实与 outbox 同事务，网络不占住事务；中文短词检索保留原文兜底。前后台租约、进程回收和取消必须有检查点，提醒不依赖 DOM 或 `setInterval` 存活。

三端资料传输保留 schema、lineage、附件身份与删除屏障；导入不复制凭据、OS 权限或可立即派发的外部动作，不直接复制活动中的 SQLite/WAL 文件。同步传来一条委托不代表新设备获准重做该动作。App 协作优先正式接口、分享和链接；高权限实验单独记录能力与设备范围，不能成为普通用户使用核心相处体验的前提。

**本阶段新增出口**：一条“电脑关闭→手机修改→应用被回收→恢复同一事项→另一端接续”的证据链，包含真实主库、版本、取消和界面结果。能够投屏、安装或打开聊天窗口，均不能替代这条独立运行证据。

**机制证据**证明版本、权限、幂等、来源、屏障和同步；**模型证据**证明在真实授权模型下能自然使用机制；**体验证据**证明实际页面可读、动作可打断、声音与焦点正确；**资产证据**证明身份/姿态/场景/动态连续；**平台证据**证明真机能力与限制。某一层通过不能替代另一层。
