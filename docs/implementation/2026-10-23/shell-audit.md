## 当前空间问题与原因

### 植物不能靠单一透明渐变保护正文

用户图 1 中植物、窗外高亮和角色下摆与正文有明确侵入关系。当前 `morning.png` 内的前景植物是整幅房间图的一部分，图自身从左到右有暖墙、窗、植物、桌面与沙发；不能只删除一个 DOM 装饰节点就解决。

当前几何分别在三处计算：

- `companion.css:17`：`.window-room` 从父容器 44% 起，背景 `auto 100%`、右对齐；不论窗口宽高比，都按高度缩放整图。
- `companion.css:19`：`.window-wash` 51% 前为 `--bg`，65% 后透明；中间是正文与窗景混合区。
- `design-system.css:1817`：窗边正文、标题与输入宽 `min(720px,48%)`，左边距 `clamp(32px,6vw,80px)`。例如 1366px 宽时，正文右边约 735.7px（53.9%），已进入 51%–65% 的透明过渡区。此为源码几何推断，不冒作本轮运行复现。

窗景边界与内容边界彼此不知道，所以继续增加渐变不具备保证；长网址、代码、公式、业务画面也各有自身宽度。主体文字需要属于明确的内容区，房间与前景植物的可见范围需要受同一布局关系约束。保留植物及光影，不能通过把整个窗景压成近乎不可见来交付。

### 人物尺寸约束已有价值，应保留

`CompanionFigure.fittedFigure()` 先按可用区域与真实图片比例 fit，再为最大 1.3 倍预留范围。拖动有 pointer capture、Escape/blur 取消、缩窗取消、键盘移动缩放。它已避免用户放大时把人物头部移出窗景，不应重写成任意 translate 的浮图。

但人物区域在 `companion.css:20` 独立用 `inset:9% 3% 2% 53%`；760px 以下又变为从 36% 起。它与正文没有共同轨道，角色虽然 fit 在自己的框中，框本身仍未与内容边界形成统一关系。

### 退让策略是全会话阈值，缺少当前任务的连续性

`App.tsx:355–367` 的策略为：

- 任一助手历史消息含 `views`，`hasScene` 就为真；整段会话以后都没有大窗边人物，也不给“回到窗边”入口。
- 任一助手消息达到 560 字或 14 行，自动进入安静阅读。
- 非空聊天在宽度 ≤900px 时自动退出窗边；空欢迎页仍允许窗边，并由高低窗口媒体规则改变结构。
- 安静布局把房间降至约 3.5%/4.5% 并直接隐藏人物，不是按当前专注对象调整相处距离。

现有自动让位和手动安静阅读值得保留。需要将“当前使用空间”与“历史上曾有复杂内容”分开：读纸/看地图时让位，回到普通交流时能自然回到所选窗边；仍由用户选择保持安静，而不是新消息出现就夺回位置。

### 窄窗欢迎页有两种真实结构，需分别验收

`workspace-continuation.css:59–97` 在宽≤900且高≥700时，把欢迎文字放到下方实底卡面，人物留上方；低于700高则隐藏人物并把房间降到6%。这两种关系不能用一张窄屏截图代替。正文放大到1.3时，底部欢迎卡也需检查是否抢占人物与输入空间。

## 主题最小正确架构

主代理确定 GPT Image 设计方向后，可沿现有所有者增量实现，不需要新的主题管理器、第二套状态层或依赖。

1. 在现有 `Appearance` 增加一个明确的色系字段（如暖杏/雾蓝/暮紫/雨金），继续保留 `theme:'light'|'dark'|'system'` 表示明暗。缺字段迁移到暖杏；原字号、密度与明暗选择原样保留。色系不写角色人格、业务数据库或记忆。
2. 根元素通过一个 `data-palette` 与现有 `data-theme` 共同选择 tokens。同一语义 token 覆盖文字、中性面、边界、控件、选中、焦点和错误；不要只改 `--accent` 后留下一页互不相容的暖灰/冷灰。
3. 窗景素材映射到色系、时段与阅读用途，由 `CompanionScene` 读取；明暗选择不由光线按钮偷偷覆盖。使用生成资产与主题光影校准，避免为每一控件引入单独滤镜。
4. 一个主壳 CSS 布局关系共同拥有内容右边界、窗景起点和人物可用区；宽窗是左右关系，窄高窗是上下关系，阅读/资料/地图拥有充足内容区。装饰全部在自身裁切范围，正文和 composer 使用同一轨道。
5. 保留 `prefersQuietMotion()`、系统减少动态和用户减少动态；主题渐变、场景移动与人物入场可取消，不通过长动画延迟用户点击。
6. `useAppearance()` 当前只有自定义 `appearance-change` 监听，没有其他窗口的 `storage` 同步；如本次保留多 renderer 表面，应补同 key 的 storage 监听，仍从同一个读取/应用函数回放。

## 返回、中断与动作连续性

已存在的关键机制不能被主壳视觉重建冲掉：

- `App.tsx:283–340`：同一 composer host 移动使用 `moveBefore`，fallback 保留焦点/选区；IME 中不迁移；FLIP 动画可取消并服从减少动态。
- `rememberReadingPosition()` 记录原 DOM 段落与视口偏移；`atWindow` 变化及回到聊天恢复阅读位置。布局改造应先记住再变化，而非自动滚到底部。
- 资料、笔记被首次打开后保持挂载，通过 `active`/hidden 切页；笔记未保存时关闭窗口会回笔记。不能为了转场动画每次卸载整页。
- `stopReply()` 增加 `sendSequence` 再 `api.stop()`，原稿与引用保留；有草稿时“补一句”沿停止旧run→核当前身份/来源→普通 `api.send`，没有旁路模型。
- 出错/取消消息的“接着说”通过原 `onContinueScene` 回当前输入。它不是自动恢复已取消 run、旧授权或未公开尾部。
- `openConversation()` 拉取该会话消息与草稿，并核导航 token；切到另一段前处理原会话生命周期；设置草稿保存在原 `settingsDraft` ref。
- `requestClose()` 先 flush program 本地值，再回读真实未保存草稿与附件；关闭弹层与窗口生命周期不能被新的全屏休憩页绕开。
