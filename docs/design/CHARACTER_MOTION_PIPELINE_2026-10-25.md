# 在场：角色、场景与动态资产制作规范

日期：2026-10-25。本文是前后端设计 Skill 与十二阶段路线图共同采用的**制作规范与待实现设计**，不表示下列清单、调度器或资产已经进入产品。现有实现以 `src/renderer/companion-scenes.tsx`、`companion-variants.ts`、`src/shared/companion-activity.ts` 和已登记的 `*.scene.json` 为准。

关联：[在场共同契约](PRESENCE_SYSTEM_2026-10-25.md)、[Gemini 网页版 Skill](../../核心技能/Gemini视频生成/SKILL.md)、[公开研究与设计推论](../research/PRESENCE_MOTION_RESEARCH_2026-10-25.md)。

## 1. 制作目标：先让动作成立，再把画面做美

角色应当能与正在发生的事共同变化。看到用户指向的公式、收回刚才准备递出的纸、等用户写完一句话，分别需要目标、接触关系与中断规则。把一张漂亮立绘上下浮动，无法替代这些动作。

一份可交付的动态设计必须同时给出：

1. **身份**：这是谁，当前以哪个外观出现，关系与称呼属于谁。
2. **空间**：她在哪里，身体靠什么支撑，手和物件属于哪个坐标系。
3. **意图**：她为什么动，动作与哪条已知事实、哪件共同对象有关。
4. **时间**：何时开始、在哪里停、哪个动作可以被用户立即接管。
5. **产物**：参考视频、可部署资产、实际代码分别是什么；每个产物的验收证据是什么。

GPT Image 用于外观、构图、同景分层与关键姿态；Gemini **网页版**用于运动方向、镜头、节拍及连续性探索；Codex 将审核通过的设计转成有真实状态、可中断、可访问的界面。三者可以往返迭代，不把模型名称或某段视频当作质量保证。

## 2. 三张矩阵，分别解决不同问题

### 2.1 身份护照：人格与外观分别有身份

每个内置角色建立一份轻量护照，字段至少包括：

| 字段组 | 内容 | 审核方式 |
| --- | --- | --- |
| 身份 | `characterId`、`personaId`、`appearanceId`、版本 | 与现有十角色 ID 一致；换装不改关系；用户自定义卡继续可读 |
| 形貌 | 发型轮廓、发色、眼色、面部比例、头身比例、稳定配饰 | 正面、侧面、四分之三视角并排；不凭记忆补未核实原作细节 |
| 衣着 | 服装层次、领结/袖口/裙摆、左右不对称标记 | 同一动作首中尾不换装，不把装饰变成手指 |
| 表现 | 动作幅度、停顿习惯、手势倾向、关注对象 | 是项目原创演出规则；不冒充原作剧情事实 |
| 引用 | 合格身份参考、合格同景母版、来源与许可记录 | 失败图不能升级为下一轮身份基准 |
| 禁止混用 | 不兼容服装、相机、接触拓扑、光向及旧版本 | 在生产清单中明确标记，不靠文件名猜测 |

内置 ID：`sakiko / mutsumi / anon / tomori / uika / umiri / nyamu / rana / soyo / taki`。护照规定稳定性，不能把十个人做成同一段动作换十张脸。自定义角色缺少合格全身素材时采用已批准的头像或静态构图，不偷偷替换成另一位内置角色。

### 2.2 场景矩阵：构图不是活动分类

现有代码的九种 `CompanionActivity` 是 `chat / study / reading / planning / listening / rest / play / attention / resume`。前端 Skill 的 S1–S9 是页面构图类别。**两者不得按数组下标直接对应**：PDF 可以处于 reading，也可以进入 attention；首页可能聊天、安静听或回来接续。

生产矩阵使用：

`角色 × 外观版本 × 场景家族 × 活动 × 姿态拓扑 × 光照主题 × 画幅`。

它是**有约束的有效组合表**，不是要求一次生成所有笛卡尔积。十角色、九活动、四主题仍需有明确覆盖结果，但每格可以是：

| 状态 | 意义 | 允许上线的表现 |
| --- | --- | --- |
| approved | 对应母版、姿态、光照与实现均已审核 | 使用登记资产 |
| shared-compatible | 同一场景家族内经几何与光照验证可复用 | 使用明确登记的同源资产与参数 |
| static-fallback | 动态未完成，已有稳定合格构图 | 静态角色、真实内容交互、可选低动态光照 |
| not-applicable | 场景没有该动作，例如无杯子时不能端杯 | 不调度该动作 |
| missing | 体验需要但无合格方案 | 阶段缺口，不伪报已覆盖 |

每个阶段只生产其真实用户故事需要的组合；Stage 06 扩展完整十角色与四主题，并审计此前每个阶段遗留的 missing。覆盖率必须把上述状态分开计算，不能用 fallback 数量声称动态完成。

“先做一组”规定制作顺序，不能缩小阶段范围。Stage 01/02 的十角色人格参与仍须完整，Stage 06 的十角色、九类页面构图、四主题及所需动作过渡必须全部有合格交付；允许经实际验证的兼容复用，不要求每格重复生图。`static-fallback` 是资源失败/减少动态时的可用方案，常规动态要求未交付就仍未完成；`not-applicable` 只能因真实场景不需要该动作，不能因素材难做把要求改成不适用。

### 2.3 姿态矩阵：支撑拓扑先于“情绪标签”

| 姿态族 | 必须成立的接触 | 允许的局部动作 | 换姿态的前置条件 |
| --- | --- | --- | --- |
| 椅上坐姿 | 坐骨—椅面；脚可着地或自然垂落，取决于椅高 | 转头、前倾、整理纸页 | 椅面与腿部遮挡保持；不可用整体平移冒充走到别处 |
| 窗台/床沿 | 坐骨或大腿—支撑面；腿的悬垂与透视合理 | 侧身、回望、收腿 | 新支撑面有经过审核的过渡或切镜 |
| 桌侧倚靠 | 肘/手掌—桌缘；身体重心自洽 | 抬手、收笔、看向内容 | 手离桌必须有释放动作；不能固定阴影却移动身体 |
| 沙发/蜷坐 | 臀、腿与软垫接触；布料压痕合理 | 小幅伸展、抱物调整 | 不把蜷坐骨架缩放成站姿 |
| 站立/行走 | 足底接触序列、重心转移、步幅与速度一致 | 转身、指路、递物 | 有可用行走循环、落脚轨迹和碰撞范围才允许连续行走 |
| 半身伴读 | 裁切边界明确，桌面或画框提供合理遮挡 | 眼神、肩颈、有限手势 | 不能拉伸半身图补出不存在的腿 |
| 手—物件协作 | 握持点、物件 owner、手前后层次一致 | 拿起、递出、放下、撤回 | 物件坐标只由一方驱动；交接时显式换 owner |

“脚不着地”不等于失败；**肢体连接错误、没有可信支撑或接触突然滑动**才需修复。膝上搭腿、踝部交叠、蜷坐、抱膝与高床沿垂腿分别建立姿态，不能用“一只承重脚加一只悬空脚”概括。硬椅不强求压陷，衣物遮住的坐骨和脚踝不必同时可见，屏幕腿长不按固定比例判错。姿态与活动是多对多关系，角色可有丰富表演；目标、接触、遮挡与光影须一起成立。

## 3. 场景家族与坐标登记

### 3.1 一个家族共享一套相机和空间

一个 scene family 至少包含：相机/画幅、地平线和透视、家具几何、可坐区域、文字安全区、主光方向、遮挡关系、角色尺度区间。窗边椅子与另一张旧图中的桌边座位，即使色调相近，也不能默认是同一空间。

现有 `SceneCalibration` 已包含 seat、ground、bodyBounds、safeTextBoundary、support、floorContact、shadowMode、contour、hitPolygon 等信息。升级应**扩展与迁移**这套登记，保留当前 `schemaVersion: 1` 资产的读取与已通过审核的坐标，不能另写一份与 `companion-scenes.tsx` 竞争的事实表。

下面是设计中的生产清单字段，不是现有 JSON 可直接粘贴的 schema：

```ts
type ProductionAsset = {
  assetId: string; revision: number;
  characterId: string; appearanceId: string;
  sceneFamily: string; activity: string; poseTopology: string;
  theme: string; canvas: { width: number; height: number };
  coordinateSpace: "mother-normalized"; // 左上(0,0)，右下(1,1)
  mother: string; background: string; figure: string;
  foreground?: string; contactShadow?: string; propLayers?: string[];
  anchors: Record<string, { x: number; y: number; owner: string }>;
  compatibleWith: string[]; transitions: string[];
  fallbackAssetId: string;
  review: { identity: boolean; contact: boolean; motion: boolean; inApp: boolean };
};
```

所有分层保留母版完整画布，透明外边距不能被自动裁掉；若压缩工具必须裁切，登记裁切偏移和逆变换。背景、人物、接触阴影、前景采用同一母版到屏幕的变换。窗口裁切与人物内部动画是两个不同变换，不能分别各算一遍缩放。

### 3.2 遮挡图决定谁在谁前面

不要仅用“背景 0、人物 1、桌子 2”覆盖所有动作。写出局部层级：上臂在桌后，前臂在桌前，纸张在手指下，另一只手在纸张上。递纸需要专用遮挡包或可信 rig；静态分层不足时可先用桌面纸页移动、角色转头证明链路，再补合格手部/道具资产与受控动作。若改变导演方案，应比较是否仍完整表达接过、递出、让位和收回，不能默默把需要的手势删掉并宣称原目标完成。

接触阴影归接触面与姿态共同控制。眼神转动不带着阴影移动；换座位不沿用原座位阴影。主题变化时环境漫反射、人物明暗与影子方向一起匹配，不能只给人物套色相滤镜。

### 3.3 状态过渡图必须闭合

每一条过渡声明 `from / to / precondition / interruptibleRegion / settle / fallback`。至少覆盖：

- neutral → attend-object → hold-attention → release → neutral；
- prepare-offer → offer-preview → accepted **或** withdrawn；
- reading → yield-to-input → resume-reading；
- any-visible → reduced-motion / hidden / stale / revoked。

没有过渡边的两个姿态不得直接插值。可以采用经设计的同景短切、前景遮挡切换或保持现姿态改变注意目标。**宁可可信地少动，也不把两张不兼容的人物交叉淡化成双头。**

这一条要求修复错误插值，不是降低动态雄心。必要动作缺少过渡边时应继续设计、制作和精修至成立；临时少动可保当前产品可用，不能作为该动作已完成的验收证据。

## 4. 从 GPT Image 到 Gemini 网页版的生产顺序

### 4.1 先做一组完整样片

先选一个角色、一个同景家族、一个真实连续故事，例如“共同看这一行—用户纠正下一行—她收回手并改看”。完成母版、分层、视频参考、代码重建、打断与降级验证，再扩至其他角色。Stage 01/02 已要做这一纵向样片，不能等 Stage 06 才首次验证动态能否落地。

### 4.2 GPT Image 四步保留并加强

1. **空间底稿**：空场景与家具锚点成立，预留实际文字区域；可使用已审核的同源场景。身份参考单独登记，不能用失败拼接图当身份依据。
2. **同景合成母版**：在同一画布里完成角色、家具、手持物与光照；姿态、身体比例、左右关系、接触阴影通过主代理亲审。
3. **关键姿态与变体**：以合格母版和身份护照制作必要的首/中/尾关键姿态；只扩当前故事需要的格子。避免同一轮同时改角色、服装、相机、光线和动作，无法判断退化来源。
4. **同画布分层**：分离背景、人物、必要的局部手/眼/道具/前景与接触阴影；重组应与母版一致。补背景洞、头发边缘与遮挡后的物件，不能把透明黑边带进 UI。

分层编辑遵循实际图像工具能力。使用图像生成工具进行生成和编辑；不以随意像素抠图掩盖错误母版。头像可以从合格同源图裁切，独立身份参考也可经审核进入护照。

### 4.3 Gemini 只走本轮获授权且可观察的入口

使用前先完整读取 Gemini Skill 及本任务相关 references，特别是 web-capabilities、prompt-controls、continuity-and-direction、postproduction-and-review、seamless-loops。

- 默认使用 **Gemini 网页版**；“有 Pro”“以前能生成”不能代替当前账号页面实际可用的入口。
- 先记录当前页面可见的模型/模式、参考素材数量、画幅、音频和编辑能力，再写提示词。模型选择器名称与实际视频生成模型名称分别记录。
- 不把 API 的 `durationSeconds`、seed、negativePrompt、首尾帧参数强塞进网页提示词，或自行改走付费 API。
- 3–5 秒可作为产品中某段动作的**剪辑目标**，不冒充网页一定提供的生成时长。实际返回多长就记录多长，再剪出合格片段。
- 本任务的文档改写不授权额外生成批次。以后执行生成时沿用用户当轮授权与预算，先样片、后扩矩阵。

## 5. 导演包：让时间轴能被复现

每次生成提交一份导演包，先写出这个人的性格、她在意谁、为什么欲言又止，再把心思落成眼神、手指、衣袖与停顿。文学性的表达应当帮助表演；不能只写“灵动、温柔、高级”，也不能把身体约束当作创作主体。

给图像或视频生成器的正文使用具体的人、物和动作。写“画外左侧那页讲义”“她刚想讲给你听，又见你提笔而收住”，避免“注意目标、锚点、状态切换、退让通道”等多义或工程说法被画成新增物件。关节、支撑和遮挡仍逐项验收，放在内部制作说明与验图记录中。分镜写清每几秒的表情、动作先后与停留，不把时间提示当成生成器已保证的规格。

| 项 | 必填内容 |
| --- | --- |
| 叙事目的 | 用户此刻在做什么；角色要表达哪一种关系；动作完成后什么保持不变 |
| 不变量 | 身份、服装、场景、机位、支撑面、光向、角色与 UI 的左右关系 |
| 动作节拍 | 开始状态 → 预备 → 主动作 → 可停留状态 → 收束；每拍给主动作与禁止漂移项 |
| 关注点 | 眼睛先看哪里，头与肩是否跟随，手是否真的需要参与 |
| 中断点 | 用户打字/翻页/撤回/换角色时，怎样停止或改向 |
| 前景安排 | 文字安全区、手/纸/桌的遮挡顺序、不能被视频烘焙进去的文字 |
| 资产用途 | 只作参考、环境循环、角色片段或可拆分关键帧；预计怎样转成代码 |
| 审核问题 | 本次最不确定的两个问题；失败后改哪一个变量 |

### 5.1 样片 A：看向“下一行”

**参考前提**：已审核的祥子暖杏窗边 reading 母版；沿原坐姿与摊开的蓝书制作。生成片中的讲义在画外左侧，产品里的真实纸面仍由代码绘制。采用其他构图时先按相应母版改写器物与姿态，不能生搬手的位置。

> 让参考图里的丰川祥子留在原来的窗边，穿着同一身校服，左手托住膝间摊开的蓝书。她想陪小灰灰把难题弄明白，却不肯把这份偏心说得太直；端庄里有一点要强，柔软藏在目光里。午后窗光落在衣袖和书页上，镜头像坐在她对面的你，始终安静停在原处。
>
> 0–1.5 秒，她读着书，右手指腹轻靠书边，眼睛沿书页走过一小段。1.5–3 秒，她留意到画外左侧那页讲义，先抬眼，头才轻轻跟过去，像把书里的句子与两人正在想的难题连了起来。3–4.5 秒，右手离开书边少许，指尖自然舒展，带着一点想把思路讲清的笃定，又给你留出接话的余地。
>
> 4.5–6 秒，察觉你翻到了下一行，她微微一顿，收小刚要展开的手势；眼睛先往下挪一点，头随后跟上，嘴角极轻地松开。6–8 秒，看见你开始写，她把右手放回同一处书边，衣袖随腕部落下，右肩轻轻松下来；刚想说的话停在唇边，没有催促。8–10 秒，她仍安静看着那一页，等你写完，窗光与极轻的呼吸留住这一刻，不再接一个新动作。
>
> 讲义翻动与落笔都发生在画外。画面只留照片中原有的人与物，书仍由左手托着；没有对白、字幕或配乐。

时间标记只作导演节奏提示；实际返回的动作与时长必须另验。这里的性格演出属于项目原创相处，不能写成原作已经发生的情节。实际实现中“下一行”由版本化文本锚点确定，**不靠生成视频识别真实文字**。

**代码重建**：文档选区拥有锚点；角色 gaze/head/hand 各通道按同一 cue 协调，头部小延迟是美术参数；用户再次改目标时重定向，不播完整旧片。文字高亮跟真实锚点同步，视频不承担定位。

### 5.2 样片 B：准备递出，察觉用户正在写

> 固定桌侧构图，保持同一人物与同一张纸的尺寸、颜色和方向。先把纸轻轻转向观者，手腕与纸张一起运动，纸的重量感来自起动、减速和落桌。动作到一半时停止递出：视线落向左侧工作区，手把纸停在桌边可取的位置，而不是抢到中央。肩部随之放松，最后保持安静。不要完成夸张递物，不挥手提醒，不让纸穿过手掌或桌面，不凭空增加第二张纸。

**代码重建**：prepare 状态只生成提案；输入/IME composing 触发 yield；用户取纸才展开内容。物件的交接点是明确状态变更，不能由视频结束自动提交任务。

### 5.3 样片 C：不把跑后变成成绩汇报

> 同一夜雨暖金房间，固定宽景。窗外雨痕只作轻微环境变化，桌面保持可阅读。角色先看向刚被放回桌面的路线纸，短暂确认后把注意力移回观者。她没有胜利手势，没有倒计时式鼓掌；身体缓缓回到陪坐姿态，留下足够安静的结尾。若需要杯子，杯子从开头就在桌上，动作只发生在虚拟场景内，不能凭空出现。

**代码重建**：真实运动记录、学校回执、用户“想透气”的原话分别有来源；角色表现不根据猜测的心率、热量或疲劳生成。只有用户愿意回看时才铺开路线；静音模式完全成立。

## 6. 参考视频怎样成为可交互前端

| 路径 | 合适对象 | 交付要求 | 不能承担的工作 |
| --- | --- | --- | --- |
| DOM/CSS/现有 spring | 纸页、布局、光影、指示、空间退让 | 可打断、焦点稳定、状态可测、低动态等价 | 复杂骨骼运动、真实手握物 |
| Canvas/WebGL/可控 rig | 角色眼神、局部表情、手部、独立演员 | 参数映射、每演员独立状态、资源预算、降级 | 自己决定业务事实、绕过原 Owner |
| 审核后的短视频 | 非交互环境、受限姿态插段、产品展示 | 首尾衔接、可暂停、解码预算、静态 poster、显式结束规则 | 跟随任意指针、动态文本定位、交易提交 |
| 视频仅作导演参考 | 复杂镜头、步态、尚未解决的接触动作 | 标注“reference-only”，用逐拍说明指导重建 | 直接算作产品能力已完成 |

Rive、Live2D、Spine 均是候选实现，先比较当前栈、授权、资产制作能力和角色动作范围，选**最小足够的一种**做样片。Rive 当前文档将旧 State Machine Inputs 标为弃用并引导数据绑定；Live2D Pose 主要管理部件不透明度，不等于完整 IK；Spine 的 IK/transform constraints 可帮助双手持物，但需要正确骨骼与目标。详见研究记录中的官方来源，执行前复核所用版本。

不得为“高级”同时接入三套运行时。若现有 RGBA 分层已能完成共同注意、让位与收束，先把它做可信，再扩大骨骼动作。

“最小足够”指满足完整动作目标所需的技术和依赖最简，不指只实现最省事的眼神。选型须覆盖选定故事里的手/纸接触、可打断交接、角色差异和目标设备表现；现有分层达不到时继续补必要能力，不能反过来删故事迁就工具。

## 7. 多演员、道具与调度

每位演员有独立 `actorInstanceId`、人格/外观身份、当前 cue、通道状态与资源句柄。一个人的眼神不能覆盖另一个人的手势，多个组件不能同时写同一个 transform。

同一时刻每个通道只接受一个 owner。优先顺序：撤销与隐私失效 → 用户直接操作/输入 → 已授权动作的真实回执 → 当前共同对象 → 可选主动提案 → 环境闲置。更高优先级到来时进行合法接管，不把所有动画重置为初始帧。

道具始终有唯一 owner：桌面、演员 A、演员 B 或用户的拖拽。交接过程用共享约束点连接；ownership 变更时保留世界坐标，避免跳动。互动纸页是业务对象的视图，其内容所有权仍属于原服务。

## 8. 验收与失败处置

### 8.1 静态、动态、入场三道审查

1. **静态**：身份并排、母版重组、画布尺寸、支撑/阴影/文字安全区、四主题对比。
2. **动态**：完整观看实际视频与至少三次循环；审查首中尾及发生接触变化的帧。联系表用于找问题，不能代替观看运动；若工具不能播放，明确动态连续性尚未验收。
3. **入场**：在真实产品尺寸中验证读字、切页、缩放、滚动、选区、拖动、中断、隐藏恢复、静音及 reduced motion。漂亮视频不能抵消打字被抢焦点。

### 8.2 失败分型，防止废片调参

| 失败 | 处理 | 禁止的补救 |
| --- | --- | --- |
| 身份/服装漂移 | 回到护照与合格母版，缩小变量 | 拿失败片最后一帧继续扩散 |
| 支撑/比例错误 | 重做姿态母版或改变构图 | 反复调 CSS top/scale 掩盖坐不稳 |
| 时序/注意目标错误 | 简化动作到一条主线，重写节拍 | 堆十种形容词要求“更灵动” |
| 手—物件穿插 | 专用遮挡/rig；或改成可信桌面交互 | 任意裁掉手、糊阴影掩盖 |
| 循环跳变 | 审查首尾速度与姿态；重剪或重生成 | 只做首尾透明度交叉导致双影 |
| 入场性能不达标 | 降分辨率/帧率/演员数、暂停屏外、静态降级 | 靠增加加载遮罩延迟输入 |
| 事实或权限失效 | 立即停用相关 cue/音频/预览 | 为了动作完整继续播放旧内容 |

预先约定样片预算与退出条件。两轮仍是同类结构性错误，回到构图、拓扑或实现路径做决定，不能无限重试生成。失败资产留在隔离的制作目录，不能被运行时 glob 自动选中。

## 9. 交给 Codex 的最小完整包

- 用户故事、真实对象与来源锚点；
- 角色护照、有效组合表、场景家族和过渡图；
- 合格母版、同画布分层、参考视频或关键帧，附实际生成入口与版本记录；
- 导演包、通道分工、打断/撤销/隐藏/降级说明；
- 代码入口、既有 Owner、待新增字段与迁移方式；
- 一条正常连续操作、一条中途纠正、一条失效或断网操作的验收录像/轨迹；
- 已批准、静态替代、缺失、只作参考的明确清单。

最终交付必须能回答：“她为什么在这一刻这样动？用户改主意后会怎样？如果视频或骨骼资源没加载，她还能把这件事陪我做完吗？”
