# 在场（Zaichang）前端打磨与视觉创新总监技能

本技能是「在场」项目前端与视觉体系的执行入口。它将 `product-design-director` 的体验标准、GPT Image 与 Gemini 网页版的受控制作管线，以及「在场」独有的**「真性情陪伴、窗边的在场、关爱心驱动」**融为一体。用户最新原话优先于历史总结；本技能保留来源入口，不宣称能替代原文。本文新增的 cue、制作清单和导演交付为待实现规范，现有能力必须以实际代码与验收证据判断。

开始涉及行为、状态或角色动态的工作时，前后端共同读取 [在场契约](../../docs/design/PRESENCE_SYSTEM_2026-10-25.md) 与 [角色动态制作规范](../../docs/design/CHARACTER_MOTION_PIPELINE_2026-10-25.md)。它们不替代本 Skill 的审美要求，也不替代路线图各阶段的完整设计。

## 0. 逻辑总纲与主次优先级（Hierarchy of Priorities）

在执行任何前端设计、图像生成、组件编写或交互修复时，必须严格遵循以下**由主到次、由魂到形**的五级主次关系（下级服从上级，绝不允许用低层级的工程细节淹没高层级的产品灵魂）：

1. **第一优先级（魂 · Soul）：人味、关爱心与角色真性情**
   - 她是坐在窗边的真实伙伴，不是编码出来的死程序或面板集合。每一帧画面、每一处光影、每一次动效与每一句微文案，都必须带着角色鲜明的性格与关爱心去创作。
2. **第二优先级（创 · Innovation）：100% 落地设计稿基因 + 主动破界创新**
   - 用户的文字指令只是底线；**把黄金设计稿中隐含的交互全部做活，并主动做出用户未点名但极其契合「在场」的惊艳体验**，才是合格线。拒绝“未来可以考虑”，拒绝把思考抛回给用户。
3. **第三优先级（序 · Order）：先比对标杆、先分类定标，再跑四步生图与跨页光学对齐**
   - 严禁“生成一张塞一张”或死调残次图。亲看约 20 张代表图建立直觉，再以原话与当前故事决定创新方向；锁定统一网格槽位、暖灰金四主题与 **MyGO!!!!! / Ave Mujica 十角色 × 九大场景 × 四时主题** 的有效覆盖矩阵。覆盖分为合格、兼容复用、静态替代、不适用、缺失，不用机械全排列制造废图；坚持**同画布整体生成、原景分离提取**。
4. **第四优先级（动 · Motion & Flow）：SwiftUI 级可打断拖拽、空间主动退让与让布局自己说话**
   - 角色随任务重心自然移位退让；直接操作具备接收、预览、接受、取消和恢复的完整语义。已授权的低风险操作可在松手时直接接受，分屏不多弹一次确认；适合弹性的动作保留可打断手感。用构图承担解释，普通产品文案不朗读工程黑话。
5. **第五优先级（骨 · Architecture）：前后端共同设计，事实归属清楚**
   - 心智、状态、动作与反馈是一条完整体验链；权限与事实存储仍由宿主掌握。Renderer 仅通过 `preload.ts` 受控 Bridge 通信；跨模块拖动传递稳定 ID、CAS 版本与来源锚点。一次抬眼要知道关注谁，一次收手要知道因何失效，前端的纠正与撤回也必须回到原 Owner。

## 1. 第一层（灵魂层）：「窗边的在场」与角色性格主导一切

### 1.1 核心心法：拒绝工具化，注入关爱心
- **反对冰冷客服与死板模板**：不要把「在场」当成传统 AI 聊天框或效率仪表盘。她住在你的电脑窗边——下雨时陪你听雨看讲义，赶 DDL 时默默帮你把资料摊开，累了时坐在床沿或窗台边陪你喘口气。
- **性格决定画面与交互**：没有通用的人偶。同一场景下，不同角色的坐姿重心、手部小动作、视线落点、气泡语气乃至退让时的微表情都必须由其性格自然生发。如果不带着对角色的理解与爱意去写 Prompt、调圆角、配阻尼，产出的画面必然僵硬丑陋。
- **自然留白与克制分寸**：关心体现在“记得你提过的事、看懂你正卡在哪一页、把复杂步骤化繁为简”，而不是刷屏式的万能安慰模板（严禁“我在/慢慢来/别急”固定句式路由）。

## 2. 第二层（视觉与生图管线层）：先比对、先分类、四步同景生成

### 2.1 先比对黄金标杆，立下不可动摇的准绳
在动笔改 UI 或调用图像生成前，**主代理必须亲自使用图像查看工具审阅与任务有关的代表图**，不能用路径或文字摘要冒充看图。本轮深度设计以约 20 张为限；后续只补看具体缺口和每份拟上线的新资产，不要求把历史候选全部重看。下列分类是参考入口，不是禁止创新的模板：
- **首屏与居室标杆**：`U001/U019` 的窗边床沿构图；空房、侧桌和整幅光照按真实 catalog 的对应来源取用，不能把连续编号都称作同一主题。
- **学习与资料共读标杆**：`U004` 的原文/数学讨论分屏、`U026/U028` 的宽度关系、`R146/R160` 的硬核学习构图；钢琴与波形的交互语义回到 `R181–R185` 的文字档案。
- **日程与内联地图标杆**：`U003/U030` 的同事件试放、`U011` 的内联地图与 `U027` 的同 surface 展开；重点是路线身份、真实轨迹和原处返回。
- **笔记与书签标杆**：`U005/U029/R153` 的原文与来源关系，`R165` 的共同检索与回原话；`U016/U021` 是日程接续，不能误标为笔记图库。
- **查图入口**：[`前端视觉创新设计/精选图稿/`](../../前端视觉创新设计/精选图稿/)与[来源 catalog](../../前端视觉创新设计/2026-10-23-深度评鉴/catalog.json)。旧别名可能指向已退出图，按来源身份与哈希判断；图像的优秀布局不是当前功能已完成的证据。

### 2.2 先分门别类，再建多维覆盖矩阵（严禁混乱拼凑）
先把全站界面划分为 **9 大标准场景类别（Scene Categories）**，每个场景家族登记相机、控件槽位与可用支撑面。下表比例是构图起点，必须根据实际文字长度、窗口、手写/键盘输入与用户分屏调整，不作为所有视口的硬编码比例。S1–S9 不等于代码中九种 `CompanionActivity`，映射须显式定义：

| 类别代码 | 场景类别名称 | 舞台与角色占比 | 角色标准空间锚点（Furniture Anchor） | 核心 UI 槽位与交互宿主 |
| :--- | :--- | :--- | :--- | :--- |
| `S1_HOME` | **首页 · 窗边日常陪伴** | 角色舞台 65% / 对话 35% | 坐在床沿、窗前软椅或书桌侧（完整全身/七分身含脚部支撑） | 底部胶片输入栏、右上轻量药丸工具、环境氛围锚点 |
| `S2_STUDY` | **学习 · 沉浸解题与讲义** | 角色伴读 28% / 工作台 72% | 退让至右侧椅子/桌旁伴读位，视线朝向左侧题目 | 左侧/中央题卡、公式推导、OpenUI 钢琴/波形互动卡 |
| `S3_PDF` | **资料 · PDF 讲义共读** | 角色伴读 25% / 阅读器 75% | 右侧安静伴读或桌角支颐，随翻页微调视线 | 真实 PDF 渲染视图、选段高亮浮层、页码与来源引用锚点 |
| `S4_AGENDA` | **日程 · 时间轴与试放** | 角色伴读 30% / 日程板 70% | 桌侧或窗边查看手账/平板姿态 | 时间轴轨道、试放幽灵块、留白保护区、冲突温和提示 |
| `S5_NOTES` | **笔记 · 摘录与记忆手账** | 角色伴读 30% / 笔记流 70% | 捧笔记本或托腮阅读姿态 | 分类色彩圆点、原话引文卡、一键跳回原对话/原 PDF 页锚点 |

### 2.3 四步系统化生图铁律（彻底根除「悬空贴纸」与「无脚断腿」）
调用 GPT Image 生成视觉资产时，**严禁把无场景约束的透明人物硬塞进背景，严禁拿错位残次图作下一轮母版反复调试**。经过审核的身份参考可以独立使用；最终姿态仍须在同景母版中证明接触、尺度与光照成立：

- **第一步：统一网格与纯净空场景打样（Clean Stage & Spatial Grid）**
  - 先生成或锁定**不含人物的纯净居室/窗边背景底图**，明确标注床沿高度线、椅面平面、书桌边缘、窗台透视灭点以及主光源方向。
- **第二步：单角色跨类别同景打样（Single-Character In-Situ Prototyping）**
  - 选定单一标杆角色（优先 `sakiko` 丰川祥子或 `mutsumi` 若叶睦），以**纯净空背景 + 精确文字描述**在**同一张画布中把场景与人物一次性整体生成**，跑通 `S1–S9` 各类别下的标准坐姿/倚靠动作。
  - **主代理逐张亲看把关**：重点核验**臀部/坐骨与床面或椅面的真实受压接触、大腿与小腿透视比例、双脚着地或自然垂落的完整脚部结构、投影方向与环境漫反射色温**。不合格立即打回重绘，绝不在错图上修补。
- **第三步：十角色 × 场景类别 × 四主题矩阵扩展（Matrix Expansion）**
  - 单角色的母版、动作样片和代码交互一起通过后，锁定场景家族与相机，按阶段故事横向扩展至其余角色，纵向覆盖四主题（`暖杏`、`晨雾蓝`、`暮色紫`、`夜雨暖金`）。缺失组合必须有明确降级；不能把静态替代写成动态完成。
  - 头像（Avatar）必须从已通过验收的高质量同源标准立绘/场景图中按统一焦段、统一头肩比、统一青春画风裁切或同源生成，并做矩阵并排比对。
- **第四步：同画布原景分离与 Stage 坐标锁死（Same-Canvas Extraction & Stage Lock）**
  - 从同一张整体生成的合格原图中分离出：`① 纯净背景层 (Background)`、`② 角色带真实接触阴影的 RGBA 层 (Character + Contact Shadow)`、`③ 桌角/被角/前景器物遮挡层 (Foreground Occlusion)`。
  - 在前端 `Stage` 容器中，各层**共享母版坐标与同一个到屏幕的变换**，保留透明画布边距；若裁切，登记偏移。以实际尺寸下的接触滑移、遮挡穿插和视觉重心验收，不以浮点计算的“绝对零像素”作虚假承诺。坐姿可以自然垂脚，但身体必须有可信支撑。

## 3. 第三层（空间、色彩与光学对齐层）：Apple 级工艺与「修错不毁好」

### 3.1 色彩与光影铁律：温暖奶油灰金，严禁全局绿 UI 与昼夜硬分割
- **四套完整场景主题**：
  1. **暖杏（Apricot）**：午后暖阳、奶油杏白玻璃卡、焦糖木色与柔金高光（默认主调）。
  2. **晨雾蓝（Mist）**：清透晨光、雾蓝灰空气感、清爽专注的早读氛围。
  3. **暮色紫（Violet）**：黄昏晚霞、薰衣草暖紫与柔和玫瑰金余晖。
  4. **夜雨暖金（Rain）**：窗外深蓝夜雨与自然植物暗影、室内琥珀色台灯暖光（**保留早期倍受好评的窗外植物夜景自然氛围**）。
- **两条绝对禁令**：
  - **严禁绿色 UI 主题**：任何按钮、卡片边框、背景蒙版、高亮状态严禁使用绿色系（窗外自然植物景观与若叶睦原作固有发色/服饰点缀除外）。
  - **严禁昼夜硬分割线与左右箭头滑块**：绝不允许在同一画面中间画一条分割线把左边切成白天、右边切成黑夜，更不允许放一个左右拉动的对比箭头打破沉浸感！主题切换必须是**全场景光影的整体呼吸过渡**。

### 3.2 光学对齐与「修错不毁好」（Surgical Alignment Without Regression）
- **跨页共享标尺（Shared Spatial Ruler）**：
  - 顶部导航胶囊、右上角工具栏、底部胶片输入栏、右侧角色伴读槽位在 `S1–S9` 所有页面切换时，**必须共享同一套 CSS Grid / Token 坐标**，严禁切页时按钮乱跳、边距忽宽忽窄。
- **光学对齐优先于机械数值（Optical Alignment Over Math）**：
  - 图标与文字混排、胶囊内边距、播放三角号居中、圆角嵌套（外圆角 $R_{out} = R_{in} + Padding$）必须由主代理亲眼看图校对视觉重心。
- **保护已有对齐成果（Do Not Break What Works）**：
  - 修改任何样式前，先盘点当前页面哪些区域已经对齐良好。只对错位组件做精准外科手术式修复，严禁推倒重来式地全局乱改 CSS 导致已对齐区域退化。

## 4. 第四层（灵动交互、OpenUI 与文案层）：全场景可打断拖拽与让布局说话

### 4.1 SwiftUI 级可打断弹簧动效与全场景直接操作（Direct Manipulation）
拖拽与直接操作是「在场」破除死板程序感的核心刚需。拖动吸附、空间让位等适合弹性的动作采用**保持速度连续性的可打断弹簧**；阅读定位、透明度、真实进度和精密作图分别用合适的跟手映射或曲线，不能全部套弹簧。用户操作立即接管过渡，业务完成不依赖动画结束回调：

1. **角色跨锚点自然拖拽**：先区分“移动伴读位置”与“角色真的走过去”。同一支撑面内可沿已校准切线调整；跨椅子/窗台须有合法姿态过渡或设计过的切镜，不能平移一个坐姿穿过空气。非拖拽用户可通过位置选项完成等价操作；轻语是可选反馈。
2. **学习/资料工作台无级分屏拖拽**：拖动分屏分隔线时，左侧 PDF/题面与右侧对话/角色舞台实时流式重排，松手自动吸附至舒适阅读档位。
3. **日程时间轴卡片拖拽与试放（Preview & Commit）**：从聊天建议卡或待办区直接拖入日程时间轴，实时显示半透明试放幽灵块（Ghost Preview）、前后转场/休息留白保护区与冲突温和提示；试放不直接写死数据库，确认后落位，随时可一键撤回。
4. **笔记选段与跨模块摘录拖拽**：在 PDF 或对话中划选一段话，直接拖入右侧笔记卡或底部书签托盘，自动携带真实来源页码、时间戳与精确引文锚点。
5. **内联校园地图拖拽与无缝展开**：聊天流中的内联地图支持直接拖拽平移、点击地点胶囊高亮路线、一键平滑展开为全幅校园地图，且返回时保持同一相机视角与选中状态（不重建新实例）。

### 4.2 OpenUI 作品化生成与「让布局自己说话」（Ablation Test）
- **把设计稿中的惊艳创意 100% 变成真实可交互组件**：
  - 如标杆图中的**三角钢琴声学/乐理互动卡**、**可拖拽采样点的动态音频波形/函数图像卡**、**带手绘微缩地标的校园寻路卡**、**底部胶片式记忆书签托盘**，必须全部写成有真实状态回流的活组件（OpenUI `PresentationView`），绝不用静态贴图糊弄。
- **文案消融测试（Ablation Test）与工程黑话清零**：
  - 如果拿掉冗余说明后操作仍可发现，删掉重复解释；保留必要标签、键盘提示、可访问名称、错误恢复和真实状态。不能以“少文字”制造猜图标考试。
  - **普通体验不朗读内部术语**：聊天、工具栏和反馈不用 `SceneSnapshot`、`CAS revision`、`BGE`、`sidecar`、SHA 等替代人能理解的结果。按需展开的开发诊断可以保留真实字段；课程分数、页码、人数等有业务意义的数值不得因形式像 `3/3` 被误删。

## 5. 第五层（工程契约、主从协同与验收层）：单一权威底座与零「买家秀」交付

### 5.1 前后端共同在场与单一权威 Owner
- **Renderer 参与共同体验，写入归原 Owner**：前端负责可见场景、语义锚点、手势与注意让位，并把明确操作回流心智；所有 SQLite 读写、凭据、模型调用（Hermes / Luna）、文件解析由 Electron Main 持有，通过 `preload.ts` 有限 Bridge 通信。权限边界清楚不等于设计割裂。
- **单一数据源与稳定 ID 流转**：记忆归 `MemoryService`；`memoryInquiry / recall_experience` 是检索调查入口，不是第二记忆库。笔记归 `NotesService`，资料归 `MaterialService`，日程归 `CalendarService / NativeAgendaService`，地图归现有 `mapService` 与共享地图契约。跨模块携带 `stableId + expectedRevision + sourceAnchor`，由原 Owner 核验。

### 5.2 主从代理协同铁律（Main Agent Helms, Subagents Parallelize）
- **主代理（你）必须亲自做的事**：
  1. 亲读核心原话与设计文档，亲看任务约定的代表图和拟上线的新资产；完整观看拟使用的动态样片，不能把联系表当作运动验收；
  2. 亲自制定审美标准、角色动作矩阵与破界创新方案；
  3. 亲自启动并操作真实桌面端界面，逐页比对设计稿与实际渲染画面。
- **子代理（Subagents）并发攻坚的事**：
  - 严禁派子代理做“数文件、算哈希、列目录”等机械凑数杂务。
  - 协作服从用户当轮范围。本轮仅公开 idea 调研可以使用子代理，仓库精读、设计、修改与审校由主代理完成。后续获准并行实现时按独占文件与完整故事拆分，不强制人数、代码占比或返工轮数；交付质量不以改动行数衡量。用户确认本地已包含云端时，不额外合并旧分支。

### 5.3 十条「一票否决」验收红线（触犯任一条即打回重做）
1. **无魂死板**：文案像客服模板、画面像后台管理面板、角色毫无性格区分。
2. **只做点名事项**：没有主动挖掘设计稿隐含功能，或把有价值的创新写成“后续建议”。
3. **人物接触或身份崩坏**：非构图意图的断肢、无支撑漂浮、手与物件穿插、影子不跟接触关系、失败图污染母版。
4. **内置角色失真或自定义被覆盖**：内置十角色出现违和成熟写实风、身份漂移；或把用户自定义形象强行替换成内置角色。
5. **绿色 UI 或昼夜分割线**：出现绿色系 UI 控件/背景，或出现带左右箭头的昼夜硬分割画面。
6. **跨页跳动或破坏已有对齐**：切页时导航/输入栏跳动，或修 A 页面时搞坏了原本对齐的 B 区域。
7. **假交互或死贴图**：拖拽无试放/无可理解反馈/不可打断，视频冒充可互动角色，或钢琴/波形/地图没有真实状态。
8. **工程黑话外露**：普通相处界面用“已接通/待验证/哈希值”等内部词代替实际结果。按需诊断保留必要字段，课程分数、页码、人数等业务数值照常呈现。
9. **前后端串味或假数据**：前端自造第二状态库、跨模块拖动丢失原来源 ID 或覆盖未读分支改动。
10. **卖家秀退化为买家秀**：未经过主代理真实运行界面与原设计稿 1:1 并排视觉核验就宣告完成。

## 6. 动态导演的强制工作流

### 6.1 先写一段相处，再写组件

每个阶段必须设计一个完整连续故事：用户来时正在做什么 → 共同对象出现 → 她如何关注和参与 → 用户改主意 → 她怎样让位 → 真实结果留下什么 → 离开后如何接续。逐拍写出 **可见变化、权威事件、来源锚点、通道 owner、中断与降级**，不能只交“加呼吸动画”“增加主动性”。

“心智—状态—动效—在场”闭环中的三种时间分别处理：事实时间由原 Owner 决定；交互时间由用户输入决定；表演时间由前端编排。表演不能延迟用户提交、假装外部行动完成，或把看见等同于接受。

### 6.2 七种动作语法，共用一套相处逻辑

1. **看向**：依据当前文本/物件锚点形成共同注意，不默认追踪鼠标或分析面部情绪。
2. **让位**：用户选字、打字、写笔记、放大讲义时，角色、纸页、光和声音共同退让，输入焦点不动。
3. **递出**：先准备再呈递，用户取走才展开；新输入到来可停在桌边。
4. **摊开**：同一个对象扩展为可操作视图，保留身份、选区与返回位置。
5. **收回**：撤回建议、纠正下一行、取消动作时，手势、正文、音频与后续意图一起更新。
6. **回来**：恢复已有页码、笔迹、路线或未完话题，只强调真正发生的变化，不重播欢迎演出。
7. **同乐**：节奏、弹奏、故事或轻轻点一下“嗯？”的回应来自当下互动，不用随机动画假装懂你。

每种语法都要有静音、键盘与低动态等价方案。动作参数和角色差异见 [06-presence-orchestration.md](references/06-presence-orchestration.md)。

### 6.3 GPT Image × Gemini 网页版 × 可交互代码

执行顺序：角色护照 → 场景/姿态有效矩阵 → 同景母版与分层 → 导演包 → Gemini 网页版样片 → 完整动态审核 → 选择代码重建路径 → 真实界面中断验收。

Gemini 的当前可见能力是本轮生成依据；历史模型名称、API 字段与固定秒数不冒充网页能力。视频先标为 reference-only，只有明确适合的环境循环或受限片段才部署。文字、选区、业务对象、手势接管与状态回流必须由实际代码承担。详见 [07-gemini-and-asset-production.md](references/07-gemini-and-asset-production.md)。

### 6.4 动效不是常驻噪声

同一帧每个身体/眼神/手/纸/光/声音通道只有一个写入者。用户输入、取消、隐私失效优先于表演。屏幕隐藏时停止无意义解码与调度，回来重新核验有效版本，不补播过期动作。安静和静止也是被设计的状态；不要让呼吸、眨眼、漂浮、光晕、打字机与背景视频同时抢注意。

### 6.5 一次交付必须包含什么

交付连续故事、逐拍分镜、真实入口与待新增契约、资产适用矩阵、正常/纠正/失效三条轨迹、实际操作证据和未完成项。文档任务验证文档与链接；代码任务按风险验证机制与真实界面；生成任务验证素材。不得用重复测试或截图数量替代尚未解决的具体问题。
