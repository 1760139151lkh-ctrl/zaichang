# 在场：大学生的人与环境模型、128 个情境与检验方法

## 使用范围与材料性质

这份材料为「在场」的主动生活助理提供需求模型和合成检验情境。它面向不同学校、年级、专业、居住方式、身体条件、经济条件和生活取向的大学生。所有编号场景均为人工构造的假设；它们不是小灰灰的真实经历，也不代表任何大学的通行规则。场景中的期限、制度、营业时间、价格、天气、课次和地图信息都必须通过对应证据夹具提供，不能直接写进正式产品。

配套文件：[128 场景可读版](08-SCENARIOS-128.md) · [结构化场景数据](scenarios/scenarios.json)。数据元信息明确设置 `synthetic=true`、`is_user_profile=false`。

这里的“对人建模”是建立一种可用、可修正的理解：此人现在关心什么、正在经历什么、哪些选择真正可行、哪些信息还不知道，以及助手此刻能怎样帮助。模型始终允许人改变主意、保留空白、作出尚未解释的选择。它不宣称穷尽一个人的内心，也不从少量行为推断固定性格或健康状态。

本材料的概念划分属于针对本项目的设计综合，不冒充经过验证的心理学量表。用户本轮需求，以及所附记忆讨论中关于证据、有效时间、观察与解释、示例与本人事实的区分，构成这里的设计约束。其他框架与研究的来源核查由总研究包统一提供。

## 1. 一个情境要把哪些事情接起来

大学生的生活经常同时包含学习、关系、照顾自己、探索方向、处理手续和享受生活。例如，朋友约今晚吃饭是否值得答应，不能只查“晚饭时有没有课”。还要知道这个邀请是否已经答应、是否想见这位朋友、明天展示准备到哪里、饭店是否需要长途往返、支出是否舒服、今天是否已经疲惫，以及用户有没有把那段时间留给自己。

这些信息不需要一次性全部获取。助手只需要在具体决策中找出真正影响选择的部分，并把剩余的不确定性留在它应在的位置。已有可靠信息足够时就直接帮助；一个缺口会改变结果时才问一句必要的问题；当现有状态没有形成有用的行动机会时，就让生活继续。

### 1.1 人及其生活的十二个互相作用的维度

| 维度 | 需要理解的对象 | 在判断中承担的作用 | 证据边界 |
| --- | --- | --- | --- |
| 身份、角色与生活阶段 | 新生、在读、交换、毕业准备；组员、室友、家人、兼职者等并行角色 | 判断一件事为什么与此人相关，以及同一时间有哪些责任 | 不凭年龄、专业、性别或学校给出人格、价值观和家庭条件结论 |
| 当下重视的事情 | 学会某物、守住承诺、恢复精力、陪伴朋友、获得收入、探索、玩乐、独处 | 解释当前选项之间为什么需要取舍 | 用户明确说的取舍与系统猜测分开；不同人的目标并无统一排名 |
| 目标、愿望与探索 | 想试一次、持续目标、暂时暂停、未来打算、正在比较的方向 | 给长期事情留位置，同时控制新增负担 | “想做”“考虑”“答应”“完成”具有不同状态；暂停不是失败 |
| 承诺与进行中的事项 | 课程、作业、实验、考试、社交约定、申请、等待回复、零散想法 | 找到真实期限、依赖、责任人和可协商空间 | 正式规则需有机构、学期、课程或事项的适用范围；草稿不等于对外承诺 |
| 时间与生活节奏 | 逐周课次、假期、临时调课、实际开始结束、专注块、休息与缓冲 | 判断什么时候可以启动、能否收尾、何时需要决定 | 空白日历不保证有可用精力；预计结束时间不同于实际结束事件 |
| 身体与可用精力 | 用户自述的饥饿、疲惫、不适、运动愿望；经授权的设备记录及其覆盖情况 | 决定是否适合移动、学习、运动、休息，以及是否需要正规支持 | 缺测不同于异常；设备数据不直接产生诊断；当次状态不自动写成长久画像 |
| 学习与创作的过程 | 当前卡点、已有尝试、前置条件、任务类型、工具材料、发现边界 | 选择能接上当前进度的帮助，保护已进入的思路 | 独立完成、跟着做、读过和助手代做分别记录；不把看过当掌握 |
| 关系、归属与边界 | 邀约、互助、共同空间、分工、感谢、拒绝、需要陪伴或独处 | 看清与他人的协商成本、信任和公平，允许社交具有自身价值 | 只使用授权材料；不猜他人感情和动机；对外消息由明确授权控制 |
| 空间、移动与可达资源 | 当前地点及精度、目的地、入口、路线、交通、天气、开放时间、材料位置、无障碍需求 | 判断方案在现实中能不能执行，自动让地图成为情境中的工具 | 建筑坐标不等于入口证据；位置过期不能冒充当前定位；距离短不保证可走 |
| 金钱、物品与设备 | 已到账资金、已承诺开支、预期收入、材料、证件、电量、网络与设备兼容 | 暴露时间以外的真实代价，避免计划到了却做不了 | 预算由用户选择；模糊交易待核；没有购买意愿不生成购买目标 |
| 制度与数字能力 | 校园规则的版本和作用域；已接入工具、权限、可读写范围、实时性与失败状态 | 区分事实能否获得与动作能否完成，支持插件逐步接入 | 未接入、无权限、过期、暂时失败、确实为空是五种不同情况 |
| 表达风格与互动关系 | 助手角色预设、称呼、温暖程度、简洁度、调侃、鼓励方式、主动闲聊设置 | 让同一可靠判断以用户舒服的方式被接住 | 助手的人格设定与用户画像分开；当次要求可以覆盖默认设置 |

这些维度之间存在真实依赖。天气影响可选交通，交通影响能否赴约，赴约是否值得还取决于关系与当次意愿。疲惫可能让原本可行的学习安排不再舒服，但用户也可能因为很期待一次见面而愿意出门。模型需要保留这些原因，而不只记住最后选择的地点或活动。

### 1.2 同一事实必须区分现实、观察、理解与选择

| 层次 | 例子 | 后续可以做什么 |
| --- | --- | --- |
| 现实中的情况 | 学生已经提交作业，学校页面仍未同步 | 现实未必直接可见；不能假定某个接口完整代表现实 |
| 有来源的观察 | 用户发来本次作业的成功回执；页面更新时间早于提交 | 对齐同一事项，保留双方时间与来源 |
| 当前理解 | 本次作业已有提交证据，后台同步待完成 | 解除催交，仍能解释为什么页面不同 |
| 用户意图与授权 | 用户要求不要再提醒本次作业 | 结束相应提醒，保留必要的完成状态 |
| 实际动作和结果 | 本次提醒被撤回；用户之后查询能看到回执 | 只有动作回执或可验证状态才能支持“已经处理” |

这个区分同样适用于“朋友没回复”“用户整天没离开宿舍”“临时改地点”“下周才生效的新住处”。从行为到原因、从愿望到承诺、从查询到执行、从数据缺失到现实不存在，都需要额外证据。

## 2. 从一次情境到一次合适的主动行为

### 2.1 主动性包含六种可以被观察的结果

主动性应体现在助手能否自己识别相关事件、接上未说完的事情、找到有用时机、完成已授权的小事，并处理后续变化。用户不需要先说“请调用地图技能”。

| 模式 | 适合出现的时刻 | 用户侧能感受到的结果 |
| --- | --- | --- |
| `offer` 建议或陪伴 | 有具体收益，尚需用户选择 | 一个能理解、可拒绝的下一步、机会或回应 |
| `ask` 必要询问 | 一个未知会改变当前决定 | 只补关键缺口，同时先获得已有可用帮助 |
| `act` 授权内完成 | 请求或既有授权已经覆盖这次动作 | 真实完成并有可查结果；失败时准确说明范围 |
| `wait` 等待 | 事项仍有效，但现在没有必要打扰或无法确定 | 该回来时能接上；没有无意义的重复催促 |
| `silence` 静默 | 候选没有足够价值，或此刻用户更需要完整生活 | 课堂、休息、关系相处和自由时间得到保留 |
| `correct` 修正 | 新事实、用户纠错、撤销或权限变更影响已有结果 | 旧误解和它造成的后续安排一起停止生效 |

六种模式的比例不是产品指标。一个人连续几小时专注时，静默可能是合适的；一个人在主动倾诉或探索周末计划时，较多自然互动也可以是合适的。固定每天发几条、固定多久不回复就降低关注，都会错过具体情境。

提醒还需要保留其承诺来源。用户明确设置“下午两点提醒我买文具”，就已经约定了投递时刻；助手不能因为觉得学习更重要而替用户取消。系统自行发现的采购机会尚未承诺何时展示，则可以等到专注结束。随课程改期而自动更新的出发建议，需要原有的随事项同步授权。已有授权覆盖的调整可以直接完成，无需每次重复询问；授权不覆盖的独立闹钟、外部约定和已确认日程应保留原本语义。

因此，场景 S001 的静默针对未承诺投递的采购候选；S026 的更新针对已获随活动同步授权的自动出发建议；S127 的合并针对三个未承诺投递的主动候选。这些结果都不构成助手可以随意改闹钟的通用规则。`offer` 和 `ask` 生成的方案同样不会自动覆盖已确认日程，只有本次或已有适用授权允许时才落实。

### 2.2 先判断有没有值得改变的事情，再决定怎样说

每个候选要形成一段可以重建的理由：

1. **发生了什么变化？** 是真实新事件、接近决策时点、用户发起请求，还是同一条信息的重复同步？
2. **与此人哪件当前有效的事情相关？** 一次提醒应能对应愿望、承诺、需求、当下情绪或用户选择的陪聊方式。
3. **此时仍有哪些可行选择？** 同时考虑时间、移动、物品、精力、金钱、对他人的承诺及真实能力。
4. **现在说或做，会改变什么？** 是保住最后选择机会、减少准备负担、报一个可信好消息，还是只多占一次注意力？
5. **哪些结果已经被用户决定或授权？** 可以直接完成的就完成；需要用户取舍的就把代价说清楚。
6. **结果以后怎样保持有效？** 取消、改期、已完成、数据过期、权限撤回和跨设备确认都应改变后续行为。

这六个问题用于构建判断，不要求向用户显示检查表。学生最终看到的可以只是一句：“明早换到另一幢楼了，我把路和出门时间一起放好了。”

例如“十二天还需三次运动，明天可能下雨”只产生一个值得查看的机会。还要检查之后是否存在可用窗口、任务规则是否适用、天气不确定性、身体自述、场地和个人偏好。若后面仍有多个窗口，就不能推出“今天必须跑”。如果唯一剩余窗口也不适合身体状态，助手需要诚实呈现约束和正规替代途径，而不是把运动任务凌驾于人之上。

### 2.3 温暖人格的作用位置

人格设置至少可以分别调节称呼、温暖程度、简洁程度、调侃频率、鼓励方式、主动闲聊和角色表现。它们可以组合成几个默认预设，也允许用户分别修改。缺失的角色细节可以以后补，不应阻止已有基础人格先使用。

助手从互动中形成的理解应保留证据和条件，用户手动设置应清楚显示其作用范围。比如“平时直接一点”是一般设置，“今天累了，温和一点”是本次覆盖，“以后不用那个称呼”则是新的长期设置。角色活泼不会使未知考场变成已知，也不会让一项未授权消息获得发送权限。

表达范例只是一种可能的口吻。可以简洁温和：“今天这次取消了，安心休息。”也可以稍活泼：“好呀，今晚给自己留点空白。”检验要看它有没有接住真实语境，而不是有没有使用某些固定词语。角色的亲近感可以来自具体记得、适时帮忙、尊重选择和自然陪伴；不需要编造助手的生理需求、让用户照顾它或营造排他关系。

## 3. 场景覆盖矩阵：为什么是这 128 条

这批场景按 **16 个主领域，每个 8 条** 组织。主领域只用于导航，实际情境都交织多个维度。每条至少包含三个相互影响的事实，并明确一个目标冲突、证据来源、预期动作、表达示例、缺失信息或反事实以及可观察验收。

| 主领域 | 编号 | 所覆盖的独立困难 |
| --- | --- | --- |
| 学习过程与注意力 | S001–S008 | 连续思考、短空档、求助与发现、课堂等待、分工未知、设备窗口、休闲自主、计划原因复盘 |
| 考核、作业与有后果的期限 | S009–S016 | 改考场、提交回执与延迟、确认写入、缺考场等待、不同考核形式、跨端重复、日期冲突、正式取消 |
| 长期目标、探索与发展 | S017–S024 | 低承诺探索、方向未知、暂停、前置条件、作品整理、等待回复、可信成长、改变方向 |
| 日程协商与突发重排 | S025–S032 | 临时机会、依赖更新、社交意愿、授权写入、缓冲、结束不确定、减负、撤销 |
| 社交邀请、表达与边界 | S033–S040 | 赴约取舍、当次意愿、拒绝草稿、尊重真实协商、新关系邀请、不催回复、重复邀约、条件意向 |
| 同住、归属、互助与关系责任 | S041–S048 | 新环境归属、共同空间、公私时机、团队公平、独处、感谢、互助、关系事件结束 |
| 空间、出行、天气与可达性 | S049–S056 | 跨校区、自然问路、无台阶需求、封闭更新、GPS噪声、预报波动、低电量、保留户外体验 |
| 身体需要、休息、运动与自报健康 | S057–S064 | 饥饿、午休、舒适习惯、任务余量与天气、不佩戴设备、现实照护、取消、指标误用 |
| 情绪自述、陪伴与主体选择 | S065–S072 | 先听、减负选择、禁止位置归因、暂停分析、具体成长、恢复掌控、自然转场、玩笑误记 |
| 预算、兼职与资源取舍 | S073–S080 | 社交开销、到账时点、浏览误判、账目整理、申请机会、促销等待、交通成本、交易纠错 |
| 生活事务、设备与材料准备 | S081–S088 | 搬运负担、小记事本、排队时机、设备兼容、离线缓存、材料位置、完成同步、家务模板 |
| 校园制度、手续与公共机会 | S089–S096 | 逐周课程、跨校政策、维护、临时通知、材料草稿、消息过滤、开放探索、规则待确认 |
| 休闲、兴趣、创作与好消息 | S097–S104 | 小惊喜、不剧透、无聊、灵感捕捉、群体决策、兴趣时间、自由空白、庆祝 |
| 可调人格、称呼与互动风格 | S105–S112 | 组合设置、当次覆盖、活泼与时机、跳过设置、缓存更新、真实等待、未完成预设、闲聊授权 |
| 证据、记忆、纠错与信息边界 | S113–S120 | 引语主体、未来生效、文件示例、删除、条件化原因、临时行为、时区、转述去重 |

### 3.1 关键交互覆盖

| 交互或边界 | 代表场景 | 为什么足以区别于简单换课名 |
| --- | --- | --- |
| 时间 × 地点 × 物品或设备 | S049、S055、S081、S084、S086 | 即使日历不冲突，交通班次、电量、箱子、接口或证件也会使方案不可执行 |
| 个人愿望 × 社会承诺 × 可协商空间 | S027、S033、S039、S047 | 已答应、被邀请、想去、愿意改期四种状态导致不同动作 |
| 身体自述 × 天气 × 期限余量 | S059、S060、S061、S063 | 同一运动目标可能对应建议、询问、等待或撤销，不能只检测晴天 |
| 注意力 × 主动性 × 人格 | S001、S004、S029、S107、S110 | 性格活泼也要能等待；后台真的在工作也不需要不断发进度 |
| 新证据 × 有效时间 × 派生状态 | S009、S016、S026、S092、S114 | 新版本不能只改文字；路线、提醒和未来生效范围也会变化 |
| 观察 × 原因 × 长期画像 | S008、S067、S072、S117、S118 | 相同行为可能来自施工、玩笑、临时疲惫或偏好，证据支持的范围不同 |
| 多设备 × 子代理 × 撤回与权限 | S032、S109、S116、S121、S122、S123、S128 | 局部正确仍可能重复打扰、复活旧计划或在撤权后继续工作 |
| 成果 × 兴趣 × 无任务时间 | S007、S023、S097、S100、S103、S104 | 助手要能记得愿望、报好消息和支持庆祝，也要允许什么都不安排 |

以上矩阵只表明已覆盖的关系，不能证明所有组合都覆盖了。场景专门包含静默和等待的 **43 条**：静默 25 条、等待 18 条。其余为建议或陪伴 38 条、必要询问 16 条、授权动作 14 条、修正 17 条。这个分布用于迫使评估看到“不打扰也可以正确”，不是规定正式产品 43/128 的机会必须静默。

### 3.2 每条如何成为有用的验收，而不是表演台词

每条 JSON 记录均包含以下固定字段：

| 字段 | 类型 | 含义 |
| --- | --- | --- |
| `id` | 字符串 | S001 至 S128，引用时保持稳定 |
| `domain` | 字符串 | 主领域导航 |
| `situation` | 字符串数组 | 至少三个相互作用的事实 |
| `goal_conflict` | 字符串 | 为什么需要判断，哪些诉求发生竞争 |
| `trigger` | 字符串 | 为什么此刻进入判断，而不依赖用户手动叫技能 |
| `evidence` | 字符串数组 | 判断所需的真实观察或夹具，不能由助手自己的解释替代 |
| `expected_action` | 对象 | `mode` 加 `description`，明确何时行动、询问、等待、静默或修正 |
| `example_utterance` | 字符串 | 可选语气范例，静默场景也明确不推送 |
| `missing_or_counterfactual` | 字符串 | 哪项未知仍待查；改变一个关键事实后判断如何翻转 |
| `acceptance` | 字符串数组 | 用户侧结果或系统可观察状态，不以逐字匹配文案判通过 |

[结构化场景数据](scenarios/scenarios.json) 的顶层还包含场景性质、全局假设、模式定义、统计和 `scenarios` 数组，适合后续导入检验工具。它不包含账户凭据、真实学生资料或生产规则。

运行检验时，应先准备原始证据及工具状态，再触发该事件，观察助手实际产生的动作、消息、状态变更与副作用。把预期答案直接塞进模型输入只能检查复述，不能检查情境判断。对于静默场景，需要观察一个明确事件窗口内没有产生对应通知，同时事项状态和未来唤醒条件仍然正确；不能只看聊天界面没有文字。

每条至少应做一个最小反事实：只改变记录中指明的关键事实，其余保持相同。S060 可以把后续仍有多个可用运动窗口改成仅剩一个已证窗口；S049 可以把位置改为过期；S121 可以把两个相似文案改为不同场次。预期判断需要随这项变化而改变。若模型无论证据怎样都给同一句关心话，场景没有通过。

涉及动作的记录还需要区分四个层次：理解正确、决定正确、工具调用成功、后续状态一致。用户日程草稿写入成功不等于共同预约已改；地图显示路线不等于入口事实已核查；生成拒绝回复不等于消息已发送。最终验收应说明证据停在哪一层。

### 3.3 一组有代表性的演示路径

实际演示可以沿同一个学生的一天串起 S004 → S027 → S049 → S009 → S121 → S032，但这些编号不意味着六条在真实数据中必然属于同一个人。演示夹具需自行统一人物、日期和承诺，避免把互相矛盾的前提拼接成“全能演示”。

另一条可以围绕一个持续目标：S017 → S023 → S019 → S024。它检验能否从探索开始，看到可证成长，尊重暂停，最后接住改变方向。第三条可以围绕一次误解：S118 → S117 → S116，检验观察、纠错、删除及派生缓存失效。它们分别检查一天内协作、较长时间的目标演变，以及错误理解的修复。

## 4. 场景集还没有替代什么

这 128 条提供足够广的第一轮设计压力，仍需在实际产品中验证输入来自哪里、数据的准确度如何、什么时候打扰最合适以及用户是否觉得被理解。语气样例尤其需要真实学生体验；预设“温暖”并不能证明用户感觉温暖。

后续应根据真实使用扩大以下范围：不同学校与年级的制度、残障和暂时行动不便的具体可达性、家庭照护与异地生活、语言文化差异、住宿关系、经济困境与求助渠道、严重健康或情绪危机的正规支持路径、无智能手机或长期离线场景，以及多人共同计划中的实际授权模型。这里没有用少量案例宣称这些问题已被解决。

更复杂的三方冲突、连续数周变化、工具恶意或失真输入、并发编辑、权限切换和通知送达失败，也需要真实系统中的集成检验。可从现有场景派生有意义的组合，但新情境必须引入不同机制、取舍或边界；只换课程、地点、天气名称不会形成新覆盖。

完成这轮场景理解后，Codex 应能说明：某项帮助为什么此刻对这个学生有用，依据来自哪里，哪些信息仍未知，用户可以怎样改变选择，以及事情变化后旧结果如何停止生效。界面上的热情、地图入口和后续插件由这一份具体理解支撑。
