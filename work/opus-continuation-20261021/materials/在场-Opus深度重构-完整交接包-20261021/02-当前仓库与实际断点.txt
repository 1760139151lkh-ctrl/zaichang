三、请沿这条真实链理解产品
原聊天输入 App.tsx
→ preload / main IPC
→ Harness 的原话控制、范围和本轮准备
→ ContextCompiler 的原话、当前事项、允许来源、引用与能力
→ runtime/hermes.ts 与 Python sidecar
→ 锁定 AIAgent 主循环
→ 宿主模型传输和工具注册
→ CapabilityBroker / 领域服务 / 受控子任务
→ 工具观察回到同一主助手
→ 必要的结果与来源复核
→ 同一消息的正文、Scene、View 和后续对象
→ renderer 里的原聊天、共享地图、纸页与输入引用。

后台从有效托付、业务变化日志或时间节点进入 Attention / OpportunityScheduler，再由同一 Harness 判断和准备。它与前台共享真实状态及执行边界，不是另一个无记忆的定时聊天机器人。

五、静态代码定位到的具体接缝

C01 · 默认有形象，文字人格可能从空白开始
src/shared/persona.ts:88–100 的 emptyCore 从 custom 与空文字起步；migratePersona/default 在约 274–290。src/renderer/companion.tsx:52 的默认外观是 mio。
这是两个独立状态的静态事实。它提示应测试“全新用户看到一个角色，但真实模型到底收到哪份人格”的路径；并不说明所有用户当前都没有保存角色，也不意味着应强制把所有人改成同一个人格。

C02 · 交互默认值可能收紧了亲近和主动
src/shared/interaction.ts:11 为 natural / humor none / depth adaptive / initiative prepare / meaningful_change。请观察这些指引与角色核心叠加后的实际提示。用户选择活泼人物时，“none”如何解释，预设是否同时给合适的交互起点，都需要核实。
src/shared/types.ts:381–382 的天气和提醒默认关闭，请检验初次连接流程能否让用户轻松理解和启用真正想要的能力。默认关闭不授权后台偷偷打开。

C03 · 底层支持文本增量，主执行桥却没有传回调
provider.ts:233–244 接受 onText，约 379 处理 delta.content。
harness.ts:1172 调用 complete(..., undefined, requestOptions)。约 1214 的前段发布，在主模型完整返回且还有 tool_calls 时才调用 rhythm.offer。
sidecar.py:309–328 先等待 model.request 完成，再在 stream 模式把整个 assistant 包成一个 SSE chunk。
据此可以确认，当前这段主执行链没有逐 token 接通用户可见正文。它仍可在完整的工具轮之间发布内容，不能概括为“完全没有过程交流”。请对照时序追阻塞点，也保住正文、动作完成声明、取消和最终复核的区分。

C04 · 自然的短回应被现有节奏指导收窄
conversation-rhythm.ts 的指导允许先给实质帮助，但明确排除“正在检索”等占位，只在有新实质内容时接话。这个初衷能防假进度，却可能把有意义的关系性回应一并压掉。
rhythm.finish 只有完整前缀相同时避免重复，否则把前段和最终文本拼接。语义上的复述未由这个逻辑识别。这是值得复现的重复风险，不能没有运行就断言所有答案都会重复。
请让真实的接话、内容增量和最终结果有清楚事件语义，不靠删除词语或再加一个改写模型。

C05 · 准备、聊天与通知还没有等同于同一个主动交流闭环
attention.ts 约 801 处，initiative=prepare 时 notify 会转为 prepare。choice=notify 需要真实新价值与 local_notification 渠道。后台注册工具白名单在 coordinator.ts 约 1644：包括查询、原文、部分管理与 decide_help 等，不包含 curiosity_invitation 和 write_reflective_letter 这些前台创作工具。
这表明“能在前台写来信/带新鲜事”和“后台真的能主动带来这些内容”不是同一能力。请追任务授权、工具白名单、结果落地、消息追加、曝光/去重与用户接续；不要简单把整个前台工具集放进后台来掩盖职责问题。

C06 · 系统通知当前使用固定文字
actions/reminders.ts 约 276：标题为“在场 · 到约定的时间了”或“在场 · 有一处变化”，正文为“打开在场查看详情。”
这是固定通知投递代码，不是角色自己写的消息。请设计能承载角色与真实结果的私聊内容，再按通知预览设置给合适投影。锁屏是否展示细节由用户选择，不能把个性化理解成在锁屏曝光全部私文。

C07 · 动态教学明确局限于 quadratic
shared/explorable-study.ts:18–22 注释与 schema 明确只接受 quadratic；runtime/explorable-study.ts 沿同一有限模型校验。现有值、曲线、切线由同一声明计算，是值得保留的精确性。
波叠加、相位、时间动画这类需求超出该契约。请把“可扩展表达能力”作为研究对象，而不只增加一个 sine 专用分支。如何组合数学、解释、滑条、动画、图表与原问题引用，是后端与渲染共同的工作。

C08 · UI 有来源门，也有真实失败历史
CURRENT_STATUS 第七批记载真实正常日历流程先经历 scene_unavailable，随后出现双 Scene 与正文整表重复，后来修到单次读取及原对象续问。它说明模型工具返回、Scene 身份和呈现去重的接缝曾真正影响体验。
这些是项目历史记录，不是本轮重新执行。请回当前入口检查同类风险，特别是新领域、工具重复、历史引用和实时更新，别只用脚本手动投影出漂亮页面。

C09 · 提示已经很长，不能继续只往末尾加规则
prompts/system.md 在本基线共 82 行，很多是很长的密集规则段；实际提示还叠加 persona、interaction、conversation rhythm、当前范围和专用任务指引。
冷淡、重复和保守的确切成因需要实际提示与时序复现，不能单凭字数判断。请测量实际进入模型的各段，检查冲突、重复、职责错位和规则叠加，给出整理前后的真实可观察差异。

C10 · 一些源码能力尚未开放，不宜列成已经可用
PROJECT_NAVIGATION 明确 storySetting 的正常工具入口已冻结，没有可用 StorySettingView。BGE 候选也有默认不注入的现状。若本轮要启用，请完成真实消费路径和对应验证；否则保留清楚状态，别让能力清单继续写得比产品更大。

六、截图反映的体验问题，与根因分开看
在场截图显示：语气反复强调未改动；讨论中以“先停在讨论层”定性；原笔记只被看到片段，答复离具体疑问越来越远；路线/天气调查遇到读取限制后把后续责任推给用户；人物在部分画面压到正文或表格。
这些是观察，足以定义待修体验。它们没有单独证明是哪一条提示、哪个模型或哪个函数造成，实施时请从最早可见分歧定位。

参考产品的猫形象有持续自称、称呼和语气，进入建议时仍有识别度。借鉴的是人格贯穿交流和开口的轻松感；截图里的特定建议、占卜功能或泛泛夸赞，不自动成为在场的功能或正确答案。
