## 一、先看别人怎么做：真正值得借鉴的不是产品名称，而是机制

### OpenAI：用户看到的记忆摘要，并不等于全部记忆

目前 OpenAI 的公开说明已经不只是过去的“Saved memories＋聊天历史”两项。它描述的是：根据过去聊天等上下文持续更新的综合记忆，而用户看到的 Memory summary 只是一个高层视图，并不包含系统可能利用的所有细节；用户可以修正记忆，也可以查看部分个性化来源。**但它没有公开完整的提取算法、存储结构和召回策略。**([OpenAI Help Center][1])

对你的启发是：**展示给用户的个人简介，与后端真实保存的记忆，必须分开。** 简介应当可读，但不能成为唯一存储。

### Hermes：小型常驻记忆，加按需读取的历史

Hermes 当前内置记忆主要是两个有容量限制的文件：`MEMORY.md` 和 `USER.md`。它们在会话开始时作为固定快照进入上下文；另有 SQLite 会话记录和全文搜索，用来找回没有写进常驻记忆的细节。文档还描述了回合后的后台复查，以及可选的记忆写入审批。([Hermes Agent][2])

这个组合很实用，但对你的产品而言，**这两个文件适合做“常驻摘要”，不适合承担完整个人记忆的唯一事实来源。**

### Letta：让记忆可检查、可修改、可追踪版本

Letta 当前文档介绍了基于 Git 的记忆文件系统 MemFS，以及后台回顾对话、整理记忆的 dreaming 机制。值得借鉴的是：记忆不只是文本生成结果，也是一种能够检查、修改、整理和追踪变更的状态。([Letta Docs][3])

### Graphiti：把“什么时候成立”作为记忆的基本属性

Graphiti 把实体、关系、事实与时间一起存储，支持事实失效、历史上下文，以及结合全文、语义、时间和关系的检索。它的关键启发不是“必须使用图数据库”，而是：**用户事实会变化，不能只留下一个脱离时间的最终值。**([Zep][4])

另外，Mem0 当前文档把自动提取和存储做成了方便调用的接口，但其 `add` 文档明确描述为新增式存储。因此不能看到“自动记忆”四个字，就默认所有纠错、冲突、过期和删除语义已经替你处理好了。([Mem0][5])

**我的选择不是把这些框架全部拼起来，而是吸收上述机制，建立一个有单一事实来源的记忆后端。**

## 二、整体结构：完整记录、当前理解、实时状态、模型上下文，必须是不同东西

我建议你把系统拆成下面这些**逻辑对象**。它们可以主要放在一个数据库里，不代表要开发六个独立服务。

| 对象                       | 保存什么                             | 为什么不能与其他对象混在一起         |
| ------------------------ | -------------------------------- | ---------------------- |
| 原始证据 `source_events`     | 用户原话、授权导入的文件、工具返回、明确反馈，连同来源和时间   | 后续理解可能出错，必须有回看和重新提取的依据 |
| 记忆断言 `memory_assertions` | “系统目前认为用户是什么情况”，每条都有证据、条件、有效期、状态 | 这是可修改的理解，不等于原始事实本身     |
| 进行中的事情 `episodes`        | 当前在规划什么、已决定什么、否决了什么、哪些问题尚未解决     | “正在做什么”不能被压成一句性格简介     |
| 实时业务状态 `live_state`      | 最新课程、当前位置、天气、打卡次数等，带更新时间         | 今天的状态不能永久写成用户特征        |
| 记忆视图 `profile_views`     | 精简个人简介、某个领域的摘要、当前任务的记忆包          | 这些只是从底层生成的可重建视图        |
| 检索索引                     | 全文索引、向量索引、实体和关系索引                | 索引用于找东西，不应该成为唯一保存信息的地方 |

这里最重要的区分是：

**“用户喜欢晚饭后跑步”属于个人偏好；“今天已完成一次打卡”属于当天状态；“学校每天最多计一次”属于规则；“系统建议今晚跑步”属于建议。**

如果把这四者全部当成同一种“记忆文本”，系统很容易把自己的建议记成用户已经做过的事情，把过去状态当成现在状态，把某位用户的体验当成全校规则。

所以，第一条工程原则是：

> **所有记忆都必须知道：是谁说的、说的是谁、是在描述事实还是表达愿望、适用于什么时候、证据在哪里。**

### 你说的“固定存放”，应该怎样理解？

可以有一份始终容易获取的核心简介，但它应当是**经过版本管理的派生视图**，不是永不修改的真相。

例如核心简介保留较稳定、跨任务有用、用户明确表达过的内容。某个地点的详细停车体验、某学期的打卡限制、一次失败安排的原因，不必全塞进这份简介，但底层不能丢失。

**常驻的是少量索引和高价值信息；完整的是底层证据和记忆对象。**

## 三、一条记忆到底应该长什么样？

不要只存：

```text
用户喜欢跑步。
```

这样的信息几乎没有决策能力。

应该存“带上下文和来源的断言”。下面用你在本次对话中明确说过的“不接受晚饭前跑”作示例。编号只是示意：

```json
{
  "id": "mem_run_before_dinner",
  "user_id": "user_123",
  "subject_id": "user_123",

  "predicate": "running.before_dinner.acceptable",
  "value": false,

  "assertion_type": "explicit_preference",
  "strength": "explicit_rejection",

  "scope": {
    "workspace": "personal",
    "domain": "daily_planning"
  },

  "conditions": [],
  "related_memory_ids": [
    "mem_run_evening",
    "mem_run_after_dinner_interval"
  ],

  "valid_time": {
    "from": null,
    "to": null,
    "precision": "unspecified"
  },

  "evidence": [
    {
      "event_id": "event_42",
      "span_id": "span_7",
      "relation": "supports"
    }
  ],

  "status": "active",
  "version": 1,
  "needs_confirmation": false
}
```

其中几个字段不能省。

**`assertion_type`：用户明确说的，还是系统推测的。**
“我不接受晚饭前跑”与“看起来用户可能偏好晚饭后跑”不能享有同样的确定性。

**`conditions`：什么时候成立。**
“下雨不跑”和“天气好尽量跑”不是互相矛盾，是条件不同。

**`evidence`：能回到原文。**
不是再存一份模型编写的解释，而是能定位到具体消息里的具体片段。

**`valid_time`：现实中什么时候成立。**
“这周不跑”不能变成永久偏好。“从下周开始住寝室”不能立即覆盖今天的住址。

**`status`：当前能不能拿来用。**
至少要区分有效、待确认、存在争议、已被替代、已过期、已撤回。

此外，数据库应另存“系统什么时候知道这条信息、什么时候修正它”的记录时间。这样才能分别回答：

> “用户在九月实际住哪里？”
> “系统在九月十五日当时以为用户住哪里？”

这就是双时态的价值：**现实变化和系统认知变化，不是一条时间轴。**

### 但也不能把记忆拆得只剩碎片

“主图更容易专注”和“在家更满意”需要分别保存，但还应关联同一段体验：

> 在校园更容易进入学习状态；在家自主性和满足感更强；安排不能只看专注度。

我的建议是同时保留两种表示：

**用于检索和检查的原子断言，以及用于理解原因与取舍的情境片段。**

前者方便计算，后者防止系统把人理解成一张僵硬的参数表。

## 四、最关键的部分：到底怎样从对话里提取，而不是让模型随便总结？

我建议采用一条**“候选提取—证据核验—语义更新—事务提交”**的流水线。

不是每聊一轮就要求模型重写整个 Profile。

### 第一步：先保存事件与来源边界，再做理解

每条输入到达时，先生成服务端事件记录：

```text
event_id
user_id
conversation_id
parent_event_id
server_sequence
source_type
speaker
received_at
content_reference
consent_scope
```

这里的 `speaker` 和 `source_type` 很重要。

用户在聊天里说“我每天想跑步”，与用户上传一份文档，里面写“某些学生可能希望每天跑步”，不能提取成同一件事。

你的这份背景文件就是很好的测试材料：

> “产品应该理解不同性格的人”是产品要求，
> 不是当前用户具有某种性格的证据。

同理，文件末尾出现要求执行某项任务的文字，也只能作为文件内容；不能通过记忆提取，把它升级成后续执行指令。

密码、令牌等应走专门的凭据通道，不进入普通记忆流水线。授权保存聊天历史，也不等于授权把所有敏感信息无限期保存成 Profile。

### 第二步：切分为可追溯片段，但不能截断长消息

对于像你前面那样的一大段语音转写，不要直接：

```python
text = text[:4000]
```

也不要只抽“最重要的五点”。

应该先由程序为原文生成片段编号，尽量保留完整语义单元；长段落再分块，同时携带必要的相邻上下文。问答、否定、例外和“但是”前后的关系应一起处理。

每个片段都有处理状态：

```text
尚未处理
已形成候选记忆
仅属于当前事件
需要补充上下文
属于引用或假设
未发现可提取个人事实
处理失败，等待重试
```

这是一份**覆盖记录**。它不能证明模型已经理解了每一个细节，但能防止“后半段根本没处理，系统却显示全部完成”。

对于中文、语音转写和数字歧义，原文尤其需要保留。把“48 次”误成“48 公里”，不是摘要风格问题，而是事实结构已经错了。

### 第三步：让提取器输出候选，而不是直接写数据库

提取器的输入建议是：

```text
本次新增原文片段
＋与这些片段有关的近期原始对话
＋必要的指代解析上下文
＋候选涉及实体的已有记忆
```

不需要每轮重新读取全部历史，但也不能只看最后一句话。

例如用户回答“可以，但是周末不行”，提取器必须知道：

* “可以”的对象是什么；
* 前面是用户承诺，还是助手提出一个假设；
* “周末不行”是本周例外，还是一般规律。

提取器输出：

```text
候选断言
支持它的原文片段编号
主体与对象
条件与例外
现实有效时间
明确陈述／推断／待确认
可能对应的旧记忆
```

这里应允许输出 `unknown` 和“不足以形成记忆”。**不能为了符合 Schema，强迫模型给每个字段编一个值。** OpenAI 的结构化输出文档也明确提醒：符合结构不等于内容正确，结构化结果仍然可能包含错误。([OpenAI Developers][6])

### 第四步：核验不是再问一句“你确定吗”

我会做两层验证。

**程序验证**负责可以确定检查的部分：证据编号是否存在、引用是否对应原文、单位是否一致、日期是否合法、条件字段是否完整、用户范围是否合法、是否引用了无权使用的来源。

**语义验证**负责原文是否真的支持候选内容。这个验证器应重新看原文，而不是只看提取器的解释。

它要特别检查：

> 是否把“想要”写成“已经做到”；
> 是否把“有时候”写成“总是”；
> 是否把“这周”写成“长期”；
> 是否把助手建议写成用户选择；
> 是否把用户举的例子写成用户本人事实；
> 是否丢掉了否定、条件、例外和比较对象。

复杂或高影响的候选再交给更强的模型复核，普通明确事实不必每次跑一整套昂贵审查。

不要让模型随口给个 `confidence=0.97`，就认为有了可靠置信度。可以记录提取器分数，但是否能作为概率使用，需要在真实标注样本上校准。

### 第五步：与已有记忆比较，决定发生的是哪一种变化

这一步不是简单的“相似度高就覆盖”。

建议支持以下更新操作：

| 操作                 | 含义              |
| ------------------ | --------------- |
| `ADD`              | 确实是新的记忆         |
| `SUPPORT`          | 为已有记忆增加独立证据     |
| `REFINE`           | 补充条件、时间、原因或精度   |
| `ADD_EXCEPTION`    | 增加一个适用范围较窄的例外   |
| `SUPERSEDE`        | 明确的新事实替代旧事实     |
| `DISPUTE`          | 发生冲突，暂时不能确定哪个成立 |
| `EXPIRE / RETRACT` | 过期或用户撤回         |

例如：

旧记忆：“非考试期通常可以现场找图书馆空位。”
新信息：“期中期末要提前预约。”

正确操作是增加条件化规则，不是删除旧记忆，也不是生成一条没有条件的“图书馆必须提前预约”。

再如：

旧记忆：“住六楼的出租房。”
新信息：“下周开始搬回寝室。”

正确操作是保留未来生效时间。今天规划路线时仍用出租房，下周才切换。

**同一条原话经过摘要、助手复述、其他 Agent 转述十次，不能算十份独立证据。** 必须沿来源链去重，否则系统会越来越相信自己最初的误解。

### 第六步：通过数据库事务提交，禁止模型随意覆盖总档案

提取器和复核器可以提出变更，但最终由代码提交。

提交过程至少保证：

```text
检查用户与作用域
→ 检查待修改记忆版本
→ 写入新断言或新版本
→ 写入证据和关系
→ 更新处理进度
→ 登记索引及摘要刷新任务
→ 提交事务
```

消息重试、网络重连、后台任务重复执行时，同一份证据不能反复生成新记忆。为此需要幂等键、事件编号和唯一性约束。

**模型负责解释，程序负责提交、权限与一致性。**

## 五、怎样做到“像懂你”，而不只是记住更多事实？

关键是记住**带条件的取舍、理由和结果**。

你这段对话中最有价值的信息，并不是“喜欢在家”或“喜欢安静”这种标签，而是：

> 校园专注度更高，但在家满意度更高。
> 学习时不想移动，但为了跑步愿意移动。
> 想每天使用 Codex，但普通任务可以放手运行。
> 晚课后仍想跑，但愿意为次日状态作取舍。

这些信息不能被压成一个固定地点排行榜，也不能归纳为“用户懒”“用户自控力差”。

我建议在原子记忆之外，增加一种**决策经验记录**：

```text
当时的情况是什么
有哪些实际可用选项
用户选了什么／否决了什么
用户明确给出的理由是什么
结果怎样
哪些是观察，哪些只是推测
```

例如，未来某次安排后用户说：

> “不是因为图书馆远，是我已经学进去了，不想再换地方。”

这应当修正系统对问题的解释：

```text
原假设：主要厌恶路程
新证据：主要厌恶专注状态中的转场
```

然后影响下一次建议，而不是只在回答里说一句“我懂你了”。

### 不要从行为直接推导性格

用户连续三次去图书馆，可能是因为家里施工，不代表图书馆现在变成最喜欢的地方。

因此，“发生了什么”和“用户为什么这么选”必须分开。没有明确理由时，系统可以提出假设，但不能把它当成定论。

更进一步，可以训练或调整一个条件化的选项排序器，用已确认的偏好和真实反馈比较方案。但在数据不充分时，我更建议先使用**明确偏好＋条件规则＋相关经验**，不要急着给每个人拟合一个看似精确的心理模型。

**真正的个性化，是在新情境中正确使用旧经验，而不是把用户永久固定成一种类型。**

---

## 六、上下文怎么做：每次调用前，按任务“编译”一份记忆包

这是第二个核心难点。

如果用户说：

> “我接下来该干什么？”

直接拿这句话去做向量搜索，可能根本搜不到“六楼”“跑后洗澡”“图书馆暂离规则”。因为这些词与问题的字面相似度不高，却会改变答案。

所以，**检索必须围绕任务需要什么，而不只是围绕用户说了什么。**

### 1. 先形成这一次决策的“上下文需求”

例如识别到这是一次近期日程决策，系统先形成需求：

```text
用户现在的位置与时间
下一项固定安排
当前在推进的任务
可用时间长度
可用学习地点
与这些活动相关的偏好和限制
可能影响选择的最新状态
```

这不是要求你把世上所有问题都写成固定模板。常见任务可以有明确的需求协议；新任务由模型补充需求，但补充出来的需求仍然经过权限和可获取性检查。

### 2. 结构化查询和语义检索并行，而不是只用向量

我会采用四条召回路径：

**结构化查询**取当前有效、明确适用于本次任务的约束，例如晚饭前不跑、设备只能在家使用。这些不应该与闲聊记忆一起竞争“前五条相似结果”。

**全文与实体查询**处理课程名、楼宇、日期、专有名词和精确表述。别名需要在正确校园和用户范围内解析，“主图”不能跨学校混在一起。

**向量检索**寻找表达不同但意义相关的体验，例如“换地方很烦”和“重新进入状态很慢”。

**历史事件检索**找此前相似安排及其结果，而不是只找用户简介。

检索结果可以合并排序，但权限、有效性和明确的适用约束不应仅靠排序分数处理。

### 3. 找到一条记忆后，要把它依赖的条件一起找来

检索到“用户喜欢晚上跑步”，还不够。

需要沿关联关系补上：

```text
饭后间隔
雨天例外
西操偏好
关灯限制
跑后直接回家
晚课与睡眠冲突时的取舍
```

我会把这称为**依赖展开**：在有限范围内补齐解释这条记忆所必需的条件、例外、冲突和来源。

否则系统每条记忆都记对了，组合起来仍然可能做错。

### 4. 动态事实要刷新，不能用旧记忆冒充实时数据

记忆可以告诉系统：

> “这类决策应该查体育打卡进度。”

但具体已经完成多少次，需要读取足够新的状态。

对每个动态结果保存：

```text
source
observed_at
fetched_at
valid_until 或 refresh_policy
coverage
```

如果打卡同步失败，应该知道自己拿到的是旧值；如果定位是几个小时前的，不能说“你现在就在东教”。

课程、天气、位置、健康状态的刷新频率应按各自变化速度和实际用途确定，而不是统一设一个永久 TTL。

### 5. 必须有一条绕过“已提取记忆”的原文检索通道

这是防遗漏非常重要的一步。

**某条信息没有被提取出来，不应该意味着它以后永远找不到。**

原始聊天和授权保留的文档，也需要有独立的检索索引；必要时可以回到原文，重新读取和提取。

这不是理论上的小问题。Hindsight 的文档明确指出：某份文档如果经过提取后没有生成任何记忆，虽然原文仍被保存，但其 `recall` 和 `reflect` 不会找到它。这说明“保存了原文”和“系统实际能够检索到原文”是两回事。([Hindsight][7])

你应该专门避免这种断层。

### 6. 最后才组织成模型要看的上下文

一次调用的上下文可以是：

```text
固定的系统规则与工具权限

本次用户请求及必要的近期原话

当前任务状态
- 当前目标
- 已接受与已否决的选择
- 尚未解决的问题

相关个人记忆
- 有效事实
- 条件偏好
- 例外与冲突
- 必要原文证据

最新业务状态
- 来源与更新时间

缺失信息与不确定性
```

不要把完整历史、全部工具返回、所有个人资料都拼进去。

Anthropic 的上下文工程文档也强调了按需读取、压缩、结构化记录，以及只保留当前需要的高价值信息；同时指出过度压缩会丢掉之后才显现价值的细节。([Anthropic][8])

我的具体要求是：**条件与例外优先于装饰性的个人简介，当前纠正优先于旧摘要，证据优先于模型自己写过的结论。**

## 七、怎样减少“相关的重要细节被遗漏”？

这里不能靠一句“请全面考虑”。

我会建立一个**上下文覆盖检查**。

以“今晚是否适合去跑步”为例，系统先有一份这类判断所需的条件集合。然后逐项记录：

```text
用户对跑步时段的偏好：已取得
晚饭是否已经结束：未知
天气：已取得，但需要检查更新时间
操场开放及关灯：已取得
后续固定课程：已取得
次日起床约束：已取得
当前打卡进度：同步失败
```

重要的是区分：

**已知没有限制、暂时没有查到、根本还没有查询、信息存在冲突。**

这四种状态不能都变成一个空字段。

对未知的重要条件，系统应该补查、采取条件化建议，或者问一个真正会改变答案的问题。不能悄悄假定它不重要。

再加一层输出检查：当系统已经生成候选建议后，检查它涉及的行为是否引入了新的依赖。

例如原先只是推荐学习地点，后来方案增加了“先回家再返校”，那么就必须补查回家路线、上下楼、电脑时间和下一项固定活动，不能沿用原来的不完整上下文。

**这意味着检索不是只发生在回答前一次，而是允许在候选方案形成后，再做一次有针对性的补检索。**

但需要坦诚：开放自然语言中的“所有未来相关细节”，没有办法仅靠一次提取证明已经全部覆盖。工程上可以做到的是：

> 原始输入不被无声截断；
> 已知重要约束被明确检查；
> 缺失状态可见；
> 漏提取后仍能回原文；
> 通过测试持续测量漏掉了什么。

这比宣称“向量库永不遗忘”可靠得多。

## 八、长期聊天怎样压缩，才不会越总结越失真？

不要采用：

```text
旧总结＋新聊天 → 新总结
旧总结＋新聊天 → 新总结
……
```

并且把旧原文逐渐丢掉。

我建议把长期对话分成若干有边界的任务或事件，分别维护检查点。一个检查点包括：

```text
当前要完成什么
已经确认的决定
被否决的方案及原因
当前约束所引用的记忆 ID
尚未确定的事项
有关文件或结果的位置
覆盖到的原始事件序号
```

**检查点的目的，是恢复工作，不是写人物传记。**

生成新检查点时，针对发生变化的部分读取原始事件和对应记忆，不是无限压缩上一次摘要。近期对话保留必要原文，旧内容按需回读。

这也解释了为什么“会话上下文”和“跨会话个人记忆”不能混为一谈。LangChain 的文档明确区分线程内状态与跨线程长期记忆，并讨论了整体 Profile 重写和分散记忆集合各自的风险。([Docs by LangChain][9])

模型提供方的会话续接也不是完整个人记忆方案。例如 OpenAI 的 `previous_response_id` 用于延续响应链和会话上下文；不能把这种接口直接等同于你产品所需的、跨任务可纠错的个人记忆后端。([OpenAI Platform][10])

**你的数据库应当独立于模型供应商。** 换用 DeepSeek 或其他模型时，变化的是上下文适配器，而不是用户的记忆重新开始。

## 九、更新放后台，会不会导致刚说完就忘了？多 Agent 会不会互相覆盖？

会，所以需要明确的一致性设计。

### 实时路径和后台路径分开

实时路径负责：

> 保存新输入；处理撤回和权限变化；让本轮模型看到用户刚刚说的话；使明确的新纠正在本轮生效。

后台路径负责：

> 完整提取；跨会话整合；去重；更新索引；生成新的个人摘要。

不能等到后台整理完，才承认用户刚刚说“我现在已经不住那里了”。

具体做法是保存两个序号：

```text
最新收到的事件序号
长期记忆已经处理到的事件序号
```

构建上下文时，将尚未处理的近期输入作为增量一起考虑。后台落后太多、且会影响当前决策时，进行相关部分的同步补处理，不能装作数据已经完整更新。

### 多个 Agent 只能提议修改，不能各自覆盖同一份总记忆

每个 Agent 读取一个明确版本的记忆快照，返回有来源的变更提案。

写入时检查：

```text
expected_version == current_version ?
```

相等才提交；不相等就重新读取并合并。涉及语义冲突时，不是“最后一个写入者获胜”，而是按前面说的新增、例外、替代或争议处理。

读取可以并行，**同一个用户同一部分记忆的最终提交应由一个受控写入路径完成。**

后台队列需要持久化，提交与任务入队使用事务性 outbox 之类的方式连接，避免数据库已经保存输入、进程却在创建提取任务前崩溃，导致这段输入永远没人处理。

### Hermes 应当放在哪里？

Hermes 已有外部记忆 Provider 的集成机制，文档描述了上下文注入、回合前预取、回合后同步和记忆工具等接入点。([Hermes Agent][11])

对于你的产品，我会把它接到上述统一记忆服务：

* 内置文件最多作为派生摘要，不能另成一套互相竞争的真相。
* 模型可搜索和读取记忆，但正式修改经过统一写入服务。
* 避免内置记忆与外部 Provider 互相转存、重复提取同一份摘要。
* 更正、撤回和敏感范围变化必须能使旧上下文失效。

**不需要重新研发一个大而全的 Agent 框架，真正需要自己掌握的是记忆的数据语义和读写协议。**

## 十、主动提醒怎么与记忆结合？

你文件里那些“快到考试”“打卡次数不足”“应该预约座位”的场景，需要一种特殊记录：**未来需要重新检查的事项**。它不是普通偏好，也不是一条已经执行的日程。

例如保存：

```text
目标：截止日前完成打卡要求
依赖：剩余次数、剩余日期、可跑时段、天气
触发：进度更新／日期推进／天气显著变化
允许动作：生成提醒
提醒限制：冷却时间、通知时段、用户授权
```

普通事件或定时检查先用代码判断是否值得重新评估，只有需要时才调用模型，并复用同一套上下文构建流程。

这样不是让一个模型不停地读你的全部资料，而是：

> 某个状态变化 → 找到受影响的目标 → 获取所需记忆和最新数据 → 决定是否提醒。

还有一个必须独立处理的边界：**“用户喜欢有人提醒”不等于“用户授权自动预约、改课、发邮件”。** 操作权限由权限系统控制，不能让模型从亲密感或长期偏好里自行推导出来。

## 十一、纠错、删除和隐私必须是记忆机制本身的一部分

这不是最后加一个“删除按钮”就解决的。

### 记忆需要可解释，但不要伪装成读出了模型内部原因

每次回答可以保存一份“上下文收据”：

```text
用了哪个记忆版本
提供了哪些记忆
引用了哪些原文
读取了哪些实时状态
哪些条件未知
哪些检查通过或失败
```

它能说明系统拿到了什么依据，但不能声称精确揭示模型内部每个判断的成因。

用户说“这个理解错了”，应当能沿收据找到具体记忆及其证据，修正它，并使相关摘要和后续提醒一起更新。

### 删除必须沿派生关系传播

假设用户要求忘记某件事，相关内容可能存在于：

> 原文、提取记忆、情境摘要、个人简介、向量索引、缓存、已保存的上下文包。

只删 `USER.md` 中的一句话，后台下次可能又从原文提取回来。

因此需要来源与派生关系，删除时同步取消后续提取，并清理或重建受影响的派生物。已经存在于托管会话上下文中的内容也需要考虑，必要时开启干净会话。

“从活跃系统立即停止使用”和“备份最终清除”应分别定义，不能对用户承诺实际上做不到的即时全介质消失。

### 用户范围必须由服务器决定

`user_id`、工作区和权限范围应来自已认证会话，不能允许模型随意填写一个用户编号就检索。

对于多人产品，数据库行级隔离可以作为一道防线。PostgreSQL 支持行级访问策略，但其文档也明确说明了所有者、超级用户和 `BYPASSRLS` 等例外，因此应用不能用绕过隔离的高权限账户再寄希望于提示词。([PostgreSQL][12])

还要区分“当前用户本人”“用户谈到的另一个人”“产品的假想用户”和“另一个项目里的角色”。**很多记忆污染不是跨账户泄漏，而是主语在提取时就认错了。**

最后，检索到的网页、文件和历史文本仍然是数据，不能直接获得系统指令权限。OpenAI 的 Agent 安全指南也明确建议避免把不可信内容插入高权限开发者消息，并通过结构化边界限制数据流。([OpenAI Developers][13])

---

## 十二、真正落地时，我会选什么实现，而不是继续堆概念？

我会从**一个数据库、一套记忆服务、一个后台处理器、一个上下文构建器**开始。

数据库以 PostgreSQL 保存事件、断言、证据关系、版本和任务状态；语义检索可用 pgvector，精确检索配合全文或适合中文的分词／字符索引。pgvector 本身支持在 PostgreSQL 内进行向量相似度搜索，不必为了“有向量”另起一套唯一真相。([GitHub][14])

关系最初可以就是普通关联表。等确实出现大量复杂关系遍历需求，再考虑专门图数据库，不必一开始就为“记忆图谱”这个名字增加维护成本。

对外主要保留几个清晰接口：

```text
ingest_event(...)
    接收带身份、来源和授权范围的事件

build_context(...)
    根据任务、时间、范围和预算生成上下文包

propose_memory_change(...)
    提交候选更新，不能直接越权写库

search_memory(...) / read_evidence(...)
    按需找记忆与原始依据

correct_memory(...) / forget(...)
    修正与删除，并传播到派生内容
```

这些不是五个必须独立部署的微服务，而是五类职责。

### 不能只验收“能记住名字”

我会用你这段对话建立一套带预期结果的回放测试，至少覆盖：

| 测试输入或变化           | 系统应该做到             |
| ----------------- | ------------------ |
| “48 公里”被纠正为“48 次” | 旧结论被替代，所有相关判断使用新单位 |
| “这周不跑”            | 形成限时状态，不改成永久不喜欢跑步  |
| “图书馆专注度高，在家更满意”   | 保留两个维度，不能合并成单一地点偏好 |
| 上传文档写“某类用户喜欢早起”   | 不归到当前用户本人          |
| 助手建议周三跑，用户未确认     | 不记成用户承诺，更不记成已完成    |
| 新消息修正住处，后台还没处理    | 本轮不能继续使用旧住处安排路线    |
| 普通时期现场有座，考试期需预约   | 条件规则共存，不相互覆盖       |
| 某条细节未进入 Profile   | 仍能通过原文检索找回         |
| 用户要求忘记某事实         | 不被摘要或后台重提取重新带回来    |
| 两个 Agent 同时更新同一事实 | 无静默覆盖，冲突可见并正确处理    |

测量时，不只看回答是否“像个性化”。

应该分别看：**提取漏了多少、添了多少不存在的事实；条件与单位保留得怎样；检索有没有找到必要证据；旧信息有没有继续生效；最终建议有没有违反已知约束；纠错需要多久生效。**

LongMemEval 把长期记忆能力拆成信息提取、跨会话推理、时间推理、知识更新和无法确定时的克制，这些维度很适合作为你测试集的参考；但你的产品还需要额外检查真实决策是否遵守用户约束。([arXiv][15])

最后要做消融比较：同一批用户历史、同一模型、同一批问题，比较“只有简介”“只有向量搜索”和上述机制。只有当它在陌生问题、时间变化和纠错之后仍然更好，才说明记忆系统真的起作用。

---

**归根结底，你要建立的不是一份越来越长的个人档案，而是一套能持续回答三个问题的系统：**

**“我凭什么认为自己懂这个用户？”——有原始证据。**

**“这个理解现在、在这个情境下还成立吗？”——有时间、条件、例外和更新机制。**

**“这次回答真正需要知道什么？”——有按任务构建的上下文，以及缺失检查。**

做到这三层，产品才会从“记得你说过的话”，走向“能把你说过的话正确用在新的处境里”。**那种十分懂你的感觉，应当来自可纠错、可追溯、能尊重情境的判断，而不是来自更长的 Profile 或更亲密的语气。**

# 第一轮：眼前的现实——此刻发生了什么，我现在怎么做？

这一轮只关注**已经发生或正在发生的外部情况**，不讨论人生选择，也不讨论“我为什么会这样”。

### A1．课程与临时变更

“下一节到底在哪间教室，群里刚发的改教室通知算进去了吗？”

“今天是调休补课，应该按星期几的课表走？”

“老师说提前二十分钟下课，我现在能赶上那场讲座吗？”

“我刚睡醒，今天还有哪些事情已经来不及，哪些还来得及补救？”

“这门课本周停一次，是只取消上课，还是作业也延期了？”

# 第二轮：未来与可能性——我该学什么、选什么、往哪里走？

这一轮从“眼前怎么做”转到**尚未确定的路径、能力、目标和选择**。关键不再只是获得最新信息，而是比较不同未来。

### B1．学习水平与知识缺口

“我看答案都懂，自己做却不会，最近的记录更像是哪一类问题？”

“这门课我究竟缺的是前置知识，还是练习还不够？”

“下次考试前，哪些薄弱点最值得先补，而不是全部重学？”

“我总在同一种地方卡住，有没有跨题目的共同障碍？”

### B2．培养方案与选课路径

“这两门课都想选，但它们对后续课程的影响有什么不同？”

“现在选这门课，会不会堵住下学期更重要的一门？”

“我还差的毕业要求里，哪些不能拖到最后一年才处理？”

“辅修这条路线按我的实际基础和剩余学期能完成吗？”

“这门课改成旁听，会失去哪些资格，又能保留哪些收益？”

### B3．目标排序与机会成本

“竞赛、课内和自己的项目只能重点推两个，你怎么比较它们的代价？”

“我说最重视科研，但实际时间都给了绩点，这两个目标需要重新排序吗？”

“这学期做到什么程度就算够了，而不是无限往上加任务？”

“现在答应一个新项目，具体要牺牲现有的哪一件事？”

“有没有一个方案保留最重要的目标，但不要求所有方面都优秀？”

### B4．科研、实习与发展

“以我已经做过的东西，现在适合先联系实验室还是先补一个项目？”

“这份实习要求里，哪些我确实具备，哪些只是简历写得像会？”

“想申请这个方向，未来半年最有价值的证据应该是什么？”

“我之前的课程和项目，有哪些可以连成一条清楚的申请主线？”

“这个机会看着很好，但和我真正想发展的方向一致吗？”

### B5．低成本探索与兴趣验证

“我不确定喜不喜欢这个领域，能不能用一个周末做个小实验？”

“怎样区分我喜欢做这件事，还是只喜欢想象做成后的样子？”

“在正式报名之前，有没有一个成本小、但足以判断适不适合的体验？”

“我对三个方向都有兴趣，先试哪个最能帮助排除不适合的？”

“这次体验结束后，应该留下哪些观察，才不会只凭最后一天的心情决定？”

### B6．假设与反事实比较

“假设我不参加这次竞赛，这学期会多出哪些可能性？”

“如果搬到另一个校区，现有的学习和生活安排会变成什么样？”

“假如这门课没通过，我还有哪些后续路径，不要先当成我已经挂科？”

“如果接下来的项目比预计多花一倍时间，哪套计划还能成立？”

“分别按保研优先和项目优先，做两套比较，但先别替我选定？”

### B7．可逆决定与承诺时点

“这件事最晚什么时候必须决定，哪些部分还能先试再定？”

“现在拒绝这个机会，之后还有没有重新进入的可能？”

“哪些准备可以同时服务两个方向，不必今天就彻底选边？”

“这条路线走到哪一步，退出的成本会明显增加？”

“我当时定下的停止条件已经到了吗，还是只是舍不得之前的投入？”

### B8．成长评估与长期复盘

“跟一个月前相比，我有哪些能力真的变强了，不只是投入时间变多？”

“这个学习方法有效的证据是什么，能不能排除只是题变简单了？”

“这个目标现在还值得追吗，当初支持它的理由有没有变化？”

“如果继续保持现在的投入，到截止日前还缺哪些关键里程碑？”

# 第三轮：人与人的交集——不是只安排我，而是处理关系、合作与边界

这一轮把视角从单个学生移向**多个主体之间的约定、协作、信息边界和角色差异**。

### C1．多人时间协调

“我们四个人下周什么时候都能见面，只用大家同意共享的空闲时间？”

“不是大家都没课就算能开会，还得算通勤，这次哪个时段真合适？”

“我可以晚一点，他只能早一点，有没有双方都能接受的折中？”

“这次是时间已经敲定，还是只有我和另一位同意了？”

“我们轮流迁就了几次，这次能不能别总让同一个人让步？”

### C2．小组分工与依赖

“我下一步等的是谁的材料，还是别人其实在等我？”

“这个任务现在到底归谁，群里改过一次以后好像没人接？”

“我自己的部分提前做完了，能帮哪一项而不重复别人的工作？”

“队友延期之后，哪些后续任务真的受影响，哪些可以照常做？”

### C3．不同关系里的表达

“我和这位老师已经聊过哪些背景，这封邮件还需要重新介绍吗？”

### C4．承诺、边界与人际摩擦

“我答应帮他改材料，但没答应替他全部重写，怎么把边界说明白？”

“他是不是又把我的沉默当成同意了，记录里我真正承诺过什么？”

“我和室友对安静时段理解不同，能不能先整理双方实际提出过的要求？”

“这次让我不舒服的点，是对方临时变卦，还是我们的预期从来没说清？”

“我想取消这次约定，哪些受影响的人需要先通知？”

### C5．共享资源与共同支出

“小组预算里哪些支出大家同意了，哪些只是一个人提议？”

“羽毛球场预约成功后，还有谁没确认参加，费用应该怎样先说明？”

### C6．朋友、家人与亲密关系

“家人来学校这一天，怎样安排才能让他们轻松，也不让我整天赶路？”

### C7．代问、引用与身份辨别

“我替室友问选课，这些限制是他的，不要以后拿来安排我，可以吗？”

“我给你看的学长经历，是用来参考，不代表我想完整复制他的路，可以吗？”

“我说的那个小李，是实验课搭档，不是上次一起打球的小李，你能区分吗？”

“这段聊天里是对方说喜欢早起，不是我，你能重新分清是谁的偏好吗？”

“先按一位假想新生的情况做示例，不要把那个学生当成我，好吗？”

### C8．角色切换与公开场景

“我现在以班委身份做通知，别套用我私下聊天的语气，好吗？”

“这次以组长身份安排，哪些信息我有权知道，哪些只是队友的隐私？”

“我自己不喜欢早起，但不能据此给全社团排活动，对吧？”

“准备投屏讨论了，能切到不显示我私人备忘的版本吗？”

“这份公共活动方案，能保留适合我的便利，但别把大家都变成按我生活的人吗？”

# 第四轮：内在体验——我需要怎样被理解，而不只是被优化？

这一轮不再优先问外部世界，而是问：**我此刻真正需要什么帮助？行为背后的原因是什么？怎样的一天才值得过？**

### D1．本轮需要的是哪种帮助

“我现在只是想吐槽，能不能先别给我安排下一步？”

“这次别急着安慰我，我想认真分析到底哪里出了问题，可以吗？”

“我脑子很乱，你先陪我把事情讲清楚，不要立刻做完整计划，好吗？”

“我只剩一点精力，能不能只帮我决定眼前的一步？”

“我现在有能力处理难事，你别因为昨天状态不好就一直劝我休息，可以吗？”

### D2．行为背后的真实阻力

“我不是不想去图书馆，是不想重新收拾和找座，你能按这个区别理解吗？”

“我一直没开始，可能不是拖延，而是根本不知道完成标准，你能帮我分清吗？”

“我总想回宿舍，是那里更舒服，还是现在这件事让我不想面对？”

“我不愿参加这次活动，不代表我讨厌社交，能先看看这次具体哪里不合适吗？”

“我做得慢，是没有动力，还是其实在追求比任务要求更深的理解？”

### D3．精力、感受与环境

“身体不累，但不想再做需要判断的事，接下来能不能换一种负担？”

“这里很安静，我却觉得压抑，你能不能别只用噪声衡量适不适合？”

“我今天很想动，不想像平时那样一直坐着，可以按今天的状态来吗？”

“我精神不错，但注意力很散，你能帮我找到一个容易进入的开头吗？”

“我需要人多一点的氛围，但不想和人说话，有这种介于两者之间的安排吗？”

### D4．满意感与生活价值

“今天做了很多事，却感觉一天不属于自己，问题可能在哪里？”

“能不能给我留一段不需要证明有产出的时间？”

“这件事对履历没用，但我真的喜欢，它能不能被认真算进生活？”

“如果效率更高却每天都很难受，那套安排还算更好吗？”

“我想有一点惊喜，不想每一天都完全复制昨天，能留出这种空间吗？”

### D5．学习陪伴与交流方式

“这道题先只给一个提示，别把后面的突破口顺便说出来，可以吗？”

“我今天想直接知道答案，不用每次都坚持上次的引导方式，可以吗？”

“别因为我学过这门课，就默认我理解了这个概念，好吗？”

“我讲得乱的时候，先帮我整理原意，别立刻换成你的整套说法，可以吗？”

“这次让我自己讲，你只在我真的跳步时指出来，行吗？”

### D6．自主权与被督促的方式

“我想有人提醒，但不想每次偏离计划都像被批评，你能怎么提醒？”

“今天请你替我少做几个选择，不要把十个选项全交回来，可以吗？”

“我需要一点推动，但最后的决定还是想自己做，你能停在什么位置？”

“这次我明知道效率不高还是想这么过，你能接受不把我纠正回来吗？”

“我说要严格督促，不代表可以用羞辱或比较刺激我，对吧？”

### D7．自我变化与身份探索

“我以前很在意排名，现在好像没那么在意了，怎么判断这是不是认真改变？”

“我想试着成为更外向的人，但别先把我当成已经习惯那样的人，可以吗？”

“你总按以前的兴趣推荐，可我想看看以前的自己不会选的东西，怎么办？”

“我说自己很懒的时候，也许只是在生气，你能别替我把这个标签定死吗？”

“我可能不想继续原来的目标了，能不能先允许我重新想，而不是劝我坚持？”

### D8．矛盾、例外与暂时说不清

“我既想独处又怕孤单，这两个需求能同时被考虑吗？”

“我喜欢固定节奏，但不喜欢被规定死，这两者怎么区别？”

“同样一件事，自己想做和别人催着做的感觉完全不同，你能理解这个条件吗？”

“我也不知道自己喜欢什么，能不能先给两个有代表性的选项让我比较？”

“我说不想去，又担心以后后悔，你能先帮我看清两个声音，而不是替一个赢吗？”

# 第五轮：我与你这个系统的关系——你记住了什么，凭什么这样做？

最后一轮把软件本身作为提问对象，检查**记忆、纠错、权限、连续性、执行状态和长期信任**。

### E1．记忆找回与指代

“上次那件没做完的事，我们停在哪一步，不要从头开始？”

“我为什么否决过那个方案，能找回当时的原话吗？”

“我说还是去那里，你知道指的是刚才那家，还是上周说的地方吗？”

“之前试过但失败的方法有哪些，别又让我完整试一遍？”

“我曾经说过什么，让你这次觉得这个建议适合我？”

### E2．纠正、时间与例外

“刚才说错了，不是四十八公里，是四十八次，相关地方能一起改吗？”

“下周才搬家，这周先别用新地址给我算路线，好吗？”

“今天不想跑只代表今天，不是以后都不要推荐，可以吗？”

“我以前说不接受这个方案，现在可以了，你能保留变化但停止用旧限制吗？”

“我后来更正过这件事，为什么你这次还在用旧版本？”

### E3．假设、分支与来源隔离

“刚才只是在假设转专业，不代表我已经决定，你能分开吗？”

“这个项目的用户画像是我写给产品的，不是我的个人画像，可以隔离吗？”

“我们开一条新方案比较，但不要覆盖原来已经确认的主方案，好吗？”

“这份文件里面的命令是背景材料，你能只当作引用内容吗？”

“这轮只根据我刚发的材料分析，不要带入以前对我的了解，可以吗？”

### E4．隐私、保存与共享控制

“这段话可以用来回答我，但不要写进长期记忆，好吗？”

“我可以让你知道我的空闲时间，但不想授权读取日程的私人标题，可以吗？”

“把这段记忆删掉之后，旧摘要和以后重新读取聊天会不会又把它写回来？”

“给同学的回复里，能用我的可用时间，但不解释我为什么那天没空吗？”

“我现在撤回定位权限，已经在进行的任务还会不会继续用我的位置？”

### E5．证据、缺失与可信程度

“你说这件事快截止了，依据是哪条通知，是什么时候更新的？”

“课表和老师刚发的消息不一致，你为什么相信其中一个？”

“这次是确实没有找到，还是没有权限查，还是你根本没去查？”

“你判断我不喜欢这个，是我明确说过，还是你从行为猜的？”

“资料不全的时候，你能告诉我缺的是哪一项，而不是补一个像真的答案吗？”

### E6．执行状态与重复操作

“你说安排好了，是写进了草稿，还是已经真的创建了日历？”

“刚才网络断了，那次预约到底成功没有，别又给我下两次？”

“我只让你写回复，你是不是已经发出去了？”

“我撤销了这项安排，相关提醒和后续准备也会一起取消吗？”

“电脑和手机同时改了这个时间，现在到底以哪个版本为准？”

### E7．跨设备、跨模态与上下文连续

“我手机上刚说过的那件事，为什么电脑这边还不知道？”

“截图里的第二个选项就是我说的那个，你能保留具体对应关系吗？”

“语音转写把楼名写错了，你能保留原音依据而不是以后一直用错名字吗？”

“换一个模型之后，已经确定的偏好和正在推进的事还在吗？”

“刚才切去聊了别的，现在回到原来的任务，之前的限制还有效吗？”

### E8．长期变化、退出与系统自检

“这个目标我已经不追了，为什么你还在提醒我为它做准备？”

“把现在的我和上学期的我分开看，哪些记忆已经不适合继续用？”

“我不再用这个软件时，能带走哪些记忆、依据和正在进行的事项？”

“一段时间没有新消息，你会把旧信息当作仍然有效，还是标记不确定？”

“你能给我看一次这周的理解变化，让我知道有没有被你越记越偏吗？”

# 回头检查：上一版设计究竟还缺什么？

**有，而且不只是再补几个 Profile 字段。**

上一版的“原始证据、结构化断言、任务状态、实时数据、混合检索、版本与删除”可以保留。但经过这些场景，能看出它仍然偏向：

> 把过去说过的事情保存正确，再在相关时找出来。

而你要的产品还必须处理：

> **用户现在这句话，是在描述现实、探索可能、请求帮助、纠正理解，还是限制系统？这些不同含义应该改变什么，又绝对不应该改变什么？**

我认为必须往下落到以下十个地方。

## 一、在“提取记忆”之前，增加真正的语义分流

前一版说“区分事实、愿望、推测”，方向没错，但还不够具体。

例如用户说：

> “假设下个月我搬回寝室，帮我比较两种安排，先别改日程。还有，我今天不想跑，但别把它记成我以后不跑了。”

不能把整段话交给一个“提取用户信息”的模型，然后期待它自行处理一切。

这句话至少包含四种不同操作：

| 片段        | 正确处理     | 不应发生的变化    |
| --------- | -------- | ---------- |
| 假设下个月搬回寝室 | 创建假设情景   | 修改真实住处     |
| 比较两种安排    | 创建比较任务   | 认定用户选定其中一种 |
| 先别改日程     | 本轮操作权限限制 | 仅作为普通文字备注  |
| 今天不想跑     | 今日例外     | 覆盖长期运动偏好   |

因此，提取器之前应有一个**话语解析步骤**，产出类似：

```text
话语行为：陈述／纠正／假设／请求／授权／撤销／引用
主体：本人／另一个人／群体／虚构角色
指代对象：哪个地点、哪项方案、哪次承诺
现实性：真实／未来已决定／仅假设／尚未确定
时间范围：何时开始、何时结束
适用范围：本轮／本任务／某领域／长期
证据：原文位置及必要的上下文
```

然后由不同路径处理。

**授权和撤销进入权限状态；假设进入情景；承诺进入任务；真实偏好才有机会进入个人记忆。**

这里还必须允许“不确定”。比如“行，就这样吧”究竟确认哪个方案，需要先解析指代，不能自动把前面所有建议全部变成承诺。

结构化输出只解决输出形状，不证明解析正确。OpenAI 的官方文档也明确说明，Structured Outputs 仍可能出现内容错误，因此 Schema 校验不能代替语义核验。([OpenAI Developers][1])

**新增的工程要求：不只是输出一条记忆，还要输出它为什么属于这条写入路径。**

## 二、把“现实”“假设”“提议”“承诺”“执行结果”分开

第二轮和第五轮暴露了一个根本问题：**个人助手必须能讨论尚不存在的生活，而不把它记成已经存在。**

我建议在上一版基础上明确区分：

```text
现实事实：现在确实如此
假设情景：为比较暂时假定如此
候选方案：系统提出过，但用户未选择
已选方案：用户接受了这个方向
行动承诺：用户或系统答应完成某事
执行结果：有证据表明实际发生了什么
```

这些不是六份互相复制的文本，而是不同对象和状态。

尤其需要一个 `world_id`，区分现实与不同假设：

```text
real_world
scenario_move_dorm
scenario_competition_first
scenario_project_first
```

**检索真实日程时，不能把假设分支里的课表、住处和目标一起召回。**

用户后来决定采用某个假设方案时，也不能整块覆盖现实状态。应当比较其中哪些变化已经决定、什么时候生效、还依赖什么，再逐项提交。

例如：

> “就按搬回寝室的方案准备，但我还没申请成功。”

这意味着可以建立准备任务，却不能将“已经住寝室”写成当前事实。

类似地：

> “预约可能成功了，但网络断了。”

执行状态必须保留为“结果待确认”，不能简单归成失败后重试，也不能宣称成功。

**这一层不是普通记忆管理能顺带解决的，需要明确的状态转换规则。**

## 三、个人画像要分解成不同性质的模型，不能只是更多标签

第四轮表明，“用户喜欢什么”远远不够。

我会把上一版的个人画像进一步分成：

| 部分     | 回答的问题          | 例子               |
| ------ | -------------- | ---------------- |
| 条件偏好   | 在什么情况下更偏向哪种选择？ | 专注时不喜欢转场         |
| 价值与取舍  | 不同好处冲突时，重视什么？  | 满意感不能完全让位于效率     |
| 能力与资源  | 目前能够做到什么？      | 有无设备、是否掌握前置知识    |
| 当前状态   | 今天、此刻是什么情况？    | 当前疲惫、今天想活动       |
| 交互约定   | 这次希望助手怎样参与？    | 先听、先提示、直接给答案     |
| 系统解释假设 | 系统猜测的原因是什么？    | 可能不是拖延，而是不清楚完成标准 |

其中最危险的是最后一类。

**系统的解释假设不能悄悄升级成用户事实。**

例如：

```text
观察：用户三次没有去图书馆。
解释一：不喜欢图书馆。
解释二：近期经常需要电脑。
解释三：没有连续时间，过去不划算。
```

在没有足够证据时，应保留竞争解释，而不是选择一个最像心理分析的结论写进 Profile。

对于偏好，建议保存条件化的比较，而不是一条总排名：

```text
当任务是独立数学学习、没有电脑依赖时：
    活动中心优于家，理由是更容易专注。

当任务需要频繁语音与 Codex 配合时：
    家优于活动中心，理由是设备与表达条件。

当用户明确要求放松时：
    不使用“学习效率最高”作为唯一排序标准。
```

这比“家：90 分；活动中心：85 分”更接近你想要的理解。

**越懂用户，不应该越容易替用户定性；应该越清楚自己的理解适用于什么条件。**

## 四、学习记忆必须保存“表现证据”，不能用课程名和成绩代替能力

第二轮 B1、B8，以及第四轮 D5，要求补出一块上一版没有展开的内容：**能力记忆**。

“学过数学分析”与“能独立处理某类问题”不是同一件事。

至少需要把学习记录落成这样的观察：

```text
涉及哪个概念或技能
具体任务是什么
当时是否使用了提示、答案或 AI
独立完成了哪些部分
在哪个步骤发生错误或停顿
任务难度与来源是否可比较
发生时间
后来是否独立复现
```

在这些观察之上，再生成可修正的能力判断。

例如：

> “能够在提示下完成，但独立找到入口的证据不足。”

比：

> “已掌握。”

更有用。

还要把**交互偏好与能力判断分开**：

“今天直接告诉我答案”不代表用户永远不喜欢提示；“这次需要提示”也不代表其长期能力下降。

相应地，检索一条学习建议时，不是只找“用户喜欢直观解释”，还应该查：

> 这个概念最近的独立表现是什么？上次的提示已经透露到哪一步？当前要求是不剧透还是直接讲解？

这意味着上下文里需要保存**当前教学进度和已公开内容**，不能只有题目与最终答案。

## 五、上下文构建之前，需要一份“本轮使用协议”

这是这次反查后，我认为最值得增加的接口。

前一版说“按任务生成上下文”，但这里还得提前决定：**本轮哪些信息可以用、为谁用、输出给谁、允许做什么。**

我建议让每轮先确定一个结构，名称可以是 `ContextContract`：

```json
{
  "task_kind": "compare_options",
  "subject": "mentioned_roommate",
  "world_id": "scenario_move_dorm",
  "allowed_sources": [
    "current_conversation",
    "authorized_campus_information"
  ],
  "personal_memory_mode": "exclude_account_owner_profile",
  "audience": "current_user",
  "action_mode": "analysis_only",
  "interaction_mode": "explain_tradeoffs",
  "retention_mode": "session_only"
}
```

这里是示意字段，不是要求所有任务都填同一套冗长表单。

它解决的是几种完全不同的边界：

**“替室友问”**：当前账户持有人的偏好不能直接用于室友。

**“只根据这个文件”**：其他记忆不能因为相关就被偷偷注入。

**“先比较，不执行”**：查询与推演允许，修改日历不允许。

**“发到群里”**：输出受众已经变了，私人背景不能原样出现。

**“这次只想吐槽”**：不应该自动进入规划和督促流程。

这个协议应当先于检索生效，并贯穿回答和工具调用，不能等模型已经看完所有私人记忆，再嘱咐它“不要提”。

尤其需要区分两个权限：

> **允许用于判断的信息，和允许向本次受众披露的信息。**

例如用户允许系统利用自己的忙闲状态约会，但不允许公开自己为什么没空。可以使用忙闲结果，不代表可以转发私人日程标题。

## 六、检索对象应该是“完整条件组合”，而不只是若干相似句子

第一轮的现实问题很短：

> “我现在去哪儿？”

但需要的信息可能分散在不同时间、不同来源：

```text
当前地点
今天没有骑车
电脑放在哪里
下一项课程
当前任务
最小有效学习时长
场所开放状态
用户对转场的厌恶
```

所以，不能只做：

```text
query → 向量检索前十条 → 塞给模型
```

我建议上下文构建器维护两种集合：

```text
必须知道的条件集合
已经取得、且可用于本轮的证据集合
```

然后做有目的的补齐。

对每个需要的条件，至少区分：

```text
已知且足够新
已知但过期
有冲突
未查询
查询失败
无权限获取
确认没有这项限制
```

**缺失不是一种统一状态。**

“用户没有时间限制”和“系统没有读到下一节课”，绝不能表现成同一个空值。

此外，要加入**候选结果后的补检索**：

初步考虑留在学校，可能不需要知道家里设备；但一旦候选方案变成“回家做项目”，就必须补齐回家路径、设备、下一次返校时间等依赖。

这不是每次把全历史读完，而是让检索随决策依赖展开。

也不能仅靠增大上下文窗口。早期的 *Lost in the Middle* 已经在其所测模型和任务中展示过：相关信息放在上下文不同位置，会显著影响利用效果。它不证明今天所有模型都有相同表现，但足以说明“塞进去了”与“可靠用上了”应当分开验收。([arXiv][2])

**新的验收点应该是：相关条件有没有进入上下文并影响结果，而不是召回了多少条记忆。**

## 七、“同一件事继续做”需要保存决定与理由，不只是任务摘要

E1 的“上次停在哪一步”，会暴露一种常见的设计缺口：

保存了任务标题、当前进度和最新结论，却没有保存：

> 为什么这样选？哪些方案已经试过？失败的原因还成立吗？

建议把进行中的任务至少展开为：

```text
目标及当前版本
已确认的约束
候选方案及其稳定编号
已选方案
被否决方案及否决理由
实际尝试及结果
尚未确定的问题
下一步需要解决的最小问题
相关证据、文件与产物版本
```

这里特别需要注意：**拒绝一个方案，不等于永久拒绝它。**

例如：

> “之前没有远程功能，所以没选校园里监督任务的方案。”

后来远程功能接通了，这个否决理由已经失效。系统应该重新考虑，而不是说“你以前明确拒绝过”。

同理，截图中的“第二个方案”应当绑定到当时的方案编号与图片区域，而不是永久记成“第二个”。

对于图片、语音、文档，原始证据定位也要展开：

```text
文本：消息及字符范围
文档：文件版本、页码或段落
图片：图片版本、相关区域或对象标识
语音：音频版本、时间片段、转写版本
```

这些都是指向证据的地址，不代表视觉或转写结果天然正确。

**任务连续性是“能够恢复当时的决策处境”，不是“记得任务名字”。**

## 八、刚说完的纠正、撤销和跨设备更新，必须有立即生效路径

上一版已经提出实时路径和后台提取，但这次需要更严格。

假设后台处理进度是：

```text
已收到用户消息：到第 120 条
已完成记忆提取：连续完成到第 117 条
已完成索引刷新：连续完成到第 115 条
```

第 120 条说：

> “刚刚说错了，我今天没有骑车。”

这时不能等全部后台任务结束，才停止推荐骑行路线。

因此，每次上下文至少由以下部分组合：

```text
可用的长期记忆快照
＋尚未合并的相关原始输入
＋本轮纠正与限制
＋必要的最新业务状态
```

这里的处理进度应该记录**连续完成的位置**，或者明确记录缺口，不能只记“最大已完成序号”。否则第 118 条失败、第 119 条成功，系统可能误以为前面都处理完了。

还需要在两个位置检查更新：

**形成方案时检查一次，真正执行或向外发送前再检查一次。**

因为在这之间，用户可能取消任务、撤回位置权限，或者另一设备已经改变时间。

这意味着上下文包需要带：

```text
使用的记忆版本
覆盖到的事件范围
关键动态事实的更新时间
本轮权限版本
依赖的目标与方案版本
```

发生相关变化时，重新验证受影响的部分，而不是盲目继续。

这是“我刚才已经说过了，你怎么还不知道”的实际技术落点。

## 九、承诺、主动提醒和自动操作必须共用生命周期，但不能混为一体

第三轮和第五轮一起要求：

> 系统既要记住答应过什么，也要知道谁答应了、到底做没做、什么时候不该再做。

至少需要区分：

```text
有人提出
本人接受
必要参与者确认
已授权执行
执行中
成功并取得回执
失败
结果未知
已取消
```

多人约定还需要保留参与者各自的确认状态，不能把“我同意了”当成“大家都同意”。

主动提醒则应该依赖一个仍然有效的目标，而不是单独保存成一句：

> “每天提醒用户准备竞赛。”

比较合理的是：

```text
目标：仍在准备该竞赛
触发条件：阶段节点接近或进度不足
依赖数据：准备进度、截止时间、可用时间
提醒偏好：何时可打扰、怎样提醒
暂停条件：用户暂停目标或进入免打扰状态
终止条件：目标完成、取消或失效
```

目标取消后，依赖它的提醒、准备任务和候选动作一起重新检查。

**“忘记一个旧目标”有时不是删除文本，而是停止它继续支配未来。**

另外，历史成功经验也不能成为未来操作的授权。MemoryGraft 在其测试的 Agent 系统中展示过：被污染的“成功经验”被存入并召回后，可能影响后续行为。这提醒我们，经验记忆需要保留来源和信任边界，不能因为“以前这样做成功过”就绕开本轮权限。([arXiv][3])

## 十、真正的记忆控制，需要同时覆盖“存储、使用、披露、删除”

第五轮说明，用户对记忆的控制不是一个开关。

至少存在以下不同要求：

> 可以在这轮使用，但不要长期保存。
> 可以长期保存，但只用于这个项目。
> 可以用于个人安排，但不能出现在群聊内容里。
> 删除事实，也停止从旧资料重新提取它。
> 保留历史，但不要再当成当前有效情况。

因此，一个记忆对象除了“有效或无效”，还需要明确其使用与保留规则。

尤其是“不要记住”：

不能一边承诺不写进 Profile，一边把完整内容保存在可无限重提取的原始日志里，而没有相应的保留与提取限制。

对于删除，需要追踪受影响的：

```text
原始来源中的相关内容
结构化记忆
任务摘要
个人简介
索引与缓存
尚未执行的后台提取任务
依赖该信息的提醒
后续模型调用要使用的上下文
```

至于已经发送到外部模型服务、已经展示给他人的内容，不能承诺通过本地删除就让所有副本倒退消失。产品要明确区分**立即停止使用、活跃数据删除、备份清理，以及无法撤回的既往披露**。

同时，“不再用”不一定都意味着删除：

旧住处可能需要用于解释过去的路线，但不能用于今天导航。旧兴趣可以作为变化历史，但不能不断压过新的兴趣。

**记忆应当支持改变，而不仅支持积累。**

# 把这些细化合在一起，一次请求应当怎样流动？

现在可以把流程压成一条更准确的主线：

```text
用户输入或获授权的数据变化
    ↓
解析：谁在说谁、真实还是假设、请求还是引用
    ↓
确定本轮使用协议
    ├─允许使用哪些来源
    ├─服务哪个主体与任务
    ├─输出给谁
    └─可以查询、建议还是执行
    ↓
恢复相关任务与记忆版本
    ↓
检索必要事实、偏好、经验、原始证据
    ↓
补齐当前决策所需的动态状态
    ↓
检查条件覆盖、冲突与缺失
    ↓
形成候选回答或方案
    ↓
检查候选方案新增的依赖，必要时补查
    ↓
回答；或经过权限与版本复核后执行
    ↓
保存可核验的结果与变更提案
    ↓
后台提取、核验、提交、刷新派生视图
```

**不是每次都必须调用很多模型。**

“这次只想吐槽”可能根本不需要读课程和位置；“下一节在哪里”不需要重建人生目标；“比较两条半年发展路径”才需要较深的历史与任务分析。

我会把调用深度作为本轮协议的一部分，根据任务、缺失信息和错误代价决定，而不是让所有问题都走最重的流水线。

# 再拿一个混合问题，检验这套细化是否真的有用

假想学生说：

> “先别按我的习惯。我替室友问：他明天要赶两个校区的课。如果他搬到新宿舍会怎么样？先给比较，不要改日程。另外刚才说他周三有空，后来他说没有。”

正确处理不能只是“记住室友周三没空”。

它应当同时满足：

**主体正确。** 当前安排对象是室友，不是账户持有人；不把室友的情况写进本人的 Profile。

**来源正确。** 只使用用户提供或明确共享的室友信息，不能因此擅自去读取另一个人的账户。

**现实与假设分开。** 原住处属于当前情况，新宿舍只是比较分支。

**时间正确。** “明天”按这次消息的时间与时区解析；“周三没空”的具体日期或重复范围不清时，不能自行扩成每周。

**更新正确。** 在适用范围相同的前提下，后来的明确纠正替代此前的“有空”，但保留更正依据。

**权限正确。** 只比较，不修改真实日程，也不发邀请。

**记忆边界正确。** 室友资料只保留在这个任务需要的范围内，不自动建立长期、跨用途的人物档案。

这一个输入就同时检验了主体、时间、假设、纠错、授权、作用域和上下文。

**真正的难点，往往不是某个单独模块缺失，而是这些边界在同一句话里同时出现时，系统还能不能保持一致。**

# 最后：二百个问题还不是测试集，必须继续变成“状态变化测试”

这也是对上一版设计最重要的补充之一。

只把二百个问题逐条扔给模型，看看回复是否像样，无法证明记忆系统可靠。因为很多问题的难点在于**之前说过什么、后来改过什么、哪部分不该被用到**。

每个正式测试用例至少需要：

```text
历史输入序列
当前已存记忆与任务状态
本次新输入
允许读取的来源
模拟的最新工具结果
应该使用的依据
禁止使用的依据
应该产生的记忆变化
禁止产生的记忆变化
允许或禁止的外部操作
回答必须满足的条件
```

例如“今天不跑只代表今天”，至少测试：

> 今天建议是否尊重例外；
> 明天是否恢复长期偏好；
> 后台提取延迟时是否仍正确；
> 摘要压缩以后是否保留时间范围；
> 换设备继续问时是否仍然一致。

LongMemEval 将长期记忆测试分成信息提取、跨会话推理、时间推理、知识更新，以及信息不足时不乱答，这些维度可以作为基础。([arXiv][4])

MemoryAgentBench 进一步强调准确检索、交互中的学习、长程理解和选择性遗忘。对你的产品，这尤其意味着：不能只测“还记不记得”，还得测“该不该继续用”。([arXiv][5])

我还会增加两类成对测试。

### 第一类：应该因为记忆而改变的回答

同一句“我现在去哪里学习”，分别放在这些历史下：

> 今天带了电脑／没有带电脑。
> 当前住处已经改变／下周才改变。
> 只想轻松读书／需要独立做难题。
> 当前是本人安排／替室友代问。

相关条件改变，答案应有相应变化。

### 第二类：不应该因为无关记忆而改变的回答

例如用户说：

> “只按这份材料总结。”
> “把这句话翻译成英文。”
> “这是一个虚构学生，按给定条件分析。”

这时，无关的私人经历、旧项目、吃饭习惯和性格判断不应混进去。

**个性化能力不仅体现在会使用个人记忆，也体现在知道什么时候不使用。**

最后，评价指标不能只有“回答正确率”，还应分别记录：

| 要检验的东西 | 具体看什么                  |
| ------ | ---------------------- |
| 记忆写入   | 有无错主体、错单位、遗漏条件、把假设写成现实 |
| 更新与遗忘  | 纠正是否及时生效，过期内容是否停止支配建议  |
| 上下文    | 必要依据是否进入，无权或无关内容是否被排除  |
| 连续性    | 任务、方案、拒绝理由和产物版本是否接得上   |
| 行动     | 是否取得授权，是否重复执行，是否虚报完成   |
| 用户理解   | 是否尊重当前需要，而不是一律规划、一律督促  |
| 可解释性   | 能否定位依据、区分事实与推测、指出关键未知  |

这些指标需要分开看。一个系统可能能准确背出用户说过的话，却仍然越权执行；也可能没有事实错误，但把一次吐槽强行变成生活改造计划。

## 我的最终判断

**上一版不需要推翻，但必须从“可靠的记忆存储与召回”继续推进到“有明确语义和权限边界的个人理解系统”。**

这次真正新增的核心不是更多 Profile 字段，而是：

**一句话应该改变哪个状态；一条记忆在什么情况下可以使用；一个决定何时只是设想、何时成为承诺、何时真正完成；用户改变之后，旧理解怎样停止干预。**

“十分懂你”并不要求系统每次都搬出你过去的经历。更好的表现可能是：

> 它记得你为什么拒绝过一个方案，但知道那个理由已经过期。
> 它知道你通常喜欢什么，但听得见你今天说“不一样”。
> 它能替你减少决定，却不会把你的探索当成授权。
> 它看得见你的长期目标，也允许你重新选择。

**这二百个问题足以暴露一批具体缺口，但还不能证明设计已经覆盖所有情境。下一版是否真的完善，要看这些边界被写成了可执行规则，并在连续对话、纠错、分支、失效和权限变化的测试里仍然成立，而不是看架构图又增加了多少方框。**

## 一、之前的讨论已经形成了什么地基？

### 第一轮解决的是：理解不能脱离证据

第一轮最重要的结论，不是选 PostgreSQL、向量数据库或某个记忆框架，而是把六种不同的东西分开：

**原始证据、可修正的记忆断言、进行中的事情、实时业务状态、派生摘要和检索索引。**

“用户通常喜欢晚上跑步”“用户今天已经跑过”“学校已经计入一次”“系统建议今晚跑步”，必须是不同对象。它们的来源、有效时间、更新方式和行动含义都不同。否则，系统很容易把自己的建议当成用户承诺，把用户自述当成官方事实。

在这层地基上，讨论已经给出了相当扎实的机制：候选提取、证据核验、条件化更新、事务提交、任务驱动检索、原文兜底、即时纠错、派生删除和并发控制。它们应当保留，而不是重新换一组流行术语。

### 第二轮解决的是：一句话应该改变什么，绝不应该改变什么

第二轮的真正突破，也不只是列出二百个问题，而是发现：

> 同一句话，可能同时包含代问、假设、纠错、请求和权限收缩。

例如“替室友比较搬寝室后的安排，先别改日程”，不应该进入“提取我的个人偏好”的单一路径。它需要正确识别主体、假设世界、任务和操作限制。此前讨论由此加入了话语解析、`world_id`、`ContextContract`、受众边界、承诺状态与当前交互方式。 

**所以，这次不应推翻这两轮的地基，而应把它们从“设计理念”推进为“贯穿应用入口的运行协议”。**

### 当前项目的问题，不是所有东西都该重写

项目导航里的原则分层、八类职责和事实所有权，值得保留。特别是它已经明确：用户理解不拥有第二份官方成绩、课程或体育台账；权限也不能由画像代替。 

真正明显的落差在于：文档报告的实际记忆仍主要是 `Memory{text,quote,createdAt}`；Harness 固定加入全部启用偏好与部分安排；删除偏好还不能使旧摘要和历史再推断完整失效。这与讨论中的目标，隔着一整套尚未落地的状态机制。 

因此，我选择的改造方向是：

> **保留已有产品能力，重建它们之间的运行中枢。**

这里有一个证据边界：本轮收到的是讨论、导航和 README，没有收到源码仓库及原始运行报告。因此，当前能力只能按“项目文档报告”处理，不能称为本轮已经独立审计。实施提示词已要求 Codex 在真实仓库重新核验，包括导航中地图/定位描述存在的阶段性不一致。

## 二、文献真正改变了哪些设计？

我整理了 **18 项论文、研究页面及官方文档来源**，在设计包里分别记录阅读范围、采用的机制和限制。没有把某个框架的基准成绩当成“在场”将来有效的保证。

其中最有影响的是以下几组。

| 研究或实现                            | 对这版设计的实际影响                                                                      |
| -------------------------------- | ------------------------------------------------------------------------------- |
| **LongMemEval、MemoryAgentBench** | 把“存对、找回、用对、更新、该忘时停止使用”分开测试；不能只问一次“还记得吗”，要做连续输入、纠错、时效和遗忘回放。([arXiv][1])          |
| **Hindsight、Graphiti**           | 保留事实、经历和解释的区别；把时间、来源与关系作为基础语义。我的选择是先在现有存储中落实这些语义，而不是立即搬进整套图数据库。([arXiv][2])     |
| **PersonaMem-v2、PersonaMem-v3**  | 不只检查偏好是否被记住，还检查是否在当前情境恰当地使用；增加过时、重复和不必要个性化的负向测试。([arXiv][3])                    |
| **Hermes 官方记忆机制**                | 借鉴小型常驻信息、历史检索和生命周期接入点，但防止内置记忆、外部 provider 与项目数据库成为互相竞争的三套真相。([Hermes Agent][4]) |
| **MemoryGraft**                  | “以前成功过的经验”也可能被污染。因此经验只能提供依据，不能自行变成运行指令，更不能变成未来行动的授权。([arXiv][5])                |
| **上下文工程的官方实践**                   | 采用按需读取、可恢复事项状态与有边界的压缩，但不把“上下文要短”理解为可以删掉条件、否定和例外。([Anthropic][6])                |

这些材料共同支持一个设计判断：

**更懂用户，不等于拥有一个更大的人物介绍；它更依赖对证据、条件、变化和使用时机的正确处理。**

另外，我也补查了会直接影响实现的细节，而不只读宏观架构。例如 SQLite 的 trigram 全文查询不能匹配不足三个 Unicode 字符的子串，所以“主图”“西操”不能只靠“开启 FTS5”就认为解决了。设计里加入了实体别名、中文短词索引和有界回退。([SQLite 官网][7])

DeepSeek 的当前工具调用协议也有需要保留特定 `reasoning_content` 状态的情形。因此，设计将**供应商协议状态**与**个人记忆**分开：需要时按协议回传，但不能把它写成用户事实；权限或来源边界收缩时，要重建干净的调用链。([DeepSeek API 文档][8])

## 三、完整 Harness 应该怎样搭起来？

### 1. 保留当前技术方向，但改变职责关系

这版设计没有要求你为了“高级架构”立即迁移到 PostgreSQL、Neo4j，或把应用整体替换成 Hermes。

我的建议是继续基于当前的 **Electron、React、TypeScript、SQLite、DeepSeek**，采用一个模块化单体：界面、权限、记忆、规划、行动和接入分清职责，但不拆成一堆服务。当前技术方向与已有地图、校园读取器、本地安排等能力，都有项目文档依据。

整体主线是：

```text
用户输入／获授权的数据变化
        ↓
可信身份、用途边界、保存规则
        ↓
解析主体、话语行为、现实／假设、时间
        ↓
建立本轮 ContextContract
        ↓
恢复事项，取得相关记忆、原文与动态事实
        ↓
检查必要条件、例外、冲突与缺失
        ↓
形成回答或候选方案，补查新出现的依赖
        ↓
按受众生成输出；必要时取得具体行动授权
        ↓
执行前复核 → 真实回执／结果未知
        ↓
受控更新理解、事项与依赖结果
```

这不是要求每轮都走最重路径。用户只想吐槽，可以不查课表；询问下一节教室，不必调出长期目标；只有复杂比较，才需要较深的历史与多轮取证。

### 2. 个人理解必须保存“取舍结构”，而不是只有标签

这版将个人理解分成几类：

| 内容    | 应当怎样表达                   |
| ----- | ------------------------ |
| 稳定事实  | 有证据、适用范围和有效时间，允许更正       |
| 条件偏好  | 在什么情境下，更偏向哪个选择           |
| 价值取舍  | 专注、自主、舒适、效率等发生冲突时，用户怎样比较 |
| 能力与资源 | 有什么设备、能独立完成什么、哪些表现需要过提示  |
| 当前状态  | 今天或此刻的情况，不直接变成长期人格       |
| 解释假设  | 系统可能怎样理解原因，明确保留不确定性和竞争解释 |

例如，“不去图书馆”不应该直接生成“不喜欢图书馆”。

可能的解释是设备在家、只有四十分钟、已经进入专注状态、不想重新收拾，或者这一次单纯想休息。**系统应该记住明确理由，并知道这些理由什么时候失效。**

因此我加入了 `DecisionExperience`：保存当时真正可用的选项、建议、选择、明确理由、实际结果，以及未观察到的部分。

它带来的变化很具体：借到电脑以后，曾因“没有电脑”被拒绝的方案可以重新进入候选；但这不等于用户已经愿意采用，更不等于系统可以自动安排。

### 3. 上下文不是“检索前十条”，而是补齐完整条件组合

对于“我接下来去哪儿”，字面相似度很难保证找到真正重要的信息。

所以设计先构建 `TaskNeeds`：这个判断必须知道什么，哪些条件只在涉及移动、设备、天气或外部行动时才需要。

然后结合结构化约束、实体与全文、关系展开、相关经历、原文兜底等路径取证。**明确的硬限制不与闲聊记忆竞争 top-k；偏好也必须携带适用条件和例外一起进入上下文。**

缺失状态被分开表示：

> 未查询、没找到、查询失败、没有权限、已经过期、存在冲突、确认没有该限制。

预算不足时，系统应该缩小任务、给条件性建议或询问一个关键问题，而不是删掉硬条件后继续给确定答案。

更重要的是，检索不只发生在回答前。候选从“留在学校”变成“回家做项目”，就新增了路线、设备、转场和返校时间依赖，需要再次检查。

### 4. “不要保存”与“不要使用”，必须在正确的位置生效

这一版加强了两个此前容易遗漏的边界。

**第一，保留判断在持久化之前。**
不能先把完整内容写进聊天日志、任务队列和索引，再发现用户说“这段只用于本轮”。仅会话使用的内容不能从日志、缓存或后台提取悄悄进入长期理解。

**第二，对外披露在模型输入处就做投影。**
给群里写可约时间，通常只需要忙闲区间，不需要私人日程标题。应该先生成可披露的忙闲投影，再交给对外草稿生成过程，而不是把私人详情全部给模型，再要求它“不要泄漏”。

同时，删除不只是删一条 Memory。它需要影响原始来源、摘要、索引、缓存、待执行任务、相关提醒和旧模型调用链。旧备份或离线设备恢复时，也不能绕过删除屏障。

### 5. 依赖机制连接了记忆、规划和行动

这是我认为整个 Harness 最需要补牢的一处。

一个方案必须知道自己依赖哪些事实、偏好、权限、能力和假设，以及它们的版本。随后：

* 课程变化，只重验相关空闲时段和路线。
* 用户取消目标，相关提醒和准备任务停止。
* 某个资源可用了，旧拒绝理由重新检查。
* 权限被撤回，正在运行的任务不能继续沿用旧上下文。

这里的核心不是每次都重新规划全部生活，而是**准确知道什么受影响，并尽量保留没有受影响的已接受安排**。

### 6. 行动系统必须承认“结果未知”

本地保存安排、用户接受方向、外部预约成功，是三回事。此前讨论和项目导航已经强调了这条边界；这版将它进一步落成明确状态机和执行协议。 

例如外部服务已经成功，但响应丢失：

```text
已批准 → 派发中 → 结果未知 → 核查 → 确认成功／确认失败／仍无法确定
```

不能直接把超时当成失败，然后再约一次。

批准还必须绑定具体参数、受众、版本和期限。生成方案时检查过权限，不代表执行时仍有权限；派发前要再查一次。

### 7. 插件、工具和 Skill 各自承担什么？

我没有把“user information”设计成一个包办所有事情的大插件，而是明确区分：

**业务域**决定事实和规则归谁所有；**Provider/插件**连接外部来源；**Tool**提供受控操作；**Skill/TaskRecipe**描述某类任务的方法与信息需求。

地图接入空间能力，校园读取器提供分域记录，天气提供有地点和时间范围的预报。它们不能各自建立一份随意更新的“用户总档案”。

现有 `look_up` 可以继续作为模型侧的高层入口，批量查询、刷新、去重和底层端点选择由 Harness 内部处理。这样既不需要给模型暴露几十个重叠工具，也不会把所有职责塞进一个无边界的工具。

## 四、给 Codex 的提示词，怎样防止它又只交付一个外壳？

最终提示词已经合并了架构、实施步骤、验收和未来接口要求。它要求从现有应用入口改造，而不是另起一个演示项目。

实施顺序是：

> **基线保护 → 权限与证据 → 记忆与上下文 → 事项与依赖 → 行动与恢复 → Provider及扩展 → 真实入口、质量与打包验收。**

其中有几项硬要求。

**新代码必须被原入口使用。**
只有测试函数调用 `ContextCompiler`，但原来的输入框还在固定拼接全部偏好，不算完成。

**必须检查实际数据流。**
验收观察真实数据库、检索访问、发给模型的请求、外部请求次数和用户可见状态，不能只看最后的回复是否像样。

**机制测试与模型质量分开。**
模拟模型能帮助检查幂等、撤权和崩溃恢复，却不能证明真实模型能正确理解“只是今天”“替室友问”“只根据这个文件”。

**未知接入不得伪装成可用。**
没有真实外部预约、手机健康或邮箱连接，就明确未接入；但相应契约、错误处理和受控模拟不能省略。

配套验收资料包括原讨论的 **40 个方向、200 个问题**，以及新增的 **94 个多轮状态验收规格**。这些规格包含初始状态、输入或故障步骤、禁止行为和预期检查，不只是把二百句话逐个扔给模型。

例如，删除测试不止问“你还记得吗”，还要检查：

> 删除后重启、旧 worker 完成、重新提取旧来源、恢复旧备份，是否会让内容重新进入有效理解。

外部行动测试也不止模拟成功，而要模拟“服务已经执行但回执丢失”，观察是否产生第二次副作用。

**这些是验收规格，不是本轮已经通过的应用测试。**本轮完成的是设计包的文件、编号、交叉引用、JSON及 TypeScript 类型样本检查；真实应用、模型和连接器验证仍需在仓库中执行。相关边界写进了交付包的验证报告。

## 五、第五步的优化：未来空间不只是多几个插件

我单独写了 **16 项扩展契约**。每项都有体验目标、数据结构、插入点、权限、失败方式、本轮应落实部分和真实激活条件。

其中更值得保留的，不只是手机、语音和外部服务，而是以下几种能力。

### 帮用户保留选择，而不是催促所有决定

当用户同时考虑科研和实习，系统可以识别共同准备、最晚决定时间、退出成本和不可逆步骤。

对应的是 `OptionWindow`、准备依赖与分支比较，而不是马上把其中一个方向写成用户目标。

### 记住拒绝的理由，也知道理由已经过期

“不在学校做项目”可能只是因为没有设备。

设备变化后，应该重新检验方案，而不是永远记住“用户不喜欢在学校做项目”。这需要资源能力、拒绝理由和方案之间真正存在依赖关系。

### 允许用户探索过去不喜欢的生活

个性化不能变成不断重复过去。

用户明确要求探索时，系统应该弱化历史软偏好，但继续保护明确禁忌、现实限制与行动授权。一次尝试也不能立刻改写长期身份。

### 学习陪伴知道“用户自己走到了哪里”

看过答案、得到提示后完成、独立找到入口，是不同表现。

因此预留的不只是题库接口，而是学习观察、辅助程度、已公开内容和提示范围。没有这些对象，“记住学习进度”很容易退化成记录做过哪些题。

### 多人协作不需要交换完整私人生活

多人约时间可以共享忙闲投影、通勤缓冲和确认状态，而不共享私密原因。

它要求受众投影和逐参与者承诺，而不是给四个人各建一份互相可读的档案。

此外，扩展规范还覆盖多模态证据、跨设备冲突、注意力预算、学校规则版本、隐私存储与导出、外部通知、执行核查与补偿、反馈学习、经过审核的方法升级，以及模型协议替换。

**为了避免这些接口只是摆设，提示词还要求一个“陌生扩展测试”：**登记一个协调器原先不知道的借用设备能力，使它通过真实的注册、取证、依赖更新和撤权流程运行；不能在主循环里针对这个插件名称写特例。

## 最后，哪些地方可以等待，哪些不应该再留空？

可以等待的是：真实手机权限与后台行为、第三方接口是否支持核查和幂等、第二学校规则来源、多人账号服务，以及真实学生对主动提醒的反馈。这些需要外部证据或产品决策，不能靠想象填成已接入。

**不应该再留空的是：主体和来源边界、证据与记忆更新、即时纠错、遗忘传播、条件覆盖、依赖失效、行动授权、未知回执、受众投影，以及它们如何贯穿原应用。**

这些已经在设计中落到具体对象、协议、更新路径和验收要求。

实际交接时，把 ZIP 解压到仓库旁，在最终提示词顶部填入两个路径：**真实仓库路径**和**设计包路径**，再交给 Codex。

这轮最重要的完成标准，不是它是否做出了更多插件，而是：**同一个用户改变想法、纠正事实、取消目标或收缩权限之后，系统的下一次读取、判断和行动，是否真的随之改变。**

这里必须准确区分：**这是原函数运行结果，不是完整应用的真实模型评测，也不证明错误日程已经被写入。**例如，同义登记句的明确委托标记错了，但在这个夹具里 `prepare_action` 仍然可见，不能夸大成所有写入工具都消失。

但最重要的结论已经成立：

> **模型还没有开始判断，程序就已经根据你的用词，改变了它能做什么。**

这就是一个很强的模型也可能被用得很差的直接机制。

## 1．所谓“语义提案”，实际没有语义模型参与

`policy.ts:55–149` 的 `proposeInterpretation`，并没有调用模型。它靠正则产生意图、来源、参与方式、主体与若干置信标记。

例如，本地登记大体由两组词组合判断：一组包含“帮我、顺手、记一下”，另一组包含“会、会议、安排、提醒”。

所以：

> “帮我分析为何我开会时总会紧张。”

能命中“帮我”和“会”，于是得到登记标记。

这不只是某个正则写坏了。

**给结果起名 `InterpretationProposal`，不会使它成为语义理解。给它再加一个 `confidence`，也不会使它获得可信度。**

更严重的是，下游真的拿这些结果决定工具是否可见。代码注释说它只是“routing hint”，但行为上，它已经影响了主模型的能力边界。

## 2．“让回答简短”，竟然变成“不要充分调查”

`coordinator.ts` 会根据“一个方向、第一步、只要一句”等表达判断简单对话，再移除 `delegate` 等工具。

但下面两件事完全不同：

> 我只想看一句结论。
> 你只需要做一秒钟的工作。

用户可能要求：

> “帮我把两份合同核对清楚，最后只告诉我能不能签。”

输出可以很短，内部工作却必须充分。

当前设计把**表达成本**与**求解成本**混在一起，实际上会奖励“少查、少做、快收尾”。

## 3．子代理并非完全不存在，但它没有成为可靠可用的能力

新包的 `harness.ts:584–681` 确实有实际子循环、并行调用和只读限制。因此，不能说源码里完全没有 sub-agent。

问题在于：

**能否使用它，先被词面规则控制；子任务的上下文，又仍然受到父请求解释的影响。**

此外，它需要的不只是一个 `Promise.all`：还包括子任务自己的目标、独立取证、明确结束条件、结果被父代理实际消费、失败保留、定向补充、取消、预算与恢复。

“代码里有 delegate”与“用户可以稳定地获得多 Agent 协作”，隔着一段实质距离。

## 4．它默认关闭了显式 thinking 模式

新包 `provider.ts` 中，默认请求参数包括：

```text
max_tokens: 4096
thinking.type: options?.thinking || "disabled"
```

主生成路径没有传入 thinking 选项。

因此，这条路径默认没有启用 DeepSeek 的显式 thinking 模式。**这不等于模型完全不会推理，也不能说打开以后所有问题都会解决。**但在比较“模型本来有多强”和“Harness 把它用成什么样”时，这个变量必须对齐。

官方文档明确提供 thinking 控制，并规定了工具调用情形下的续接字段要求；实现必须按实际选定的接口和版本验证，而不是只在元数据里写一个“支持 thinking”。([DeepSeek API Docs][1])

## 5．“高情商”又被缩成了年龄与短句模板

新提示词确实把“小朋友、长辈或已经很累的人”放到一种统一要求下：短句、一步。

我要纠正一个证据边界：**本次没有在所读核心里确认“匹配老人两个字就进入专门路由”的代码；确认的是提示词加入了这类统一模板。**

但这个模板本身已经有问题。

一个长辈可以要求非常深入的分析；一个孩子可以已经懂很多；一个疲惫的人也可能明确要求你把来龙去脉讲清。用户说“没讲清楚”，不一定需要更短，可能恰恰需要更充分。

这不是加一条“用户要详细时例外”就结束的问题。应该推翻统一前提：

> **交流方式由当前需求和反馈决定，不由年龄词、情绪词或固定人格分类决定。**

# 二、为什么读过 Hermes，最后还能做成这样？

因为**看到了组件，却没有保留组件之间的控制关系**。

拿到记忆表、证据收据、权限结构、计划对象、审批状态以后，很容易觉得架构越来越完整。但一个关键问题一直没被回答：

> **究竟是谁决定下一步？**

当前路径更接近：

```text
程序用词表决定用户是什么意思
→ 程序决定需要哪些资料
→ 程序决定能给模型哪些工具
→ 程序决定应该用什么交流方式
→ 模型在这个范围内生成回复
```

在这种结构里，大模型主要负责填空和表达。

所以，即使外围工程越来越完整，实际智能也可能越来越弱。**它把开放世界里最难的部分交给了最弱的词法判断，把模型最擅长的语义能力留到了最后。**

原讨论其实已经明确说过“模型负责解释，程序负责提交、权限与一致性”，也写过可以让 Hermes 接统一记忆服务，不必重做一个大而全的 Agent 框架。 

而那二百个问题，原文明确说明是检验设计的假想输入，**不是二百项必须逐个编码的功能**。

所以，我上一版真正错的地方，不是“没有提到语义理解”——提到了很多次。错误是：

**没有把语义决定由谁作出、模型如何获得原话和修订权、哪些词法控制路径必须禁止，落实成比新增字段更优先的工程要求。**

再加上没有强制先做最简 API、原生 Hermes 与自研方案对照，就容易形成这样的开发循环：

> 用户指出一个失败 → 加一条规则 → 原句通过 → 宣布修复。

这不是泛化，而是在维护不断增长的例外表。

# 三、从第一性原理看，Harness 本来是怎么出现的？

## 1．最初的问题不是“怎样分类用户”，而是“模型怎么接触世界”

一个云端模型接收消息，返回内容。

单独调用一次 API，它可以说“已经预约”，但这句话本身不会在预约系统里产生任何记录。

因此，需要一个程序负责：

**把模型提出的工具调用交给真实函数执行，再把真实结果交回模型。**

最小的 Agent 循环大致是：

```text
给模型：用户原话、必要前情、可用工具说明

模型决定下一步：
    直接回答；或者请求调用工具

宿主：
    检查真实权限与参数
    执行工具，取得观察
    把成功、失败、缺失或不确定交回模型

模型依据新观察继续判断
```

这里最重要的不是 `while`，而是**控制权属于模型与环境反馈的循环，而不是一开始就写好的语义分支**。

OpenAI 公开的 Codex agent-loop 说明就是这一结构：模型产生最终回复或工具调用，宿主执行工具并追加结果，再次请求模型；上下文长度管理也是运行时职责之一。([OpenAI][2])

因此，你说“我们没有本地大模型，也可以发云端 API”完全成立。

**模型参数放在云端，不妨碍本地程序拥有完整的 Agent 循环、工具系统和子代理运行时。**

## 2．后来为什么增加了记忆、子代理、审批、恢复？

因为真实任务暴露出更多问题，而不是因为用户类型越来越多。

| 遇到的问题            | 增加的机制          |
| ---------------- | -------------- |
| 一次生成的计划碰到现实变化就失效 | 模型—动作—观察循环     |
| 任务需要查询或修改外部系统    | 结构化工具调用、真实执行   |
| 长任务超过上下文窗口       | 压缩、外部笔记、原文回读   |
| 多个独立方向需要调查       | 子代理、任务协调与结果汇总  |
| 工具调用可能产生后果       | 权限、审批、幂等、核查与补偿 |
| 用户中途改口、进程失败      | 中断、重定向、检查点和恢复  |
| 不知道到底哪里做错        | 运行轨迹、环境终态与评估闭环 |

历史上，2022 年的 ReAct 就研究了推理与行动交替，利用新观察继续调整；2023 年的 function calling 则提供了更直接的结构化模型—函数接口。它们不是所有 Agent 的唯一起源，但能清楚说明这一演变方向。([arXiv][3])

MemGPT 和 Reflexion 分别探索了有限上下文之外的记忆调度，以及利用反馈改善后续尝试。它们强调的是**让系统能够继续工作、利用过去的结果**，不是把所有未来问题提前写进一个分类表。([arXiv][4])

到了可交付产品，真正重要的工程工作变成：如何维持循环、管理状态与资源、正确实施边界、让客户端看到实际事件。Codex 的 App Server 就体现了把引擎与客户端分离的路线。([OpenAI][5])

## 3．为什么有限工具可以处理远多于二百种场景？

因为程序编码的是**操作的语义**，不是**用户句子的全集**。

日历工具需要标题、日期、时间、参与者，这很正常。

但工具不应该要求：

> 用户必须出现“会议”“安排”或“提醒”，才允许模型判断是否需要日历。

同样，委派协议可以有目标、材料、权限、预算、结果状态，但不需要提前定义“孩子代理、老人代理、雨天代理、考试代理”。

**有限的搜索、读取、比较、草拟、修改、核查和委派能力，可以依据不同观察动态组合。通用性来自这种组合，而不是更长的场景目录。**

# 四、关键词检索不是罪魁祸首，方向搞反了才是

你问“为什么还要检索关键词，我们让 AI 理解不行吗”，这里必须分清两种情况。

**合理的情况：**

模型判断需要找一条调课通知，于是用“调课”搜索；没有找到，再换“教室调整”、课程名、老师名，或者回读相关消息。

这是模型利用精确检索工具，既高效，也容易追溯。

**错误的情况：**

程序发现用户没有说“调课”，所以认定这不是查询任务，不给查询工具。

前者是**模型选择关键词作为手段**；后者是**关键词替模型决定任务与能力**。

所以我不会建议把全文索引全部删除，也不会声称换成向量检索就解决问题。一个固定向量检索器漏掉信息后，若主模型同样无权继续查，也会造成相似瓶颈。

最终设计保留全文、实体、时间和原文检索，让模型能够提出查询、根据结果修改查询、读取必要上下文。向量检索可以增加，但不应成为唯一真相。

Anthropic 的上下文工程文章甚至直接指出，脆弱的 if/else 式硬编码提示是一种失衡；另一端，过于笼统、默认模型知道一切的提示同样不好。正确方向是清晰的原则和有用的上下文，同时给模型留下推理空间。([Anthropic][6])

**把正则搬成一百条 prompt 条件，也不自动变成了优秀 Harness。**

# 五、这次查到的成熟实现，究竟有什么共同点？

我没有把它们按营销介绍排一个“工业成熟度分数”。主要检查的是实际入口、循环、工具、子代理、状态、扩展和已公开的限制。

| 实现                       | 值得借鉴的东西                           | 不能想当然的地方                                |
| ------------------------ | --------------------------------- | --------------------------------------- |
| **Hermes**               | 可直接编程调用的 `AIAgent`、完整工具循环、独立委派与控制 | 默认记忆、工作区、工具和日志未必符合在场的数据边界               |
| **Codex**                | 可复用核心循环，客户端与引擎通过事件、线程、回合和审批协议交互   | 不能只因支持可配置接口，就假定 DeepSeek 可无缝替换全部协议与模型配置 |
| **DeepSeek Harness／DSH** | 模型、循环、工具、界面等通过插件与生命周期组织           | 官方仍标注 developer preview，不能直接称生产安全就绪     |
| **DeepSeeker 桌面产品**      | 真正复用 DSH，自己负责桌面安装、启动监督和产品体验       | 它是独立社区产品，不等于官方 DSH                      |
| **DeepSeeker-Code**      | 独立流式循环，多个入口共享 core，真实工具调度与事件      | 面向单人编码；源码也有启发式，不是“完全没有规则”的神话            |

上述对应公开实现与文档。([Hermes Agent][7])

此外，我也比较了 **Deep Agents JS、Pi SDK 和 OpenCode**。它们分别提供可配置的 Agent 底座、可嵌入会话与工具接口、主代理与子代理机制，是实际候选，不只是几个热门名字；但它们的默认文件、记忆、权限与产品定位仍然需要核查。([Docs by LangChain][8])

这里有两个特别重要的发现。

### 第一，“DeepSeeker”与官方 DSH 不该混成一个东西

我查到了两个容易混淆的项目。

`deepseeker-app/DeepSeeker` 明确说：DeepSeek 提供 Harness 核心、插件与 Web UI，它自己负责桌面包装、安装和面向普通用户的产品工作。**这本身就是“产品不需要自己发明通用引擎”的具体例子。**([GitHub][9])

`xknk/deepseeker-code` 则有自己的流式 `runAgent.ts`。我读到的主循环确实调用模型、调度工具、回写观察，并处理取消和事件；但里面也挂接了复杂度与早收尾 nudge 等启发式。不能因为它是别人的项目，就把它描述成完美无规则系统。([GitHub][10])

**我们要检查规则放在哪里、产生什么影响，而不是把“别人也用了规则”或“别人叫 Agent”当结论。**

### 第二，大公司的多 Agent 不是“每条消息都排队经过七个 AI”

Anthropic 公开的研究系统使用主代理组织独立调查，再综合结果；同时也讨论了额外成本与任务适配问题。可并行的信息研究，与高度耦合的任务或普通交流，并不适合完全相同的编排。([Anthropic][11])

因此，多 Agent 当然可以，而且在你的项目中应该真正能用。

但应该是：

> 主代理发现几个可独立查证的方向，启动工作者；
> 工作者获得自己的目标与工具，实际取证；
> 主代理拿到材料后继续判断。

而不是：

> 意图 AI 分类 → 情绪 AI 分类 → 画像 AI 分类 → 规划 AI → 回复 AI → 共情 AI。

后一种结构如果仍然早早固化错误解释，只是把便宜的坏流水线换成了昂贵的坏流水线。

# 六、第一轮重设计，再反过来审查：哪些方案仍然不该选？

## 方案 A：把所有正则换成几个模型

这比纯关键词有进步，但我没有选它作为最终方案。

因为它仍然可能要求每条消息经过完整流程；前一个模型如果只传一个标签，后面的模型仍然没有原话和修订权；不同角色又可能只负责自己的输出，没有一个角色对用户最终得到的帮助负责。

**真正应该替换的是控制结构，不只是分类器的实现技术。**

## 方案 B：直接把默认 Hermes 放进 Electron

这比继续修补当前循环更值得先试，而且必须作为强基线。

但作为最终个人数据产品，不能不加处理地采用默认配置。

Hermes 的外部 memory provider 是添加式接入，不能默认认为它替代了内置记忆；上下文文件、提示组装与委派日志也有自己的路径。它们可能把在场本来禁止保存、禁止读取或不应进入学生对话的东西重新带进来。([Hermes Agent][12])

此外，官方 Python 嵌入方式采用源码环境，并没有一个受支持的普通 wheel 安装路径。Windows 打包、版本固定、进程监督和升级是真实工程成本。([Hermes Agent][7])

因此，不能把“传入 `skip_memory=True`”等同于“所有缓存、子代理日志、错误日志都不会保存”。

## 方案 C：真正复用 Hermes 引擎，在场控制自己的业务与数据边界

这是最终选择。

选择它，不是因为本轮已经测出 Hermes 的回答最聪明，而是因为：

**它已经提供了你当前最需要真正落实的循环、工具、委派与程序化控制；继续自研这些通用部分，没有得到足够的收益证明。**

相应代价是增加 Python sidecar 与一层窄适配。这个代价我明确接受，但也给出了否决边界：

> 如果所谓薄适配最后要求重写主循环、复制大段上游核心、为每个任务加入专用逻辑，那就已经失去了采用现成底座的意义，必须暴露这个具体阻塞，不能改名后继续自研。

# 七、最终架构：只保留一个真正负责对话的主循环

整体结构是：

```text
原有聊天、地图、日程 UI
           ↕
在场宿主：身份、权限、业务事实、记忆提交、行动与回执
           ↕
受控 Hermes 运行时：主 Agent ＋ 按需工作者
           ↕
用户已配置的 DeepSeek API
```

**在场不再自己拥有另一套竞争性的模型—工具循环。**

## 1．主模型直接看原话，决定怎样帮助

主 Agent 获得当前输入、必要近期的真实角色历史、正在处理的事情、明确控制、时间和可用能力。

不再要求每轮先填完：

```text
InterpretationProposal
→ TaskNeeds
→ interactionMode
→ 完整计划
```

才允许它回答。

它可以直接回应，也可以检索、读取、提问、起草、请求动作、委派或修复。工作笔记可以帮助恢复，但不是每句话必须完成的行政表格。

**“我只想听一句结论”影响最终表达，不自动禁止内部调查。**

## 2．宿主只守它真正能确定的边界

程序负责账号身份、实际连接、对象权限、参数格式、版本、费用与预算、事务、取消、回执。

模型负责理解请求、选择资料、判断下一步、组合工具、分析取舍与选择交流方式。

这里仍然需要少量语义控制处理：用户可能说“只用附件”“不要保存”“先别发送”。这些限制不能等到全量读取私人历史、写完数据库以后才发现。

所以，最终方案保留一个**只解释控制要求的小型模型调用**，在当前输入暂存内存的阶段处理来源、保留、披露与动作限制。它不判断人格、情绪类型或完整计划，也不能扩大既有账号权限。

这通常增加一次小调用，是明确的隐私与延迟取舍，不隐藏成本。强制的界面控制仍然是更确定的边界。

同时我也写清了限制：本地“不保存”不等于云模型服务从未处理数据；不能先把“不要发到云端”发到云端解析，再声称没有外发。相应场景必须有发送前控制或真实本地处理能力。

**没有哪个模型解析器能替我们形式化证明永远读懂所有限制。**

## 3．工具可见性不再取决于用户有没有说某个字

新的规则是：

> **实际已连接、已授权、该角色允许、用户显式启用的能力，可以提供给模型。**

工具过多时，主模型始终能发现能力、查看更多结果和重新搜索。第一次没有找到某工具，不会被当成永远禁止使用。

工具描述围绕真实任务，而不是内部表名。返回结果区分未找到、未授权、未连接、过期、部分覆盖、失败与结果未知。

**模型不仅能调用工具，还要能看见失败以后继续想办法。**

## 4．子代理是独立工作者，不是几段角色提示

复用 Hermes 的真实委派，但对子代理创建、权限与日志做受控适配。

每个工作者获得的是开放的任务目标、必要材料、允许来源与工具、预算和结束条件。它有独立 API 调用、独立上下文与真实工具观察，不再预先继承父任务那份错误的关键词需求。

默认从较小并发开始，依据授权预算调整；不是用户说出“多个”二字才开放。

主代理持续负责对用户的交流。工作者不轮流接管用户；它们交材料，主代理核对冲突、遗漏和依据，再形成答复。

尤其要记录：

> 子任务已启动，不等于已完成；
> 已完成，不等于父代理已经消费；
> 补充指令已入队，不等于工作者已经采用；
> 用户取消，不等于外部后果已经撤销。

这些是运行状态，而不是人群分类。

## 5．记忆的内容保持开放，元信息保持精确

原讨论中的证据、断言、经历、事项和实时事实分离，仍然保留。

但记忆内容不应被限制在一组手写谓词里。

可以保存有来源的自然语言：

> “拒绝这个方案的原因是，当时电脑只能在家使用；现在借到电脑，这个原因暂时失效。”

而不是只有：

```text
likes_library = false
```

主体、来源、时间、用途、版本这些由宿主控制；条件、理由和取舍可以保持开放表达，由模型在新情境中理解。

本轮原话和明确纠正立即参与回答，长期整理放后台。没有提取成断言的原文仍然能检索。一个会话可以包含多件事，一件事也可以跨会话继续。

**长期记忆应当帮助模型理解变化，而不是给用户固定身份。**

## 6．真正的行动仍然需要精确协议

这里不能走向另一个极端：“既然模型很灵活，那它说什么就执行什么。”

明确、可撤销、已启用相应处理政策的本地动作，可以低摩擦地完成；外发、影响他人、费用和不可逆动作，需要具体授权。

但“明确委托”的语义应由模型结合原话、前情和对象判断，不再由“帮我＋会”决定。

事件、待办、截止、提醒、计划时间块分别处理。未知结束时间不自动填一小时；超时不自动重试；执行结果用真实回执表达。

系统应该能把事情真正做完，也应该能准确说：

> “已经写入本地安排，但还没有同步到外部日历。”

而不是把所有状态统一成“完成”。

## 7．高情商留在持续交流中，不另设一个流水线末尾的“安慰器”

一个持续负责的主代理，更容易保留：

用户现在为什么不耐烦，刚才哪一步没有被接住，已经明确不希望什么，还有哪件小事尚未处理。

当用户要分析时认真分析；需要先说完时不抢着规划；用户只剩一点精力时，尽量把能查的查好、明确交代的办完，而不是再发一个选择题问卷。

**“温柔”不是固定句式，“人性化”也不是永远简短。**

对当前请求作出正确参与，比事后加三句安慰更重要。

# 八、再攻击最终方案：怎样避免换成 Hermes 以后又长出同一坨东西？

我在反向审查里设置了几个明确的失败条件。

**第一，桥接层不能长成新的关键词大脑。**
它只传身份、许可、能力、状态、事件和原话，不能再次根据用户句子删工具或签发意图。

**第二，不能以为一个 hook 就覆盖所有安全路径。**
Hermes 的 `pre_llm_call` 是回合级入口，并不是每一次内部模型请求前都执行。权限、预算、撤销必须在真实传输口和宿主工具端实施，不能望文生义。([Hermes Agent][13])

**第三，不能出现第二套记忆和隐藏保存路径。**
主会话、压缩、子代理日志、错误、缓存和恢复都要进入受控存储路径。只关闭一个记忆开关不够。

**第四，不能以安全为由永远不做事。**
纯倾诉不得乱执行；但倾诉加明确登记又必须能登记。这两条要同时通过。

**第五，在场新增的层不能获得免于对照的特权。**
同模型、同工具、同合法资料下，如果轻配置 Hermes 反而更能听懂、工具使用更好，而在场只是更慢、更啰嗦，那么该删除的是在场造成退化的增强，不是给基线制造劣势。

这一点直接回应你的疑问：

> **是的，倘若自己做的层不能比直接套 Hermes 带来实际价值，就不应该为了“这是我们的架构”而保留。**

在场真正值得自研的是校园数据与地图、生活事项、可控记忆、真实代办和连续交流体验，不是为了证明自己厉害而再发明一遍 Agent 循环。

---

# 九、给 Codex 的验收不能再是“跑过了”，必须是“找到原因并改好了”

这里要区分两个循环。

**产品运行循环**：Agent 根据工具观察继续工作。

**开发改进循环**：Codex 根据失败轨迹修改代码、提示、工具与上下文，再跑真实模型。

你说的“验证一次，什么都不改”，只完成了第二个循环里的观察，根本没有完成改进。

最终提示词要求：

```text
真实失败
→ 找到最早发生分歧的位置
→ 提出可检验的原因
→ 做一个一般机制修复
→ 重跑原失败
→ 重跑未用于写补丁的新表达和反例
→ 检查相关回归
→ 再进入独立留出评估
```

OpenAI 公开的 agent improvement loop 也把轨迹、反馈、评价、诊断、Codex 修改与再次运行连接起来，而不是把生成一份失败报告当终点。([OpenAI Developers][14])

## 1．首先用你已经提供的 API，而不是机械宣布缺 Key

提示词已经明确：

**沿用用户已交给 Codex 的配置入口，实际尝试请求。**

需要核对的是 endpoint、实际模型、thinking、输出上限、工具协议和续接；不能打印密钥，不能扫描其他项目找替代凭据，也不能未尝试就套用旧文档的 `not_run`。

首先证明能真实生成、真实调用工具、把观察交回模型、启动独立子任务和取消。

但 `200 OK`、有文本、有 `tool_calls`，仍然都不等于任务完成。

## 2．四组对照，明确是谁把效果弄差了

| 对照               | 用来回答什么                  |
| ---------------- | ----------------------- |
| 最简 DeepSeek 工具循环 | 模型在不过度加工的条件下，原本能做到什么？   |
| 当前在场路径           | 现有 Harness 到底在哪一步退化？    |
| 轻配置 Hermes       | 直接使用现成底座能达到什么水平？        |
| 最终在场集成           | 新增记忆、边界和产品逻辑究竟带来收益还是伤害？ |

模型、工具、合法资料与模式尽量对齐，额外调用和成本单独报告。

工具在第一轮请求里已经消失，就先修工具暴露，不改共情文案。

工具存在但没调用，再查工具描述、上下文和模型配置。

工具调用了，但结果没进入下一轮，就修协议。

正确证据都在，仍然答错，才继续检查推理、条件利用和表达。

**不再把所有失败统一翻译成“再提醒它一句”。**

## 3．修复必须跨表达成立

每次语义修复，至少重跑原例、五个没有用于写补丁的新表达，以及相邻反例。

例如，修复查询能力不能只加“明儿”“头一节”两个词，而应该让：

> 同一个已授权查询需求，无论怎样表述，都不会因为一个初始词法分类失去工具。

反过来，保留否定、引用与主体变化的差别，不能把真正不同的语义也粗暴判成同一种。

**原句对了，新说法仍然错，这个补丁不准合入。**

## 4．关键词补丁在代码和 prompt 里都不允许

禁止新增：

用户正文 → `contains/regex` → 意图、授权、工具禁用、人群模板。

也禁止把失败原句与标准答案逐条塞进 prompt。

可以修改一般原则、工具描述、上下文组织、真正的模型参数、调用协议、状态传递和执行机制，但必须说明：

> 为什么这个改动解决的是一类问题，而不是这一次句子？

静态检查可以找可疑路径，但不能凭“代码里没有正则”就认证泛化；prompt 同样可能过拟合。

## 5．判分器必须能抓住“漂亮地什么也没做”

故意让系统不写日历，却回答“已保存”；重复执行两次；偷偷读取禁用记忆；子代理没有真正请求模型却显示完成。

独立检查必须失败。

如果这些都能通过，先修判分器，而不是继续提高系统分数。

Anthropic 的评估说明明确区分尝试、运行轨迹和环境终态，并讨论代码、模型与人工判分各自的作用。对在场而言，**任务是否完成与交流是否合适，必须同时看**，不能用列表数、安慰词或工具调用次数替代。([Anthropic][15])

# 最后的结论

这次最关键的改变，不是增加了几个更高级的对象名，而是明确撤销了当前错误的控制权：

**自然语言关键词不再有权替用户确定意图、替模型决定必要能力、替交互规定固定情绪模式。**

同时也没有走向“全部交给几个 AI 自由讨论”的另一端。真正的身份、权限、业务事实、执行后果和恢复，仍由程序负责。

本轮已经实际运行了源码函数探针，并重新运行确认了结果；没有在这里运行完整 Electron、真实 DeepSeek 或 Hermes 集成。因此我不会把设计文件完整，冒充为新版产品已经验证成功。最终提示词要求 Codex 在你已经配置好的环境中完成那个闭环。

**在场不需要学会把二百种场景写进二百个分支。它需要给模型保留理解原话、发现能力、取证、协作和修正的空间；然后用真实运行证明：换一种说法，不需要再改一次代码。**
