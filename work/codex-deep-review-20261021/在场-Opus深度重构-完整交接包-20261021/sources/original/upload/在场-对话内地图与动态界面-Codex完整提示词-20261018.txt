仓库提供的公开地图预览已经在云浏览器打开并观察过。本次浏览器实际进入 OpenLayers 平面兼容路径；公开托管预览也不等同于最新源码版本。因此，本文件不把最新 2.5D 效果、完整路线播放或帧率视为已经验证。实施后请运行当前代码观察相关变化。

## 二、产品方向：我们在看同一个东西，也能一起改变它

我希望对话保持整个产品的连续入口。助手能根据原话、真实工具结果、当前选择和相关前情，决定此刻什么值得呈现，并把它直接放到用户需要的位置。

一段交谈可以自然地从文字展开成地图，从地图接上时间安排，从已经确认的图书馆行程接上预约与准备的材料。共享的是地点、日期、前情和用户的选择；地图、天气、成绩和笔记仍然保留各自适合的阅读与操作方式。

不要要求每次随口一问都先创建完整“事项”，也不要把所有内容都塞进同一种卡片。查一个成绩可以直接回答；“这一片以前没逛过，带我看看”可以自由探索；“今天不想赶，就在附近待着”也应成为值得认真设计的体验。

核心感受应当是：

1. 我还没开始手动标点，助手已经结合当前交流找到了合适的地点与路线。
2. 地图出现时，第一眼就能回答我关心的问题。
3. 它移动得很有判断，知道什么时候看全局、什么时候靠近某个入口。
4. 我一伸手，它就把画面交给我。我改变主意，画面能从眼前继续接上。
5. 我说“这里”“那天下午”“换刚才那个”，助手能理解我在界面中明确选中的对象。
6. 它会提前准备，也知道有些时候保持安静更贴心。

## 三、先从一段足够生动的地图体验做起

以下课堂、时间与生活细节都是设计情境，不代表已经查询到了用户当天真实行程。实际呈现必须来自当时可用的数据。

### 分镜 A：下一节课，地图在话说到的地方展开

用户刚结束一节课，问：“下一节在哪？我现在过去来得及吗？”

助手先给有用的回答，例如目的地和基于明确起点的时间判断。若只有课表而没有新鲜定位，应自然说明“从上一节课的教室出发”；不要把上一节课地点当作用户此刻的 GPS。

这句话附近直接出现一幅可以拖动、缩放、选择建筑的地图。它有足够的面积辨认道路和端点，第一帧已经包含当前问题需要的空间关系。不要先让用户点进独立地图，也不要每次先从整个城市或校园全景飞下来。

如果用户关心“远不远、来不来得及”，先稳稳呈现 A、B 和连起来的路线，时间结论立刻可读。如果用户关心“怎么走”，在建立方向之后，用一次简洁的空间解释帮助他认识路线：

- 起点与目的地先清楚起来，周围保留一个或几个真正有辨识度的地标。
- 路线沿真实道路逐渐变得明确，画面适度抬高、平移或倾斜，让空间关系好懂。
- 经过容易选择错误的岔路、桥头或楼侧时，才靠近并强调那个选择。
- 最后让目的地与已核实入口保持清楚，停在用户接下来需要使用的视角。

这是一段空间说明。用户不用等动画播完才能读结论或操作。陌生路线可以更有表现力，熟悉路线、重复查看和紧急情况应更快进入有用画面。具体时长由实际距离、信息增量和渲染手感决定，不把固定秒数当成设计真理。

一个值得精修的日常画面是：话说到 B，暖灰建筑中 B 的轮廓先得到轻而清楚的金色强调；一条暖金路线随后从 A 沿真实道路展开。桥头确实需要解释时，镜头稍稍靠近，让桥的两端仍能一起看见。金色沿路带着注意走，镜头停稳以后就安静地留下路线，像有人将校园摊在桌上，沿着路给你指了一遍。用户伸手，这次指引马上停下，画面自然跟着手走。

### 分镜 B：我先回去拿电脑，再过去

用户继续说：“我先回 A 拿电脑，再去 B；之后还要回 A。”

沿用正在讨论的旅程。把停靠顺序、必要的停留时间与回程接起来，地图和简短的时间关系共同解释这件事是否可行。新增地点时，只更新受影响的部分，让用户看得懂哪里改变了、增加了多少路程或时间。

A 是同一个地点，但在旅程中可以出现多次。地点身份、停靠实例与路段身份要能够表达 A→B→A、A→C→B→A 等顺序。回程需要根据真实约束生成自己的路段；不能假设将去程折线倒放就一定是有效回程。

当去程与回程完全重合，不要堆两条同时闪烁的线。让当前讨论的路段有明确方向，其他路段保留轻量上下文，配合可点选的停靠顺序即可。用户选择“回到 A”，地图知道是在看回程；如果他只是说“镜头回到 A 看看”，应能理解那只是观看请求，并未改动安排。

### 分镜 C：动画中，我用手接管

镜头正在去 B 的途中，用户拖动地图去看旁边的楼。画面立即跟随操作；相机、路线强调和待执行的自动纠偏都交出控制，之后的迟到回调不能再把画面拉回去。

用户手动查看期间，新的解释可以通过文字、轻量标注或路段强调补充。只有明确的继续讲解、回到路线或新的空间观看请求，才重新移动镜头。不要为了“跟随助手”持续争抢视角。

用户在镜头运动时说“等等，先看 A”，画面从当前可见状态自然改向。无需先完成旧动画，无需瞬间跳回初始镜头。展开、收起、替换路线也遵循这种连续性。

### 分镜 D：触摸也进入交流

用户点中一栋楼，接着说：“那我先去这里，回来还来得及吗？”

助手应当知道“这里”对应的稳定地点身份，以及用户正在试算。这是对话与界面真正接合的关键场景。

把操作按含义处理即可，不必为手势构建庞大分类系统：

- 拖动、缩放、旋转是观看操作，通常留在本地，不改计划，也不逐次调用模型。
- 选中地点、路线、日期或时段，会产生明确的当前引用或试算选择，能接回下一句话。
- 真实预约、修改已有日程等行动，仍走项目当前的执行能力与结果记录。

可以在输入区域附近自然表达“关于这栋楼”“按周六下午”，并允许轻松取消引用。具体样式由你设计，避免每选择一次就增加一条大消息或一排标签。

### 分镜 E：到达后，场景接着帮忙

当有可信的到达信号，或用户明确说“我到了”，地图可以收成恰当的空间提示，将接下来真正有用的内容接上：预约信息、开始自习前的一小条笔记、要找的书、离开前要做的事。

路线预览播放到终点，不等于用户到达。没有真实到达依据时，停留在预览或计划状态。

## 四、动效的审美与手感

我参考的方向是 Apple 对即时反馈、可中断和空间一致性的解释，以及 Google Maps 对路线总览、街道细节、入口与相机路径的设计。请把这些原则翻译成适合当前校园数据和窗口的体验。

每次镜头动作应帮助回答一个问题：在哪里、往哪里、哪里要转、从哪里进、改变了什么。不要只因引擎支持 flyTo 就让镜头不断飞。

把“人在走的路线”和“相机观看路线的轨迹”分开。道路几何必须沿现有路网，镜头则可以稍微领先、侧移、升高或保留一个熟悉地标。不要让相机机械贴着每个道路顶点急转，也不要为了曲线漂亮把实际路线画到楼里。

保留现有暖灰与金色的语义，金色优先用于当前路线、选择或此刻的重点。地图底色和周边建筑退到合适层次，详细标签随视野逐步出现。选中的楼、所需入口和路线端点应被清楚区分，不能被浮层、工具栏或字幕盖住。

少量浮动控制可以用薄而有层次的材质，让人理解它在地图之上。大段正文、成绩表和所有地图内容不用一律变成毛玻璃。文字的可读性、真实空间的层次和恰当留白比装饰数量更重要。

按钮按下要及时反馈，直接操控应跟手。运动中改变目标时从当前状态衔接；迟到数据和过期动画不能打断用户已经开始的新操作。旋转、倾斜和缩放适度配合，避免每次更新都同时大幅改变三个方向。

路线预览的游标与真实定位点应有明确区别。预览可以被播放、暂停、继续或按行程位置查看，但不需要常驻一整排播放器控件。真实定位应具有自身的新鲜度与精度含义，不从演示进度推导。

支持减少动态效果；必要的路线、方向、端点与变化仍能通过稳定画面理解。平面兼容模式要继续好用，允许它通过平移、适度缩放、路线强调表达相同意图，不必伪装成已经拥有完整 3D。

## 五、呈现的位置也要设计

推荐以“对话中按需展开的场景”为日常入口，配合可自然进入和返回的聚焦查看。

内嵌时，地图应出现在相关句子与后续解释之间，宽高足够承担当前空间问题，文字继续自然阅读。数据尚未齐备时保持稳定的布局位置，显示已有信息与真实等待阶段；数据到了就可使用，不额外等待装饰动画，不显示编造的百分比。

遇到复杂往返、比较多处地点、仔细找入口时，同一个场景可以进入更大的聚焦区域。设计目标是保留用户正在看的对象、镜头意图、当前选择和交流前情。尺寸变了可以重新拟合可见范围，不要求机械保持相同缩放数值。

桌面可以保留轻量交流入口；窄窗口和手机键盘打开时，可以采用可自然唤回的输入方式。具体布局通过真实渲染选择，别为了同时塞下完整聊天、地图、详情和输入框而形成拥挤的多栏控制台。

收起时回到自然的对话位置；重新展开时接着看，不再重复校园全景开场。进入聚焦态不应使用户忘记刚才说到哪里。

自由探索时，可以设计更沉浸的空间视图，让地图暂时成为主要内容。把它作为确有价值的探索模式，不强迫每次查教室都进入全屏旅行片。

仔细处理聊天滚动与地图操作的竞争：桌面滚轮经过内嵌地图时不应轻易误缩放，触摸设备要保留自然的拖动和双指操作，键盘也应能完成地点选择与必要动作。使用平台熟悉的方式，依据实测调整，不规定一套未经验证的万能手势。

## 六、主动照顾的想象力

主动性由主模型理解原话、日程、可信观察与相关前情后判断。不要写成“提到下一节课就展示地图”“提到下雨就展示天气卡”的固定路由。

延续项目已有的 attention、help opportunity、preparation 和通知机制，让呈现与它们接通。已经准备好的地图可以在自然的交流节点出现，不必永远藏在需要手动打开的“可用资料”里；准备完成本身也不是打断用户的理由。

可以设计不同力度的参与：

- 先准备：已知下一节课和可能的出发前提，但用户正在处理另一件事，先把可靠结果准备好。
- 自然加入：话题转到下课、出门或下午安排时，直接带出有用的一句解释与恰当大小的地图。
- 及时提醒：确实将错失重要出发窗口，才使用符合现有约定的提醒方式。提醒解释原因，允许用户说“先不去”“我已经在那边了”并立即接续。

主动照顾也可以是发现用户已经进入合适的学习状态，即使另一个地点条件略好，仍判断留在原地更符合这次需要。不要从点过几次某栋楼推断长期偏好，也不要把“今天不想跑”固化成“用户不爱运动”。

记忆中的理由和条件很重要。例如用户明确说过“换地方会打断我刚进入的状态”，在相关情境中应能使用这条有出处的理由；用户改变想法时，以当前原话和必要证据更新理解。界面选择只是当下证据的一部分，不自动升级为人格或长期偏好。

主动展示地图也要允许被一句话轻松改写：“我还没下课”“我已经到西区了”“今天想绕一圈”。从当前前情继续，而不是清空后让用户重新填起点、终点和意图。

## 七、放开想：从地图长出来的生活体验

下面是设计空间，供你理解共同基础需要容纳什么，并据此创造更好的情境。它们不是要求这次把所有外部服务都接齐。实现范围见后文；远景可以设计完整，展示时准确区分真实能力与待接入能力。

### 1. 日历：看见真正能用的一段时间

“下午两节课之间，我能去图书馆待多久？”

可以出现一段简洁的时间带：前一节课、路上时间、真正可用的自习时间、收拾与返回、下一节课。用户看见的重点是实际可以安稳坐下多久，而不只是课表上的空白有多长。

点选图书馆或另一栋楼，地图与时间关系一起变化；拖动一个候选时段是在试算，助手能理解“那就这个时间”。接受安排之后，才按当前本地日程能力保存相应对象，不把拖动演示当作已经修改了学校课表。

这里可以形成一个很有辨识度的动作：用户点向另一处地点，原路线轻轻退下，只有变化的那段暖金道路变得清楚；新的路程确定后，时间带里“可以安稳坐下”的空白随之伸长或缩短。旁边只说这次选择最有用的结论。空间上的改变和属于自己的时间，在一个连贯动作里接上。点击“还是刚才那个”或直接这样说，都能自然返回原方案。

用户也可以说“这段别给我安排，空着就好”。空白应被当作一个有价值的选择。日历无需总是填满，更不应该把每件生活小事都变成待办压力。

### 2. 天气：只呈现眼下需要的时间尺度

问“这周哪天适合在外面待一会儿”，可以用轻盈的七天带直接比较每天的气温和降水条件；选中某天后继续说“那就那天下午”，助手能把日期选择接到现有本地日程中。

问“去上一节课会不会淋雨”，理想的未来体验是把出发时间与整段行程放在一起，滑动时间即可查看对应的预报变化，而不必翻进天气应用。可以让地图中的光线和氛围适度配合，但明确它表达的是预报或时段；装饰性的天气效果不能冒充现场观察。

当前只有杭州七天内按日预报，可以真实完成按日比较和日期引用。它不能支持“二十分钟后停雨”“某一小时是出发窗口”这样的结论。逐小时、分钟级与路线局地天气须在接入相应数据并说明时间与覆盖范围后实现，不能用按日概率插值伪造。

同一个天气视图也可以服务轻松的交流：“我想挑个舒服的傍晚散步。”不必强制将它变成正式日程；助手可以先给有依据的选择，等待用户继续。

### 3. 成绩：让用户迅速看懂自己问的那件事

问某一门课，直接呈现课程、成绩和需要的解释；问整学期，给可读的成绩表、学分与口径；问趋势，才出现适合比较的图。不要在一个简单查询后默认塞出完整学业仪表盘。

用户点中一门课，再问“这门对总绩点影响有多大”，助手应带着当前课程、学分与计算口径继续，给可核查的说明。不同学期或不同来源 GPA 必须保留自己的范围，缺失数据不能悄悄按零分计算。

如果讨论复习或学习安排，可以在得到用户意图后把相关考试、课程材料和空余时段接起来。不要由高分推断掌握程度，也不要把低分变成人格、能力或态度标签。视觉可以舒展、平静，具体成绩值得被清楚对待，无需自动礼花、排名焦虑或游戏化奖惩。

### 4. 图书馆：从“能去哪儿”接到“到了做什么”

用户说：“找个地方安静坐两个小时，之后还要回去上课。”

理想体验是先比较真实可用时间、路程和有证据的地点条件。如果有可信的座位数据，就从建筑地图自然进入相应楼层或座位图，座位可点选、时间可比较；没有座位几何，就清楚呈现真实的房间或预约记录，不画一张看似精确的虚构座位图。

用户选好之后，真实办理应走现有或后续接入的写入能力。候选、提交中、已成功、失败和结果未知要与实际回执一致；读取已有预约不等于能够新建预约。若提交结果未知，先核查同一行动的结果，再决定后续，避免重复占位。

已确认的预约可以接上去图书馆的路线、真正需要的签到时间与用户准备做的事。对已经有预约的人，不必再次让他挑座位；到达后，视图可以把重点交给座位信息和学习材料。取消或改时间时，只更新受影响的行程与提醒。

### 5. 体育打卡：呈现事实，也给身体和心情留余地

“这学期还差几次？今天要不要去？”

先区分学校系统认定的有效次数、用户自己记录的活动、未来手机测得的运动。三个来源不能因为都叫“跑过了”就合并成学校已认定次数。计数、适用规则、统计时间和缺失范围按真实连接器给出；字段不足时就明确不足。

如果已经知道剩余次数、截止日期与可用时间，可以帮助用户看见还有哪些从容的机会。呈现一小段事实与合适的可选安排即可，不做天天催促的红色进度墙。

结合天气和用户当下想法，可以出现去操场的路线、可行时段，以及“今天休息”的自然选择。“今天休息”只影响这次判断；不要写成长期偏好，也不因用户没接受建议而不断追加提醒。

未来手机开始运动时，界面可以收成适合边走边看的距离、用时、位置质量与必要控制。轨迹计算、定位精度、后台权限和学校认定规则需要分别接入。地图动画转了一圈绝不表示完成了一圈运动，更不表示获得一次有效打卡。

### 6. 笔记：让一句念头在合适的地方重新遇见用户

“下次到图书馆附近，提醒我看看那本书。”

这句话可以保留原文、具体书名和触发条件，并成为未来行程中可被考虑的一件小事。下次讨论去图书馆时，助手知道用户曾经想做什么；可以指出是否顺路，而不总是另开一个大提醒面板。

“先别管这件事”“我已经看过了”“下个月再说”应能改变这条意图。经过附近是有条件的机会，不是每次经过都必须通知。只有行程预览而没有实际位置时，不推断用户真的到了那里。

地图上的建筑、一次预约、某门课都可以成为笔记的可引用对象；自由写作仍保持自由，不强迫每条念头填写结构化表单。当前材料与原话能力可以作为基础，完整笔记工作区是否存在、需要补充哪些能力，要依据当前代码判断。

### 7. 整个下午的轻量预演

“先上课，去图书馆取书，再到操场，最后回来。”

这是一个很有潜力的探索方向：时间带与地图是同一段安排的两种观看方式。轻轻选中某一站，地图看向那一段，时间带解释到达、停留与下一步。用户调整一个停靠点，能看见改变的路程和真正剩下的时间。

未来若天气数据足够，可以把选定时段的天气也接入这一段预演。重点仍是帮助用户决定怎样过这个下午，不需要把日历、天气、地图、预约各自的大面板堆到一起。

必要时保留两种方案：“从容一点”和“多去一个地方”，让它们围绕真实差异比较。方案名称和判断必须来自这次交流；不预设所有人永远偏好最快路线。

### 8. 没有任务的探索与陪伴

“这片校园我一直没逛过。”“我今天不想赶路。”“附近有没有值得坐一会儿的地方？”

允许助手温和地组织一段空间探索。可以先让用户认出自己熟悉的地标，再把附近有可靠资料的地方慢慢带入视野；点到感兴趣的建筑或地点，就围绕它继续聊。

探索模式可以慢一点：先把熟悉的桥或建筑留在画面一侧，缓缓带入校园更远的一角。具备空间体量的模式中，用一次轻微的弧形移镜显露楼与楼之间的关系；平面模式通过平移、适度缩放和标签层次完成相同发现。金色只落在此刻介绍的地方，镜头在值得继续了解的位置停下，留出用户自己看看、随手点选的时间。

不要为了推荐而虚构“那里现在没人”“这条路特别安静”“这家店此刻营业”。有依据的环境信息可以用，没有依据时保留不确定性，也可以邀请用户自己发现、自己描述。

如果用户只想倾诉，地图可以已经准备好，但先不出现。好的主动性包含等待和理解；它不需要把每一段情绪都变成出门、运动或效率建议。

### 9. 电脑到手机：同一段生活继续发生

未来从电脑起身时，手机能继续刚才选定的旅程、下一站和相关前情。打开后优先呈现此刻需要的那一段，无需重演整条路线。

这里应保持对象身份与选择的连续，同时重新核查位置与数据的新鲜度。电脑上假设的出发点不能覆盖手机的新鲜定位；用户刚才观看的路线也不能被当作已经实际走过。

手机布局需要依据单手操作、键盘遮挡、屏幕方向和边走边看重新安排。可以自然收起输入，再随时唤回交流，避免把桌面窗口等比例缩小。

先在本次基础中保留清楚的状态与事件边界。真正跨设备同步、手机原生定位、后台提醒和健康平台接入，按未来明确能力逐项落实，不用一个假“同步成功”按钮提前宣告完成。

## 八、OpenUI 在这里应承担什么

用户指定的项目是：https://github.com/thesysdev/openui 。
本次检查的主分支版本：8d9c4c3b108a7b5352192a6a9d7327bdf7ea19b5，MIT。
开始实施时按当前官方文档与实际安装版本重新核对必要 API，不盲目套用本文件记录的旧接口。

OpenUI 可以作为现有聊天的呈现适配层。它允许用 defineComponent 注册带 schema 和说明的 React 组件，createLibrary 组成允许模型使用的组件库，让模型输出 OpenUI Lang，经 Renderer 解析后成为界面；交互通过本地状态与结构化动作继续发生。

官方明确支持已有聊天界面只更换助手消息渲染，保留原来的消息列表、输入框、会话与传输。若使用自己的组件，不必搬入 react-ui 的整套默认皮肤，也不必用 AgentInterface 重建当前产品。接入开源 runtime 本身不要求更换模型、购买托管 API 或换掉 Hermes。

优先围绕真实的校园地图、按日天气和本地日程注册适合本产品的组件。模型理解“此刻看哪一段旅程”“比较哪两个日期”“强调哪一个入口”，现有业务工具提供事实，地图引擎完成精确运动。

组件属性引用经过主机验证的数据、对象、路线与稳定地点身份。不要让模型逐帧输出经纬度、编写一张新的校园地图，或生成任意 JavaScript 执行。模型有足够表达力选择与组织呈现，具体 schema 和组件边界由你依据现有代码设计，不必使用某套固定命名。

用户无需每次说“请渲染地图组件”。主模型从原话、当前对话与可用能力判断是否值得展示、怎样组合。继续使用现有上下文与取证方式，别另造一个先按关键词分配 UI 模板的意图路由器。

本地拖动、暂停、已知选项切换、表格排序等即时动作直接响应。确实改变交流语义的选择，带上对象、引用与当前意图进入助手上下文；需要新查询、新判断或真实行动时，再调用相应工具。

如果当前 OpenUI 版本存在集成限制，先认真读源码并用最小适配解决。保留自有业务契约与组件，避免让整个应用依赖某段不稳定 DSL 文本。若仍有关键阻塞，准确说明阻塞和采取的替代方式，不能用普通静态卡片加上“OpenUI”名字声称接入完成。

## 九、共同基础需要守住的连续性

这部分是实现设计意图所需的状态关系，不要求你照抄一套新的大型架构。优先扩展已有 SharedMatterView、对象版本、交互与执行机制。

### 事实、当前对象与观看状态各自清楚

事实应能追溯来源、时间、覆盖范围与必要条件：哪一份课表、哪次天气预报、哪版路线、哪个预约回执。UI 看起来连贯，不代表这些信息具有相同的新鲜度。

有持续交流需要的旅程、安排或候选保留稳定身份、当前版本与用户选择。简单查询无需强制升级成一个完整事项。呈现对象能引用它们，也能呈现一次性的查询结果。

场景或视图有自己的稳定身份；相机、选中的路段、展开状态、试看的日期等属于观看与交互状态。临时视角不自动写入长期记忆。重要选择能够被下一句“这里”“那天”正确引用，并清楚区分试算与已接受安排。

真实行动沿用项目已有权限、执行、版本核查和回执。用户选择一张图、模型生成一个按钮，不自动等于已经预约、修改日程或完成打卡。准备、候选、提交、成功、失败与未知结果，按真实过程呈现。

### 当下可以变化，旧对话仍保留当时的意思

历史消息保存当时讨论过的结果。今天打开昨天的天气，不应悄悄换成今天的查询；看旧行程，不应让它暗中变成最新课表。

当用户要重新采用旧安排时，核查受影响的事实与行动条件，再接续当前对象。只在有意义的位置轻轻说明“这是上次的安排”“教室后来改到了这里”等变化，不把 revision、token、协议字段摆进产品正文。

回看旧消息不应自动重播路线，不应自动提交操作，不应让几十个地图实例同时占用资源。当前活动地图应立即可操作；离屏或历史内容可以采用保留快照与可恢复状态的资源策略，由实际性能与连续感决定。

### 流式呈现保持稳定

已经有经过验证的数据时，尽快呈现有用的第一帧。流式增加文字或更新局部内容不能频繁重建 WebGL、重置镜头、改变已选对象或不断推移聊天位置。

地图宽高变化、内嵌与聚焦切换、下一轮模型回复和历史恢复都要考虑稳定身份。确有需要重建渲染实例时，应恢复场景与镜头意图，让用户可以自然继续；不要把某个 React 节点存在就当作已保证连续性。

用户取消生成、换路线、切换话题或关闭视图后，已过期回调不能继续驱动相机、更新旧选项或执行真实动作。保留有效结果，针对当前动作准确取消即可，不因一处更新重置整个会话。

### 让以后接入一个新领域有明确入口

一个新领域至少应能提供：适合模型选择的组件说明与属性契约、可追溯的数据引用、自己的直接交互、能回到交流的语义选择，以及需要时的真实行动桥接。

地图与天气无需共用同一布局，但应能共享“刚选了哪个对象、这个结果属于什么时候、下一句话怎样引用、重新使用时检查什么”。组件库负责表达可用呈现；主模型继续判断对用户有什么帮助；现有主机运行层负责准确的事实与执行边界。

## 十、实施前值得知道的具体代码现场

以下观察均基于前述研究版本，用于少走弯路。行号和接口可能随着当前代码变化，请按职责重新定位。这里给出的是已发现的约束，不要求你为每一项增加一套新框架。

### 1. 抽出真正可复用的地图表面

重点阅读：

- src/renderer/App.tsx
- src/renderer/map/CampusMap.tsx
- src/renderer/map/map-engine.ts
- src/renderer/map/map-state.ts
- src/renderer/map/map-types.ts
- src/main/mapService.ts
- src/main/capabilities/spatial.ts

MapSheet 同时负责 dialog.showModal/close、地图实例创建销毁、定位循环及若干模块级状态。研究版本中的 savedCamera、savedSelection、entered、sessionLocationEnabled 等状态，在多张内嵌地图之间可能串联。

因此，应抽出共享的地图 surface/controller 与恰当的场景状态，让对话内嵌、聚焦查看和原地图入口使用现有引擎。直接把整个 MapSheet 注册成一个 OpenUI 组件，会把弹层、定位与全局状态问题一起带入聊天。

定位应复用现有主机能力并明确生命周期，避免每条历史地图独立申请位置、启动重复轮询。保持当前地图数据、路线服务和兼容路径的一致性；不另建平行校园地图或另一份地点库。

### 2. 在已有 CameraOwnership 内补齐可取消的编排

map-state.ts 已有 CameraOwnership，以 revision/ticket 拒绝旧动作；map-engine.ts 的指针、滚轮与 takeControl 已会接管、停止相机、停止 reveal 并取消待发生的路线拟合修正。

这是很有价值的现成基础。新编排应把一次“解释旅程”的开始、阶段完成、替换、手势接管、销毁与过时回调纳入同一套权属机制。使用地图引擎实际的完成/取消信号衔接阶段，不靠几个 setTimeout 猜镜头已经完成。

注意当前方法的实际语义：zoom、rotate、north、setPitch、overview、focusPlace、fitRoute 都会调用 takeControl；取一次 ticket 后连调这些方法，可能被自己的第一步使 ticket 失效。研究版本 fitRoute(result, ticket) 只要 ticket 非 undefined 就返回，不能想当然把它当作已经支持自动编排的接口。

可以调整现有内部接口来区分用户命令与同一编排内的阶段动作。不要在旁边再造一个相机拥有者，分别直接操作同一 MapLibre 实例。

### 3. 复用路线几何与已有预览

研究版本 map-engine.ts 已根据真实折线建立累计里程，按逐段道路插值，保留转弯；已有约 640 ms 的路线强调，以及明确标为“路线预览，非当前位置”的进度游标。

路线拟合已考虑标签、控制区、边界与有限次的实际测量修正。发展这些能力，避免为了动效重新绘制一条与道路脱节的装饰曲线。估计或条件路段在强调过程中也要保持原有虚线等含义。

相机编排和真实行程可以分别建模；复用现有步行路网，不能用更快的播放速度宣称已经支持骑行或手机实时导航。

### 4. 接上已经存在的事项、选择与准备机制

重点阅读：

- src/shared/presentation.ts
- src/shared/interaction.ts
- src/shared/harness.ts
- src/renderer/HarnessViews.tsx
- src/renderer/LifePanels.tsx
- src/main/runtime/context.ts
- src/main/runtime/attention.ts
- src/main/capabilities/campus-query.ts
- src/main/capabilities/builtin.ts

SharedMatterView 已有对象与选项 id/revision、selectedOptionId、placeId；MatterSelectionInput 已有 expectedRevision；ObjectPresentationState 已表达历史与当前对象的变化关系。优先接通这些身份和版本，不再建立一份互不理解的“OpenUI 选择”。

上下文已经有 authoredText 原话、会话历史、当前事项、观察、准备材料与能力目录。保留主模型基于原话自主取证的方向，让有意义的界面引用自然进入这里。

AttentionService 已有 prepare/wait/ask/notify/none、有效期、去重及不同呈现/通知方式；PreparationShelf 当前主要呈现材料文本。主动地图应接到现有准备与呈现路径，既有真实触发与生命周期，也能在恰当时机直接进入对话。不另造一个只看时钟和关键词的提醒器。

### 5. OpenUI Action 并不自动等待任意动画

在 OpenUI 研究版本的 packages/react-lang/src/hooks/useOpenUIState.ts 中，ActionPlan 遍历动作时会 await Mutation，但自定义动作调用 handler 并不 await 宿主动画完成。

因此下面这种表达不能直接被当作可靠的视觉时间线：

Action([@FlyToA(), @TraceRoute(), @FlyToB()])

它可能很快发出三个事件，相机动作互相取消。更合适的是一个语义动作请求“展示这段旅程”，由地图控制器在已有权属机制中执行，并根据真实完成、取消与新意图接续。具体动作名字由你设计。

### 6. 流式、增量编辑和状态恢复有具体边界

同一 OpenUI hook 在 isStreaming、响应包尚未完整或存在响应包解析错误时，阻止新 Query effect 提交。这里对应 bundle.error，不代表所有 DSL 类型错误或可恢复警告都会统一阻止 Query。不要承诺模型刚输出 Query 开头就会立刻取数。快速呈现可优先使用现有工具已经准备好的可信结果和引用，再让稳定视图展开。

研究版本 Renderer 对数组子项使用索引 key，未解析引用可能从数组中移除。因此，即使 DSL 中 statement 名称相同，也不能保证流式插入或重排时 WebGL 实例天然不重挂载。这是从源码结构得出的集成风险，尚未在当前产品实测复现；请围绕稳定 view/scene 身份验证实际行为，不把推断写成已经发生的故障。

官方增量编辑可以按 statement 名合并补丁，但示例等待补丁流完成再合并，以避免半写完的 root 导致节点暂时不可达。设计局部更新时应核对当前实现，不在每个 token 到达时重建整个地图。

消息协议可保存 UI 文本及 context，但 Renderer 忽略 context；宿主需要解析、通过 initialState 恢复，并用 onStateUpdate 保存合适状态。组件库版本和业务事实快照也由宿主明确管理。运行实例的 Query 缓存不等于跨会话或跨设备的数据存档。

组件说明与 schema 中的动作限制不能代替主机执行校验。仍以「在场」的权限、对象版本、当前真实能力和执行回执决定能做什么。

## 十一、本轮实施应完整做到什么

以对话内地图作为第一条完整链路，并用一个现有数据足以支持的非地图场景证明共同基础能延展。优先考虑“七天按日天气选择日期 → 下一句‘那就那天下午’ → 接续本地日程”，或者同样有说服力的现有日程与地点接续。

这里要证明的是界面选择能够进入持续交流、不同领域能够引用同一个日期或地点；仅仅把两个互不相干的组件摆在一起，不足以说明基础已经接通。

地图这条链路应覆盖：

1. 主模型在实际交流中根据上下文与工具结果选择呈现地图，用户不用额外点“打开”。
2. 地点解析和路线来源可靠，A→B、A→B→A 与增加停靠点都能连续解释和修改。
3. 用户在运动中直接接管，或者用下一句话改向，画面从当前状态接续，旧回调不会抢回控制。
4. 用户在地图中点选地点，再用“这里”继续交流，助手能够正确理解；观看、试算和实际行动的含义清楚。
5. 内嵌、聚焦、收回、多轮更新与历史回看保持合理连续性，当前地图真实可操作。
6. 现有准备/注意力机制能够在一个合适情境下带出有依据的地图帮助，并允许用户纠正前提、延后或改主意。
7. 没有 WebGL 或启用减少动态效果时，必要信息与直接交互仍能成立。

与此同时，为天气、日历、成绩、预约、笔记与活动数据留下清楚的组件、引用和动作接入方式。可以补充有真实依据、能让整体体验更完整的小功能，不把远景写成空壳按钮，也不为了“全部完成”虚构外部服务。

关于当前未连接能力：可以给出具体设计、接口接入位置与后续所需事实。不要把缺少的逐小时预报、实时空位、真实预约写入、手机位置或运动认证用演示数据冒充接通。开发夹具可用于隔离验证，必须与用户真实结果、实际执行和公开演示明确区分。

## 十二、怎样判断你做出的东西值得交付

先运行当前实现并真实操作你改变的路径。截图能帮助检查构图、文字和遮挡；动画连续性与手势接管需要实际播放与中途操作，不能只凭静态图或“调用成功”判断。

最重要的观察是：用户一眼知道在哪里、什么时候行动；修改意图时界面跟得上；自由查看时助手让开；下一句话能接上当前选择；回来后仍认得同一段交流。

选择少数有辨别力的真实场景观察：一条陌生路线及入口、一次往返中途改向、一次触摸接管、一次内嵌与聚焦往返、一次界面选中对象后的指代、一次跨领域日期接续。对已经足够验证的结果不反复制作视频、截图矩阵或表面评分。

针对本次确实引入的状态与执行风险，加入必要验证，例如过期相机回调、旅程版本替换、流式更新中的稳定视图、历史结果与重新采用、动作重复触发。复用现有测试与夹具，不为低风险样式改动编写镜像实现的测试。

按当前 AGENTS.md 执行相应门槛。研究基线要求模型实测只使用 GPT-6 Luna 测试替身，不做 DeepSeek 测试；生产模型和 Hermes 契约保持项目规定。开始时重新确认当前规则，别为了这项 UI 接入迁移整套模型运行方式。

遵守当前源码与公开评审资产的边界。公开地图预览可以使用仓库允许的公共地图数据，私人原话、账号、模型配置、定位和校园查询结果不进入公开构建或源码提交。不要因为需要展示效果就自行发布含真实用户数据的页面。

有设备或连接器限制时，准确写明哪个环境、哪个路径已验证，哪个仍未验证。平面兼容路径通过不表示 2.5D 动态已经验证，模拟预约通过也不表示真实办理成功。

完成后给出：

- 最关键的设计选择，以及它们怎样回应这里的生活情境。
- 实际完成的连续交互与当前使用方式。
- 相关代码与文档变更、必要的运行与验证结果。
- 足以判断效果的代表性画面；若用动图或短视频，围绕真正需要展示的运动与接管过程。
- 仍需真实数据或设备接入的部分，及下一步明确入口。

不要把交付结论写成几十条内部检查项。让人清楚知道这次产品能够怎样用了，为什么更自然，还有什么具体限制。

## 十三、研究依据与继续阅读

这些资料提供设计原则、实际示例或当前 API 依据。请迁移适合本产品的判断；Google 的影像与三维数据能力、Apple 原生系统 API 都不能被当作本项目已经具备的资源。研究时阅读了官方文字、逐字稿与源码，并观察了 Google 官方路线示例画面；没有据此声称亲自操作过所有参考产品的完整动效。
